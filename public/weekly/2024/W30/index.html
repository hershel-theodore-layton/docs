Week 30: Jul 22–Jul 28, 2024

8 noteworthy changes, organized by the source changelog sections.

Breaking Changes

3 changes
  • Mon, Jul 22
    ConstIndexAccess and IndexAccess now constrain their key type parameter with as arraykey; collection contains() and containsKey() declarations received the same constraint. Custom implementations and calls that explicitly supplied an unconstrained, non-arraykey type argument may now fail type checking. 716478479e
  • Wed, Jul 24
    The HHI for HH\ImplicitContext now exposes the abstract IS_MEMO_SENSITIVE boolean and CRun context constant introduced in systemlib earlier this month, so typed subclasses must define both. Calls to runWith(), runWithAsync(), get(), and exists() must provide a capability set that is a superset of the subclass's selected CRun; [this::CRun] states a callee requirement and does not grant that capability to the caller. Both runWith() and runWithAsync() additionally carry the callback's contextual requirement through ctx $f. 0746e19f3f
  • Wed, Jul 24
    The hh --xhp-autocomplete-snippet command-line option has been removed. ac67a519c5

Future Changes

2 changes
  • Mon, Jul 22
    Experimental class-level where clauses have been removed from the language. They were never enabled as a supported feature; use type refinements for constraints on associated types. 46632da404
  • Wed, Jul 24
    The disabled-by-default .hhconfig option type_refinement_partition_shapes=true enables constraint-based is refinements for closed shapes with required fields. Open shapes and shapes with optional fields are not yet handled by this path. e99ed3d046

Highlights

3 changes
  • Wed, Jul 24
    When hh is invoked with --from, an explicit --error-format now takes precedence instead of being silently replaced with plain output. 392e317d12
  • Fri, Jul 26
    HHVM now registers ARM JIT trap fixups correctly, preventing trap metadata from taking precedence over the intended fixup and breaking stack unwinding. dec8107878
  • Fri, Jul 26
    HSL sorting documentation now states the comparator contract consistently: return a negative value, zero, or a positive value when the first argument sorts before, equal to, or after the second, respectively, as with <=>. b3a1874c44
