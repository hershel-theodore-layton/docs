Summary:
We have two APIs for building a naming table:
1. using a crossbeam channel to send workitems as they're encountered, leaving sql writes to a background thread. (used in production scenarios)
   1. this routine also writes two log messages, "creating indices..." and "closing DB transaction..."
   2. this routine requires the caller to have set up a sqlite conn in the correct manner, with the appropriate PRAGMAs for speed
   3. it returns the conn back to the caller, but our only caller merely closes the conn and checks for error during closing
2. using an iterator; this is just a wrapper for the first. (used mostly for tests)
   1. this routine doesn't write any logs
   2. this routine creates the sqlite file, and sets up the conn with the appropriate PRAGMAS. It taks a bool for whether to use the appropriate PRAGMAs, even though there's never any reason not to.
   3. it returns the conn back to the caller, but all of our callers simply drop the conn, without even doing close()?

I don't think there's need for this kind of difference. Also, it's wrong that the PRAGMAs should be duplicated in two places. Also, I am about to write another piece of code which uses crossbeam, and I definitely didn't want to duplicate the PRAGMAs in a third place!

Therefore, this diff consolidates the two:

* I figure there's no real need for the logs, so removed them to make the two functions behave the same. They had the feel of logs which are great for a developer who sits down with firm intent to improve the sql-perf-magic, but not relevant for any consumer of the functions. For what it's worth, "closing db" takes 3s, and "building indices" takes 20s on an unsorted and 13s on a sorted database.
* I figure that knowledge of which magic PRAGMAs to use to construct sql fast is properly an internal implementation detail
* None of our callers need to keep the conn open, and I think there's no reason to believe that the conn that's left open is in a fit state (has the right PRAGMAs) for further activity, so I no longer return a conn.
