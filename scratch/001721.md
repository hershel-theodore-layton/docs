Summary:
# Terminology
Runtime-patching - patching of a C++ object with C++ patch. Both object and patch are generated by Thrift compiler.
Dynamic-patching - patching of prtocol::Value object with protocol::Object patch. These are obtained from serialized data without knowledge of the thrift schema.

# Problem
Today StructPatch structs have following operations:
- assign
- clear
- patchPrior
- ensure
- patchAfter
Every operation is represented as a field in the StructPatch. Ignore operations other than ensure (they don’t have this problem) for now. Ensure has the same type as original struct for which the patch was generated. That works great for both runtime and dynamic patching. But there are several problems with current approach:
- size - ensure and other operations are not optional, so all the fields of original struct are present in the wire serialization even if client never ensured anything.
- slightly broken behavior - API of ensuring a field implies that only specified field should be ensured. But in reality all the fields implicitly ensured (except those that are optional in the original struct) regardless if client asked or not.
- patchPrior never used for non-optional fields - this is effect of previous problem, all the non-optional fields are always ensured, hence patchPrior is never used for them. This is not a big deal, because it doesn’t affect correctness, but may be confusing.

Given all the problems above - current approach works for both runtime and dynamic patching. But size remains problematic, even simple structure of union containing struct containing map of vector values quickly balloons to 1KB of patch size just by ensuring one field in a union and inserting one they with one element into the vector.
Solution to size problem is making all the patch fields terse, this helps a lot, but size is still ~250B. And here is where we get into real problem.

# Real Problem
The best patch size is achieved when we make both patch fields and original struct to be terse. Then minimal patch can be as small as 1B and in my experiments patch size from example above goes from ~1KB to 51B. So where is the problem?

How this works. When fields are ensure they set into intrinsic defaults or custom defaults - former one fill be skipped during serialization and the later one is going to be serialized into the wire. This makes all the fields look like optional in the wire if they have intrinsic default values.

Let’s look at runtime-patching - it just works. Deserialization just sets the fields in ensure value into their defaults and to C++ objects they looks absolutely the same as before.

Dynamic-patching is another story. Remember that on the wire terse fields look like optional. It means that value of ensure operation is going to be an empty struct, but this is intrinsic default for a struct - hence ensure operation itself is not going to be serialized into the wire. **This basically makes ensure operation disabled in dynamic patching because it is never going to do anything.** This is particularly breaks one common use-case where users want to apply patch to a value that doesn’t exist - so they expect that patch will create new value on the fly. Remember here we don’t know the schema, we cannot just create default-initialized instance, we have to rely on ensure to write all the missing fields into the protocol::Object and then apply patch to it.

Once Thrift team turns on terse writes by default for everyone - dynamic patching will be completely broken.

# Solution
One simple solution is to generate something that we can call EnsureStruct (similar to FieldPatchStruct). This struct will contain all the fields from original struct but will make them optional and but have **same types as original struct (this is important!)**. Optional fields disable terseness - meaning that even default values when ensured will be written into the wire. Optional will also fix the ensure semantics - only explicitly ensured fields are actually ensured (before all the non-optional fields were ensured all the time). And patchPrior actually works as intended now.

Let’s look at an example (assume that TerseWrite is enabled on everything):
struct Bar {                              struct BarEnsureStruct {
	i32 field1;                              optional i32 field1;
	i64 field2;                             optional i32 field2;
}                                                }

struct Foo {                              struct FooEnsureStruct {
	Bar bar1;                               optional Bar bar1;
	Bar bar2;                               optional Bar bar2;
}                                                 }

One may ask - why does FooEnsureStruct::bar1 have type Bar and not BatEnsureStruct. There are many reasons:
- runtime patch API structured in a way that user ensures only fields in struct Foo when calling FooPatch::ensure<ident::…>(). There is no sense in making FooEnsureStruct::bar1 to have type BarEnsureStruct.
- When we actually ensure fields of Foo by applying patch we do something like foo.bar1() = *patch.ensure()->bar1(); This requires that both Foo and FooEnsureStruct have the same type for field bar1. And it has to be like that because user may want to ensure the field with non-intrinsic default value, so we have to have correct type to hold it. Or we would be forced to do deep copy of all the fields into all the EnsureStructs recursively.

Let’s look at the dynamic patch.
Here it doesn’t make any difference if type of FooEnsureStruct::bar1 is `optional Bar` or `optional BarEnsureStruct` - because in the wire they will look absolutely the same (remember terse with defaults looks like unset optional in the wire) when all the fields in the original struct are terse.
User has to ensure fields of Foo separately from fields of Bar anyway e.g. user can write
`fooPatch.ensure<ident::bar1>().ensure<ident::field1>() += 1;` This will ensure that both fields are present in the object being patched and the will apply Numeric patch to the Bar::field1. And API actually doesn’t even allow fooPatch to ensure fields in BarPatch anyway.

# Summary
EnsureStruct being complete mirror of original struct but with making all the fields optional fixes the problem with ensure operation for dynamic patching and works for both. On the wire representation is minimal because original structs are going to be terse themself.
