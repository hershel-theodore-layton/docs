Commit title: Use bitset to store coverage instead of vec<int>
Commit body:
Summary:
I think the assumption was that we'd be interested in the frequency of lines covered, but we aren't using frequency at all:

**fb_disable_code_coverage**
There are only 2 callsites of fb_disable_code_coverage: [Hack test coverage](https://www.internalfb.com/code/www/[0f00e348f51c]/flib/intern/testinfra/cli/HackTestFullLineCoverageCollection.php?lines=21) and [Graph API coverage](https://www.internalfb.com/code/www/[e5f3f09e2a1f]/flib/intern/platform/graph/tools/GraphAPIRequestReplayer.php?lines=143). Both of them only uses the line numbers and ignores the frequency.

**fb_get_code_coverage**
There are no callsites

Currently, continuous coverage collection runs for Hack tests use 1024 large sandcastle machines because tests runs are slow and are more likely to OOM. Because WWW tests easily cover lines in tens of thousands of files, I suspect using vec<int> has contributed to a significant memory overhead and might be what's causing some Hack or JestE2E tests to OOM in coverage mode but not in standard mode. https://fburl.com/daiquery/z8mrl363 shows that length of all files covered by a test can be up to 11M, which would mean it could use up to approx 40MB of request memory to store coverage frequency maps. Using a bitset instead should reduce memory usage of coverage storage by about 32x, and might make running coverage collection easier.
