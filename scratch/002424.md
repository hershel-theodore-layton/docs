Summary:
`split_reqs` might indeed be a good bit of code to share, if we find we often need to aggregate requirements of different kinds in physically separate vectors (if we did, an appropriate place might be as a method on Class_ in src/oxidized/manual/aast_defs_impl.rs)! But I think we actually won't need to do this much. A split_reqs function was convenient in OCaml, and it performs well because minor heap allocation is cheap. In Rust iteration over vectors is fast (i.e., guaranteed to be cache-friendly), and allocation is not, so I suggest iterating three times in this case rather than allocating three vecs. I think it's easier to read this way too.

I suggest renaming `elem` to `cls` and using `cls.foo` rather than destructuring. `cls.foo` allows rustc to be cleverer about doing what you actually want: for instance, after the suggested changes, when we write `cls.reqs.iter()`, we automatically take `cls.reqs` by shared reference (rather than moving it out of `cls`), because `iter` takes `&self`. When destructuring, we're stuck using the same binding mode for every field (unless we explicitly opt for a specific binding mode with `&` or `ref` or `ref mut`, etc), so we end up needing to write `*kind ==` rather than `kind ==`.

I suggest replacing "class like thing" in comments with "classish", which is [used elsewhere](https://www.internalfb.com/code/fbsource/[cc31bee78b5c]/fbcode/hphp/hack/src/parser/syntax_kind.rs?lines=63) to mean "class or interface or trait".
