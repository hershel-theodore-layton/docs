Summary:
Behavior of hh_client is to launch hh_server. It will launch the hh_server found in the same directory as the current executable's realpath (if found); otherwise it will fall back to $PATH.

That "same directory" malarky is fine for fbpkg which really honestly does place binaries in the same directory. But it's a poor match for "hh switch buck2" because buck2 doesn't place binaries in the same directory. And it's a poor match for tests. So, I've invented a new cleaner mechanism. If the environment sets HH_SERVER_PATH, then clientStart will launch hh_server from there (with no fallbacks). I expect that tests and find_hh.sh will use this mechanism. It's similar to how serverFormat.go will use HACKFMT_TEST_PATH to launch hackfmt.

I discovered an issue in our buck2 rules. I explained in comments:
```
# Tooling expects that, if you build `:hh_server`, then it will place a
# 'hh_server' alongside 'hh_client'. This dependency is because when we invoke
# 'hh_client', it will sometimes attempt to spawn 'hh_server' assumed to be
# located in the same directory.
# BUT!!! WE'RE NOT ACHIEVING THAT WITH THIS RULE!
# All we're achieving is that we're silencing the various safeguards
# that check whether the directory containing hh_client also contains hh_server
# ...
# What hh_client actually does is look for hh_server in the same directory
# as the realpath of hh_client, and failing that it falls back to an unqualified
# launch of "hh_server" in PATH.
# When you build this current rule and "hh_client" too, then you end up with the
# directory $(location :hh_client) containing two symlinks,
#   hh_client ~> hh_client_precopy/hh_client_precopy.opt
#   hh_server ~> hh_server_precopy/hh_server_precopy.opt
# Because hh_client looks for hh_server in the same realpath, it's not finding
# it, and instead falls back to "hh_server" in PATH, which ends up
# invoking /usr/local/bin/hh_server, which is a copy of find_hh.sh, which
# looks up the current "hh switch" and launches the hh_server specified there.

    name = "hh_server",
```

This diff also updates our integration tests to use the HH_SERVER_PATH mechanism for launching hh_server.

Why am I even working on this?
1. We continue to have loads of flakey tests, which the oncall gets alerted about each week. They're mostly flakey in stressRuns, and all their flakiness boils down to use of hh_paths.py and $(location). I want to clean them all up.
2. I'm planning how to do "hh switch rearch" and I wanted to dig in and make sure I was doing it in a fully principled way.
