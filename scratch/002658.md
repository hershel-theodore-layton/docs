Summary:
This diff (1) adds an extra string to certain existing scuba logs for rare (non-reproducible) scenarios, (2) extends that same scuba logging to two related probably-rare scenarios.

## Context

There's some irritating code in HackIDE to deal with these possibilities:
1. what if VSCode sends didChange but clientIdeDaemon doesn't think it previously had didOpen
2. what if VSCode sends didClose but clientIdeDaemon doesn't think it previously had didOpen
3. what if VSCode sends a request (e.g. hover) but clientLsp doesn't think the file is open and nor does clientIdeDaemon
4. what if VSCode sends a request and clientLsp thinks its open but clientIdeDaemon doesn't
5. what if VSCode sends a request and clientLsp doesn't think it's open but VSCode does

This irritating code was introduced in D20954401 (https://github.com/facebook/hhvm/commit/b37ce847331a259bc1670d4921b12431fdf49b53) (April 2020) from the telemetry observation that people were receiving LSP requests for files that apparently weren't open (i.e. hadn't yet received didOpen from VSCode, or had already received didClose).

## Overall goal

Let's back up. The overall objective is that we maintain a cache of TASTs, and we'd like to keep the TASTs for files the user is working on, but we don't want to grow to an unbounded number of cached TASTs. I'd like to simplify the code. There are two possible routes to simplification:
1. We could just switch to an LRU cache, maybe of size 20, and cache the TAST whenever it's needed even if the file hadn't previously received a didOpen. Scenario1: maybe the user opens a file, closes it, then opens again, and it'd be nice to remember the cache from last time. Scenario2: maybe the user has ten tabs open, then goes through a rabbit-hole of twenty other files they visit, and then the first tab no longer has cached TAST.
2. We could simplify matters and just say "if a didOpen/didChange request has arrived then we will cache the TAST until such time as a didClose arrives"

## What this diff does, and why

But before I do that, I need to know if the paths are encountered in practice and how often. This diff merely adds the scuba telemetry I need.

There already is some logging in fact. It aggregates together cases (1,3,4). I made some observations about these situations.
* About 5 users/day (about 10 occasions per day) we hit one of cases (1,3,4). https://fburl.com/scuba/hh_server_events/8t7onq6w. I looked into a few examples:
* [InitId 4lMlXfAnj3] https://fburl.com/scuba/hh_server_events/cda3x309. This happened shortly after initialize. It didn't see any didOpen, but didChange came for the relevant files.
* [InitId yycd50fVqG] https://fburl.com/scuba/hh_server_events/t7nwvy4o.
It was shortly after initialize. didChange happened soon after, and then nothing (no didClose)
* [InitId s2OApfKctu] https://fburl.com/scuba/hh_server_events/41qngqno. user had been working happily on the file for a while, then got this message 3s before didClose
* [InitId e0IkzA76bW] https://fburl.com/scuba/hh_server_events/te9orhc5. plenty of earlier actions, then got this message 2s before didClose

This diff augments the logging to include cases (2,5), and distinguishes them in scuba.
