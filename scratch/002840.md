Commit title: Persistence for sdt analysis

Summary:
## What

In solve mode, instead of in-memory:
- write constraints to disk
- read constraints back and solve

This is a noop change in terms of high-level behavior.

## Why

This change implements most of what we need for running the analysis on an entire repo, coming in D43658327

## How

A few important details are:
- tast checks are run in parallel, in workers. The lifetimes are `hh > worker > tast_handler`. This leads to the following subtleties:
    - we persist many .hips2 files to disk. Then, on solve, we read all the files into memory and merge their data to create a `Hips2.T.t`
    - some care is taken to reduce the amount of times we flush to disk: primarily so we don't end up with source_file_count hips2 files, which could become unwieldy.

## Design decisions

- hips2 owns persistence, rather than the intraprocedural analysis. This will hopefully make it easier to make more analyses.
- I used `Caml.Hashtbl` instead of `Core.HashTbl` and `Core.Hash_set`
    - advantage: I did this in order for all the data structures to be marshallable without the `Marshal.Closures` flag, since `Core.Hashtbl` contains closures. This enables writing constraints with a different program than the program that reads constraints. Which we'll need if we're writing constraints with `hh` and solving with another executable.
    -  disadvantages: `Caml.Hashtbl` has a number of footguns and rolling our own `Set` is not fun. Also, this constraint that everything has to be marshallable could add an indefinite amount of work in the future.
    - Solution: The next time it's a pain to make something easily marshallable, move orchestration to a separate binary (neither hh nor hh_single_type_check) that generates and solves constraints. Then we can marshal closures. T146711502. I'm biasing in favor of speed of implementation while not taking on much debt (`Caml.Hashtbl` isn't completely evil)
