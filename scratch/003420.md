Commit title: Allow like-type elements in collection constructors with explicit non-like-type arguments
Commit body:
Summary:
Currently, if one writes `Pair<int,string>{getLikeInt(), "A"}` then Hack will error, because it assumes that the type of the constructor expression should be `Pair<int,string>`. This is unfortunate: writing `Pair<_,_>{getLikeInt(), "A"}` is accepted, with type `Pair<~int,string>`. So for non-pessimised types such as `Pair`, and going forward, `vec`, `dict`, and `keyset`, our "pessimisation" conjecture fails, at least without source code changes to type arguments.

So instead, we should support the absence of like types in type arguments to constructors, but infer them where possible. Suppose `$i` has type `int`, `$li` has type `~int`, `$s` has type `string`, and `$d` has type `dynamic`. Then we want
```
Pair { $li, $s } : Pair<~int,string>
Pair<int,string> { $li, $s } : Pair<~int,string>
Pair<arraykey,string> { $li, $s } : Pair<~arraykey,string>
Pair<int,string> { $d, $s } : Pair<~int,string>
```
and going forward, once `vec` is not pessimised, for example:
```
vec<int> [$li, $i] : vec<~int>
vec<arraykey> [$i, $d] : vec<~arraykey>
```
There are a lot of variables in the implementation of collection constructors, so this change is non-trivial. Look to the tests to verify that it does what we want!

For `keyset`, `Set`, `dict`, and `Map`, we change the way that we apply the `arraykey` bound. We know that dynamically this bound is enforced, so it's already safe to allow type `dynamic` to flow to keys. We intersect the `arraykey` bound on to the inferred or explicitly-given key type. So, for example
```
keyset<int> { $li }
```
has type `keyset<int>` when interpreted as a pessimised built-in, and in future, will have type `keyset<(~int & arraykey)>`, once `keyset` is not a pessimised built-in (another diff).
