Summary:
Integration tests are hard! Our experience with other hack integration tests is that they take a while to get robust. They suffer from running on test machines that are doing multiple other things concurrently. Sometimes a simple "hh check" takes too long to start up a server, or connect to a monitor, and the test times out.

For streaming-errors, I want to write several integration tests, and I want a robust platform upon which to build them. This diff makes "test/integration_ml/server_progress_tests.ml" more robust:
1. Each test now runs in its own HH_TMPDIR to be sure that other concurrent tests don't interfere at all.
2. (already prior to this diff) the target has the tag "heavyweight8_experimental" to reduce concurrency with other tests
3. The test has a lot more stderr output so that, in case of failure, it's easy to track down what went wrong: it shows timestamps, command-lines of when we invoke hack, and upon test failure it prints server-log, monitor-log, client-log, and a directory listing of the test's private HH_TMPDIR. To make the stderr output easier to read, it now prints a banner separating each test's stderr.
4. I bumped up the timeouts to 2mins
5. We can never use "Unix.sleep" in tests to wait until something has happened, since that's racey. Instead this diff introduces `let process = hh_open () in let%lwt () = hh_await_substring ~substring:"txt"`. This lets us launch the process and await until a matching line has appeared on stdout. The functions are used in a subsequent diff.
6. I changed the tests to use --custom-hhi-path pointing to an empty directory. None of the tests use HHIs, and by using an empty directory each test can start up quicker.
