Summary:
I discovered a bug. ClientCheckStatus is failing to properly do its watchman check (i.e. check that no new files have changed since the watchclock at the start of errors.bin)
```
# make a file change that introduces errors
$ hh --config ide_standalone=true
No errors!
$ hh --config ide_standalone=true
No errors!
$ hh --config ide_standalone=true
hh_server is busy [typechecking ...]
```
Logs show that `watchman_get_raw_updates_since` is correctly getting a list of changed files from watchman e.g. "flib/intern/chess/ChessBot.php", but `FindUtils.post_watchman_filter` is rejecting these.

The problem is I wasn't dealing with root-relative-paths correctly: `post_watchman_filter` was expecting a fully-qualified path that had not yet undergone symlink expansion.

Overview of how we represent paths in our codebase:
* `string` - this is how we represent filenames that come in from an external source. Some are implicitly relative to CWD e.g. "hh --single flib/intern/chess/ChessBot.php". Others are fully-qualified. Others are implicitly relative to some root, e.g. what we get back from watchman queries.
* `Path.t` - after we've fully-qualified them and resolved symlinks
* `Relative_path.t` - after we've matched the prefix of a resolved path

Out of these three options, "string" is unfortunately the correct type to represent the output of watchman.

What I've done in this diff is make more explicit what's expected, with function names and comments.
