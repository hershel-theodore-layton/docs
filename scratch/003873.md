Summary:
Streaming errors are currently rolled out to 50% of machines. Telemetry shows that about 1% of the time a typecheck ends with errors.bin (the file I added recently into which all errors are written during the current typecheck for sake of streaming) disagreeing with env.errorl (the in-memory datastructure in which all errors are stored). Here's a minimal repro.
```
$ hh stop
$ hg revert --all
$ hh --ignore-hh-version --config produce_streaming_errors=true
No errors!

$ sed -i 's/return $map;/return $map/' flib/intern/chess/ChessBot.php
$ hh --config ide_standalone=true --error-format plain
Parsing[1002] ChessBot.php - a semicolon is expected here

$ sed -i 's/$meeting_times =/$meeting_times2 =/' flib/intern/chess/__tests__/ChessBotTest.php
$ hh --config ide_standalone=true --error-format plain
Naming[2050] ChessBotTest.php - $meeting_times is undefined
```
We expect that final "hh" should produce both errors, not solely the Naming one. (Note that the terms "Naming" and "Parsing" here confusingly do not refer to Errors.phase; they're instead defined in User_error.error_kind to merely reflect `error_code/1000`: 1xxx=Parsing, 2xxx=Naming, 3xxx=NastCheck, 4xxx=Typing, 5xxx=Lint, 8xxx=Init).

The reason the final "hh" isn't printing both errors is because the Parsing[1002] error is absent from errors.bin:
```
$ cat `hh --logname`
...
[2023-04-05 08:51:16.817] [master] Errors-file: completing fd30:26536639 after 1 reports
[2023-04-05 08:51:16.817] [master] Absent from errors_file (1 errors)
  err [1002] flib/intern/chess/ChessBot.php A semicolon `;` is expected here.
```

Why is it absent from errors.bin? Well, this comment (prior to this diff) explains how errors.bin is constructed each time hh_server does a ServerTypeCheck.type_check:
```
    (* The errors file [errors.bin] must accumulate ALL errors. The call below to [do_type_checking ~files_to_check]
         will necessarily report all errors in [files_to_check] using the Errors.Typing phase.
         But there might be other Errors.Typing errors in env.errorl from a previous round of typecheck,
         but which are not in the current fanout i.e. not in [files_to_check]. We must report those too.
         It remains open for discussion whether the user-experience would be better to have these
         not-in-fanout errors reported here before the typecheck starts, or later after the typecheck
         has finished. We will report them here for now. *)
      if do_errors_file then
        push_errors_outside_files
          errors
          ~files:files_to_check
          ~phase:Errors.Typing;
 ```

What I discovered through the repro is that the comment was wrong. I had thought that ServerTypeCheck.do_typing would only ever report errors wit phase=Errors.Typing. But the repro indicates that it also reports errors with phase=Errors.Parsing. Therefore, I wasn't pushing enough pre-existing errors!

This diff fixes it by also pushing pre-existing Errors.Parsing errors.

## Discussion

We were already pushing pre-existing Typing errors. This diff makes us push pre-existing Parsing errors. Should we also push pre-existing Init, Naming, Decl errors?
* I changed it so that every mention of phases in the codebase (outside errors.ml/mli) is fully-qualified as `Errors.<Phase>`, to allow for syntactic search throughout the codebase of where these phases are used.
* `Errors.Naming`: The only place that Errors.Naming is mentioned in the codebase is the earlier Naming phase of ServerTypeCheck, and that already gets pushed, so we don't need do anything here. Indeed it would be wrong to, because all naming errors have already been pushed, so we shouldn't push them a second time.
* `Errors.Decl`: I'm convinced that phase=Decl errors never exist. I'll be adding asserts to this effect.
* `Errors.Init`: this isn't used anywhere in the codebase
