Commit title: Join all of a FactsStore's threads before sending it to the Treadmill
Commit body:
Summary:
When we evict FactsStores, we can't delete them immediately. Currently-running requests may reference them, so we need to wait for those requests to finish. The `HPHP::Treadmill` is designed to do just that. But if work is enqueued onto the Treadmill after the last request finishes, then that work will never be done.

Facts uses the Treadmill to destroy items by putting `std::shared_ptr<FactsStore>`s onto it:

https://www.internalfb.com/code/fbsource/[f8bc8faec62270e2342802078c2121aad942757a]/fbcode/hphp/runtime/ext/facts/ext_facts.cpp?lines=701-702

But if this work is enqueued after all requests have finished, then the `std::shared_ptr<FactsStore>`s will be stuck in a static list of `HPHP::Treadmill::WorkItem`s:

https://www.internalfb.com/code/fbsource/[2ae1f548811b075b9b55fdfeb16082dc5490e01b]/fbcode/hphp/runtime/vm/treadmill.cpp?lines=175-182

And these will be destroyed after process shutdown, during object static variable teardown. This leads to a thread being destroyed during static variable teardown:

https://www.internalfb.com/code/fbsource/[714639a48aa92c0a51bd3a4f8a7af7e829d78ebc]/fbcode/hphp/runtime/ext/facts/facts-store.cpp?lines=505

which leads to `hphp_thread_exit()` being called after `hphp_process_exit()`, which leads to a use-after-free.

This diff does the following:

1. Test Facts GarbageCollection by adding `-vAutoload.MapIdleGCTimeSeconds=0` to an existing Facts test.
1. `hphp_thread_exit()` should never be called after `hphp_process_exit()`, so encode that in an invariant.
1. Add a `FactsStore::close()` method which joins all of its threads, disables updates, and puts it into a "closing" state.

D44521386 is an alternative solution - it causes the Treadmill to immediately run enqueued work if there aren't any outstanding requests. I believe the Treadmill shouldn't be silently dropping work just because there won't be another request between now and process shutdown. But I understand why the HHVM team would be hesitant to accept such a large change to such an old, core piece of code.
