Summary:
This diff implements the revised plan for VSCode status discussed in https://fb.workplace.com/groups/342676619986174/posts/1261199208133906

> I need to rewrite the VSCode status-display to account for our current work to remove HackIDE tendrils into hh_server. So I thought I'd take the opportunity to simplify it. Here's my idea.
1. If HackIDE failed: `⊗ Hack: <reason>`
2. Otherwise, if the most recent shell-out to hh failed: `⊗ Hack: <reason>`
3. Otherwise, if HackIDE is initializing: `↻ Hack: initializing...`
4. Otherwise, if there's a shell-out currently underway: `↻ Hack: [typechecking 53/3250]`
5. Otherwise, if HackIDE is currently fetching decls or typechecking: `↻ Hack`
6. Otherwise, `Hack: ready`

> The principle is: (1) show failures *"computer can't proceed until user does something"* more urgently than progress *"user can't proceed until computer finishes something"*. (2) Within that, show HackIDE stuff more urgently than hh_server, since HackIDE affects far more user interactions. (3) Report it all to the user with the singular word "Hack".

The existing server-reporting functions for RPC connection to hh_server are all really horrible. I decided that this diff won't augment them. Instead it will start afresh with a new function, and later we'll delete the existing ones.

Some additional things in this diff:
1. Previously only clientConnect.ml ever read ServerProgress.json, during a `hh check` after the connection had been established. Therefore by definition there should always be a file, and we logged to scuba if there wasn't. But now, clientLsp.ml will happily try to read ServerProgress.json at any time even without a server (hence even when there is no progress.json file). I therefore removed logging in the ENOENT case, since that's now expected.
   1. I studied telemetry that had been emitted. It gets 5-10 hits a day. The failures I've seen are EINTR (meaning that ServerProgress.read isn't hardened against Lwt) and also failures when the disk runs out of space so the progress file couldn't be written. I added a TODO for the EINTR.
2. I switched to a different status refresh model. Previously it used to refresh status on every single event just prior to handling the event. This had the unfortunately consequence that during an RPC it was unable to update status. I switched to updating every second from a background task. This has the potentially nice effect that when `hh --ide-find-refs" is working then the status will get updated. (but it remains to be seen whether the status that's shown is intelligible to users).
3. The status messages inside the square brackets "hh_server is busy [typechecking 7312/9638 (78%)]" are fairly long. If we tried to render them in the status bar they get truncated "Hack: typechecking 73...". That's no use at all! So, I made the ad-hoc decision that this single most important message about typechecking will not be prefixed by "Hack:" and this way it all fits.
