Summary:
I wish to make some systematic changes to clientIdeMessage.ml in future, and in preparation I'm spending some time streamlining it.

```
type document_and_path = {
  file_path: Path.t;
  file_contents: string;
}

module Code_action = struct
  type request = {
    file_path: Path.t;
    file_contents: string option;
    range: Ide_api_types.range;
  }

  type result = Lsp.CodeAction.command_or_action list
end
```
Don't you look at this and wonder why the duplication? Shouldn't Code_action just use a similar `document_and_path` to everywhere else? Is there something essential about Code_action which means it should take optional file_contents? No.

This diff changes Code_action take a mandatory file_contents, in preparation for the next diff which unifies it with `document_and_path`.

Why is this a safe thing to do? Well, prior to this diff, if it had ever gotten None for file_contents, that would have gone into clientIdeDaemon.ml `update_file_ctx` which had only two outcomes in the None case:
```
    | (None, None) ->
      log_missing_open_file_BUG "update-without-content-or-entry" path;
      failwith "Attempted LSP operation on a non-open file"
    | (None, Some entry) ->
      log_missing_open_file_BUG "update-without-content" path;
      entry
```
The first parameter of this match is the None file_contents. The first would have failed anyway. The second case has happened only once in the past month D43598963 and it looks dodgy anyway so I didn't think it was worth dirtying the code to support.
