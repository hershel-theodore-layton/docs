Summary:
I wish to make some systematic changes to clientIdeMessage.ml in future, and in preparation I'm spending some time streamlining it.

```
module Ide_file_opened = struct
  type request = document_and_path

  type result = Errors.t
end

type _ t =
  | Ide_file_opened : Ide_file_opened.request -> Ide_file_opened.result t
  | ...
```
The code currently looks like this, with one module per message type. I think there are too many layers of indirection and too much typing of module names. This diff therefore inlines the types:
```
type _ t =
  | Ide_file_opened : document_and_path -> Errors.t t
  | ...
```

My principal was: if the meaning of a parameter or return type is obvious (e.g. document_and_path, Path.t, Errors.t) then it's fine. But if it's non-obvious (e.g. is_manually_invoked:bool) then it needs a name to explain what it means. There's only one single case which needed a name:
```
type completion_request = { is_manually_invoked: bool }
```
