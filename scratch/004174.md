A few months ago I wrote D43598963 to gather telemetry about an irritating code pattern. I wrote:

> There's some irritating code in HackIDE to deal with these possibilities:
1. what if VSCode sends didChange but clientIdeDaemon doesn't think it previously had didOpen
2. what if VSCode sends didClose but clientIdeDaemon doesn't think it previously had didOpen
3. what if VSCode sends a request (e.g. hover) but clientLsp doesn't think the file is open and nor does clientIdeDaemon
4. what if VSCode sends a request and clientLsp thinks its open but clientIdeDaemon doesn't
5. what if VSCode sends a request and clientLsp doesn't think it's open but clientIdeDaemon does

> This irritating code was introduced in D20954401 (April 2020) from the telemetry observation that people were receiving LSP requests for files that apparently weren't open (i.e. hadn't yet received didOpen from VSCode, or had already received didClose).

The question in this diff is a bit narrower: *under what circumstances will clientLsp send a `document_location` with `file_contents=None` to clientIdeDaemon, and what will be the effect?*

**Background**. `ClientLsp` has the model that it maintains current editor content of all open files. Indeed it has to since when it receives "didChange" they only carry the delta, so it has to update its existing model. `ClientIdeDaemon` on the other hand has a kind of stateless model where, on every single request, the entire editor content for that file gets sent over, in one of two ways depending on whether line+column are also needed.
```
type document_and_path = {
  file_path: Path.t;
  file_contents: string;
}

type document_location = {
  file_path: Path.t;
  file_contents: string option;
  (* if absent, should read from file on disk *)
  line: int;
  column: int;
}
```
The comment "if absent, should read from disk" is a lie...

So, when ClientLsp sends a `document_location` over to ClientIdeDaemon, what happens to it? ClientIdeDaemon always calls `update_file_ctx istate document_location`, which calls `update_file istate.ifiles document_location`, which goes through these possibilities:
1. If `file_contents=None` and clientIdeDaemon doesn't already have an entry for this file, then "failwith". Telemetry shows this happens to only 6 users over the past month. It's hard to speculate what lead to it nor why it is so rare. Nevertheless, if it's going to failwith anyway, then it matters not whether it fails in clientLsp or clientIdeDaemon.
2. If `file_contents=None` and clientIdeDaemon does have an entry for the file, then it used that existing entry. Telemetry shows this happens to only 1 user over the past month. Again I don't understand what lead to it. Nevertheless, with only 1 user affected, I feel very happy to fail fast in clientLsp if that makes the code easier.
3. If `file_contents=Some` then ... (not pertinent)

The analysis gives a clear answer: there's no value in supporting `file_contents=None`. This diff therefore turns `file_contents` from a `string option` to just a `string`.

That indeed makes sense because why would VSCode ever be sending hover requests, say, for a non-open file?

It's also a nice change to make because it now unifies `document_and_path` with `document_location`.
