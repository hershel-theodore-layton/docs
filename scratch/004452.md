Commit body:
Summary:
The previous diff had made it so that updated errors go from `clientLsp->VSCode` for didClose+codeAction. This diff puts in the `clientIdeDaemon->clientLsp` bit for didClose.

Reminder: this docblock in clientIdeMessage explains why errors are being sent in didClose:
```
  | Ide_file_closed : Path.t -> Errors.t t
      (** This returns diagnostics for the file as it is on disk.
      This is to serve the following scenario: (1) file was open with
      modified contents and squiggles appropriate to the modified contents,
      (2) user closes file without saving. In this scenario we must
      restore squiggles to what would be appropriate for the file on disk.

      It'd be possible to return an [Errors.t option], and only return [Some]
      if the file had been closed while modified, if perf here is ever a concern. *)
```

I went down a rabbit-hole of wondering about premature optimizations...
1. clientIdeDaemon could recompute the TAST off disk whenever we get didClose
2. clientIdeDamon could use the previously-computed TAST, since one was computer upon didOpen **<-- that's what I did with the diff**
3. clientLsp could decline to publish diagnostics if they're unchanged
4. clientIdeDaemon could decline to return anything from didClose if they're unchanged.

Computing TAST+errors is supposed to be fairly cheap. We do it every didOpen, every didChange, every autocomplete. But also, cached TASTs were one of the biggest drivers for LSP responsiveness once we adopted them. That's why I've continued to use cached TASTs in this diff.

Should there be more optimizations down the line? Maybe decline sending publishDiagnostics if the errors-list is empty? I don't know. Will defer that for future consideration.
