Summary:
ide_standalone comes with the idea that "live squiggles" should be computed by clientIdeDaemon for the file you have open, updated every didOpen, didChange, didClose, codeAction. These squiggles get computed by `Tast_provider.compute_tast_and_errors_quarantined`, powered by the naming-table and decls of the Local_files backend.

But are they correct? Are these squiggles true? Or do various shortcomings in Tast_provider or Local_files backend mean that they're inadequate? Are there too many false positives or false negatives? That's what this diff sets out to answer.
* False negative example: we know that Tast_provider is currently is unable to provide "duplicate name" errors, and "typedef/module has reserved name".
* False positive example: we worry that because clientIdeDaemon sometimes plays fast-and-loose with decl invalidation and naming-table updates, that it might produce incorrect squiggles.
* False positive example: current behavior of Tast_provider is to report parse+typing errors, while hh stops as soon as it encounters parse errors. [I'll have to fix this otherwise we won't get useful signal]
* False negative example: while clientIdeDaemon is initializing, there will be open files with no diagnostics yet, even though errors-file reports them. [This diff skips validation during initializing, to avoid signalling on these false negatives].

The validation strategy in this diff:
1. If a file is open, the clientIdeDaemon must have sent live squiggles for it
2. If the file is unmodified and those live squiggles were sent before current typecheck started, then the last modification to the file-on-disk must have happened prior to the start of the typecheck, and the file open in the IDE must be the same as what's on disk.
3. Therefore, when we read an error from errors.bin, and if the above conditions are met, then live squiggles for clientIdeDaemon should be present for this file and should agree with what hh_server reported in errors.bin; we'll validate this.
4. Also, if the typecheck finishes and errors.bin is marked as completed, then there should be no false positives, i.e. no squiggles reported by clientIdeDaemon which weren't reported by hh_server.
5. The limitation with this scheme is it doesn't track false negatives. For instance, if a file has no errors other than "duplicate name error", then clientIdeDaemon won't have reported anything for it, and we don't keep record of the timestamp at which nothing was reported. To get some roughly approximate (but not perfect) signal for sake of telemetry, we'll pretend that the timestamp at which nothing was reported (for open unmodified files) was prior to the start of the typecheck: if hh_server reported errors for a file, but the file was open and unmodified and clientIdeDaemon has reported no errors for it, then we'll report a false negative.

The implementation of this validation is pretty much routine. For logging, I used subsampling: we'll top out at about one event per user per two minutes, an entirely acceptable log burden.
```
  |> EL.log_subsampling
       ~max_tolerable_long_term_interval:120.0
       ~max_tolerable_short_term_spike:5
```
