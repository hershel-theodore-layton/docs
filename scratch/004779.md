Commit title: batch process changes post-init
Commit body:
Summary:
With `ide_batch_process_changes=true`, the daemon will now process file changes beyond initialization using the Rust batch indexer.

I've kept the scheduling of when we process file changes the same to remain consistent with the current availability characteristics; processing only occurs when `should_process_file_change` is true -- there's no pending message in stdin/internal message queue. In other words, if the client is trying to hover or go-to definition, we serve that request before attempting to batch process files. Given how quickly batch processing completes, I wonder if it would be better to prioritize fresh results over availability, instead of users having to wait for their current requests to complete before seeing fresh results.
