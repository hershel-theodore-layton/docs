Commit title: telemetry about stuck spinner
Commit body:
Summary:
I have been analyzing telemetry about how long "hh check" takes. This is complicated by the fact that there are a number of Ctrl+C. In statistics we call these events "censored events" because they censor information about how long the check was going to take. There's a technique called Kaplan-Meier Survival Curve to take these into account. Observations:
1. there are a lot of Ctrl+C at very longest times. Of the complete/Ctrl+C events that happen 10mins or more after the check started, about half of them are Ctrl+C.
2. Most of these long-duration Ctrl+C look suspicious -- almost all of them still trying to connect to the monitor, or while it says "hh_client:active". I think these all indicate that it's simply stuck.
3. Taking these into account, Kaplan-Meier says that our P99.9 duration of hh check is simply undefined! The P99.9 is dominated by checks that were cancelled via Ctrl+C, so we can't say how long it is.

It's therefore crucial to understand when, why, how often "hh check" is getting stuck. This diff provides telemetry that will be able to answer that. It keeps track of how long the current spinner message has been unchanged...
* When the user hits Ctrl+C, CLIENT_CHECK_BAD_EXIT (or CLIENT_CHECK_PARTIAL if we've seen at least one streaming error) will now have column `spinner` for the current spinner message, and `spinner_ms` for how many ms it has been unchanged for.
* When a check completes, CLIENT_CHECk will have the same columns.
* Every second we already write to hh_client_spinner a SPINNER_HEARTBEAT message. This now also includes the same columns.
* When the spinner changes message, this diff adds SPINNER_CHANGE with the same columns, plus a column `next_spinner` to say what the next spinner will be.

What kinds of analysis do I have in mind?
1. From SPINNER_CHANGE, I will learn whether spinners stuck for 60s+ ever progress
2. In case of CLIENT_CHECK_BAD_EXIT, if the spinner has been stuck for 60s+ on one of the known problem ones that  should always complete quicker (e.g. connecting to monitor), I might be able to assume that it's an infinite duration. This could be a cheap (scuba-computable) approximation to Kaplan-Meier.
3. I will learn whether any states appear stuck -- these are either actually stuck, or just need more progress updates.
