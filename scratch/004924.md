Summary:
This is part of a suite of three diffs which move "reserved-name" checks into the parser. The diffs are all similar in implementation, but each one comes with different behavioral changes in hackc (hence why each has its own separate diff and separate justification).

1. D45638744 (prev diff) -- bring uniformity to classish (interface, class, trait)
2. D45658285 (prev diff) -- bring uniformity to enum and enum-class
3. **D45658761 (this diff) -- bring uniformity to alias (type, newtype, module newtype, case type, newctx)**

This diff changes hackc behavior around aliases. It's similar to the previous two diffs in the stack. The question is which reserved type names may be used, and which ones can't?
```
type <name> = int;
newtype <name> = int;
module newtype <name> as int = int;
case type <name> = int;
newctx <name> as [defaults];
```

Why am I looking at these constructs? Because I systematically looked at every  construct that can get "reserved name" reported on it in either hh and hackc. The previous diffs did all other cases, so these are the only ones remaining. In the rust parser, they all start from `fn alias_errors()` but their codepaths diverge a little after that. (which is why I included test cases for all of them separately).

BEFORE: the following were all errors in hh, but not all in hackc
* names **bool, false, int, null, parent, self, string, true** -- these don't even parse as type aliases, for instance `type bool = int` isn't recognized as valid syntax and complains of missing semicolon
* names **arraykey, callable, dynamic, float, mixed, nonnull, noreturn, nothing, num, resource, this, _** -- these were allowed as type aliases, even though disallowed in hackc as classish or enum.

AFTER: all of them are errors in hackc as well as hh.

## Why?

Why am I doing this? why am I making things errors in hackc that needn't be? I'm driven primarily by the wish to clean up hh, to make all its "reserved name" errors be generated in the parser rather than in hh.

Between the choice of changing hh to now allow them, or changing hackc to now disallow them like hh does, I figured it better to disallow them: (1) it will make hackc consistent between type aliases and classish+enums, with the very simple user-understandable rule "here is a list of reserved type names and they may not be used to name your own types", (2) I don't think we're doing users any favors to allow them... they won't say "oh great this language lets me name my type 'mixed' thank you so much language designers"!

## The different "hh" behaviors

In the summary of this diff and the rest of the stack, I talked about "hh" as a single entity. But actually there are several hh-related tools. The newer ones we're developing work on a map-reduce basis, where the errors reported for a file are solely those errors encountered while checking the file. But the older tools (hh, hh_single_type_check) do an additional global analysis phase which detects some reserved names.
```
flib/ljw.php:
<?hh
type callable = int

BEFORE:
$ hh
Naming[2068] callable cannot be used as it is reserved
$ hh_single_type_check
Naming[2068] callable cannot be used as it is reserved
$ hh --re
No errors!
$ hh --single flib/ljw.php
No errors!

AFTER:
$ hh
Parsing[1002]+Naming[2068] callable cannot be used as it is reserved
$ hh_single_type_check
Parsing[1002]+Naming[2068] callable cannot be used as it is reserved
$ hh --re
Parsing[1002] callable cannot be used as it is reserved
$ hh --single flib/ljw.php
Parsing[1002] callable cannot be used as it is reserved
```
We've indeed had a user report lamenting that `hh --single` doesn't produce the expected behavior: https://fb.workplace.com/groups/hackforhiphop/posts/24584371301184820

This diff stack will allow all the tools to have the same behavior.

-------------

## How this diff works

In rust_parser_error.rs `fn alias_errors()` is used for checking all the different kinds of alias. Previously, the parser didn't report any errors for type alias reserved names. Hackc didn't check type aliases either, but hh did (still does) and reports `(Naming[2068])` for them.

This diff adds reserver-name checking for aliases into the parser, similar to how it's done for classish and enums.

The list of reserved names for classes is almost identical to the list of reserved names for aliases, except that classes also disallow three additional names **classname, darray, varray**. I'd like to solicit opinions on whether we could actually start allowing these three as classnames D45675494. I think that'd make the language design as simple as possible.
