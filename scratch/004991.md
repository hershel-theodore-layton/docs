Summary:
The hack/test/reserved tests were checking the exact output of hackc, which isn't great.

This diff switches to using FileCheck to only look for the key information. I'm being a bit sneaky in using the same CHECK: directives for the output of both hh_single_type_check and hackc. Let's see how that works... My goals in the test are
* To ensure that we report an error on a file if it uses a reserved word, and that the error text is correct
* To ensure that successful files don't have errors
* For hh, to ensure that we won't have duplicate errors
* I couldn't bear having hundreds of files. I really did want to combine all reserved names into a single file.

## Reserved name errors
```
//// Arraykey.php
<?hh
type Arraykey = int;
// CHECK: Arraykey.php
// CHECK: Cannot use `Arraykey` as a type name as it is reserved

HH OUTPUT:
File "type.php--Arraykey.php", line 2, characters 6-13:
Cannot use `Arraykey` as a type name as it is reserved (Parsing[1002])

HACKC OUTPUT:
# type.php--Arraykey.php starts here
.filepath "type.php--Arraykey.php";
.fatal 2:6,2:13 Parse "Cannot use `Arraykey` as a type name as it is reserved";
# type.php--Arraykey.php ends here
```
This one's easy. It doesn't test that hh fails to give additional errors (specifically, Naming[2068]); that's done through the hh "verify.py" test.

## Parsing errors
```
//// Bool.php
<?hh
type Bool = int;
// CHECK: Bool.php
// CHECK: A semicolon `;` is expected here

HH OUTPUT:
File "type.php--Bool.php", line 2, characters 1-4:
Hack does not support top level statements. Use the `__EntryPoint` attribute on a function instead (Parsing[1002])
File "type.php--Bool.php", line 2, characters 6-6:
A semicolon `;` is expected here. (Parsing[1002])
File "type.php--Bool.php", line 2, characters 6-16:
Hack does not support top level statements. Use the `__EntryPoint` attribute on a function instead (Parsing[1002])

HACKC OUTPUT:
# type.php--Bool.php starts here
.filepath "type.php--Bool.php";
.fatal 2:6,2:6 Parse "A semicolon `;` is expected here.";
# type.php--Bool.php ends here
```
The code "type Bool = int;" isn't actually parsed as a declaration. I could have tested that hackc produced ".fatal" here (without caring about its content), but the check for "A semicolon is expected here" works nicely for both hh and hackc.

I added "CHECK: Bool.php" to ensure we don't get out of sync, so that FileCheck doesn't match "A semicolon is expected here" in the wrong test case.

## No errors
```
//// Classname.php
<?hh
type Classname = int;
// CHECK-NOT: .fatal
// CHECK-NOT: File "type.php--Classname.php"

HH OUTPUT:
<blank>

HACKC OUTPUT:
# type.php--Classname.php starts here
.filepath "type.php--Classname.php";
.alias Classname = <"HH\\int"> (2,2) """D:2:{s:4:\"kind\";i:1;s:5:\"alias\";s:9:\"Classname\";}""";
# type.php--Classname.php ends here
```
This one's a bit odd. Hackc reports the filename even if there were no errors, while hh only reports the filename if there were errors. I used `CHECK-NOT: File: "<filename>"` to look for the hh-specific way that the filename is reported.

As for hackc, I only care that there aren't any errors (.fatal); I don't care what the content of the success case is. But I wouldn't it to get out of sync and detect the .fatal in some other file. This is mitigated by having all the error cases detect their filename "CHECK: <filename>".
