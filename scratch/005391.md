Summary:
It's confusing that `Decl_provider.get_fun` (say) will happily provide decls even for functions that don't properly exist!
```
//// a.php
function f(): int {return 1;}

//// b.php
function F(): void {}

Naming_provider.fun_exists "F" --> false
Decl_provider.get_fun "F" --> returns "function F():void"
```
Here's an example that doesn't even use case insensitivity:
```
//// a.php
typedef c = int;

//// b.php
class c {}

Naming_provider.get_typedef_path "c" --> None
Decl_provider.get_typedef "c" --> returns "typedef c = int"
```
The significance is that you can't trust the result of Decl_provider.get* unless you have some prior reason for knowing that the entity (with that capitalization) is the "winner" i.e. the one returned by the reverse naming table for that name.

This diff doesn't change behavior. It's solely a baseline to document precisely what's currently returned by Naming_provider.*_exists and Decl_provider.get_*.

Things I noticed:
1. `Decl_provider.make_env` appears to be wrong. It is called in a wide variety of places. It will overwrite whatever's in the decl store with something new, *without regard to winners or losers*. Thus, if someone calls `Decl_provider.make_env` on a file that contains looser definitions of a type, then henceforth Decl_provider.get_* will end up retrieving that looser definition.
2. Rust provider backend has some differences about what Decl_provider.get* will return, compared to ocaml. They're all cases where Naming_provider says the thing doesn't exist.  Some of them Rust provides a decl where ocaml doesn't; some of them Rust doesn't provide a decl where ocaml does.
