Summary:
Overview of this stack of five [type-ast] diffs:
* Currently the typechecker takes a list of top-level names to typecheck, then iterates over that list of names, fetches the winning definition of that name in the file, and typechecks it.
* Thanks to this stack, the typechecker will instead iterate over the list of definitions in the file and typecheck them.

## Motivation

Here's an example why the current behavior is odd, from test/quickfix_lint/sound_dynamic/redundant_cast3.php:
```
<<__SupportDynamicType>>
function main2(Wrap<float> $wf): void {
  (float)$wf;
}

<<__SupportDynamicType>>
function main2(vec<int> $_): void {
  (float)42.0;
}
```
Note that both functions have the same name. The top-level names are ["main2"; "main2"]. We iterate over that list. For each name, we search the AST for the "ast-winner definition" of each one, and typecheck that winner. In this case the second one is the ast-winner, so it ends up getting typechecked twice. We end up reporting "(float) is unnecessary" twice on the second definition, and not at all on the first.

(Actually, the concept of "ast-winner" is ill-defined and used almost nowhere. It's merely the notion of "which AST definition happens to be lexically last in the file" from a List.fold_left in [Ast_provider.get_def](https://www.internalfb.com/code/fbsource/[047abb2fec53]/fbcode/hphp/hack/src/providers/ast_provider.ml?lines=273). This is a different codebase and a different answer from the more important concept of "naming-table winner" in [Naming_global.ndecl_file_error_if_already_bound](https://www.internalfb.com/code/fbsource/[047abb2fec53]/fbcode/hphp/hack/src/server/serverTypeCheck.ml?lines=584).)

I have a second motivation. Currently duplicate-names are reported by hh_server during the "update naming-table" phase ServerTypeCheck.do_naming, which happens centrally before we calculate fanout and before we typecheck each individual file. This central phase is absent from clientIdeDaemon and distc -- therefore, clientIdeDaemon and distc currently don't report duplicate name errors. My plan is (1) the per-file typecheck iterates over all toplevel defs in a file, (2) for each one it can ask "is the naming-table winner for this name the same as the def I have in hand right now?" and if not then report a duplicate-name error. In this way, clientIdeDaemon and distc will reach parity with hh_server.

## What this diff does

There are several different typechecking functions. The diffs in this stack go step by step to bring them closer together. This diff focuses on `Typing_check_utils.type_file`. Currently it takes a FileInfo.t (the list of names of toplevel symbols) and iterates over it. This diff makes it take `(ast: Nast.program)`. For now solely uses that ast to fetch names, same as before, and same as Typing_check_service does, but in future diffs it will actually walk the ast.

## Explanation of test failures

There are two tests that fail due to this change! Let me explain why it's reasonable, and why this diff updates their .exp files. Consider a file
```
<?hh
enum Bool : {}

FILEINFO:
<empty; the direct-decl-parser claims there are no enum decls>

AST:
[(Stmt ([1:1-5], (Markup ([1:1-5], ""))));
  (Class
     { c_kind = Cenum; c_name = ([2:6-7], "\\");
       c_enum =
       (Some { e_base = ([2:13-16], (Happly (([2:13-16], "int"), [])));
               e_constraint = None; e_includes = [] });
       c_module = None })
  ]

HHST BEFORE, and HH:
a.php:2:6,6: A name is expected here. (Parsing[1002])

HHST AFTER:
a.php:2:6,6: A name is expected here. (Parsing[1002])
a.php:2:6,6: Unbound name: `` (an object type) (Naming[2049])
```
This file has a parse-error `Bool is a reserved name`.
* hh_server, distc -- these tools don't bother typechecking if there were any parse errors
* HackIDE, ide_standalone -- if there are parse errors then it still typechecks since it needs the TAST, but (for consistency with hh_server) it silently drops the check errors; it solely shows the parse errors
* hh_single_type_check -- this will report typecheck errors even in the presence of parse errors. The typecheck error is `Unbound name: '\'`.

The question is, do we iterate over the top-level entities in the AST or those produced by the direct-decl-parser?
* hh_server, distc -- these tools iterate over the entities in the AST, via Nast.get_defs
* hh_single_type_check -- previously this iterated over entities in FILEINFO, but now with this diff it iterates over entities in the AST.

All this explains why hh_server reports only the parse error, and hh_single_type_check used to report only the parse_error, but now it also reports the useless typecheck error. I think everything is working as designed, and the current hh_single_type_check is arguably more correct than it was before this diff.
