Commit title: Refactor refactorings: Wrapped modules, consistent spelling, reduced risk of one-many file-to-lib relationship
Commit body:
Summary:
Some noop changes for consistency and maintainability:

- Use wrapped libraries: this enables us to control the API surface area of a library and have a more navigable and refactorable dependency structure. Wrapped modules also make it easier to avoid errors from name conflicts (not always caught by dune). One advantage is enabling private non-lsp-protocol types for refactors (introduced later in the stack).

- Make the library entrypoint module's name match the library name, for consistency and discoverability.

- Use a directory and glob to group files rather than sticking all targets and libraries in the same directory. This makes it easier to guard against the same file belonging to multiple libraries, which is a strange kind of dependency. This change also makes it easier to break out code into separate modules and removes the need to manually maintain module lists in `TARGETS` and `dune`.

- use snake case for module names
    - Advantages:
        - Our style guide says to fall back to Jane Street Core style.
        - Also more consistent with the OCaml standard library and afaict most of the Hack codebase
        - Snake case for module names is the only convention that works with our other conventions: directory names snake case, library names snake case. If using wrapped modules (which imo we should), afaict the name of the main module matches the name of the directory so both should be snake case, which makes at least one module snake case, which pushes for making all module names snake case for consistency
    - Disadvantages:
        - Most other modules in the `server` directory use camel case, so this introduces consistency at the cost of some inconsistency. I propose gradually evolving to be more consistent and snakey
        - It's arguably nice that Lsp.ml modules, types, constructors, etc. match the ones in the LSP spec, which are camel-cased. For now, I won't touch lsp.ml, but fwiw think ideally those will be snakey, too. In most codebases I've worked on, language-native spelling trumps protocol spelling.
