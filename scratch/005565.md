This diff ports `test_rename` to ide_standalone

This was a difficult test to port which took me the entire day, because of two regressions in ide_standalone that it uncovered. I fixed them up first in two separate earlier diffs, which is why this diff now can get by smoothly.
* D46239349 - serverRename took a Relative_path.t, extracted suffix, then constructed a new Relative_path.create_detect_prefix on that suffix. Naturally its answer was a dummy path which worked only if the CWD was equal to project root. In tests, CWD isn't, and therefore it couldn't load the file, and hence couldn't construct a "deprecated" stub. My fix was to use Relative_path.t instead of string inside the codebase.
* D46241670 - when clientIdeDaemon did the first local rename in the case of a local variable, it failed to insert `$`. I fixed it.

The changes in baseline reflect the remaining behavioral differences with ide_standalone:
1. With hh_server, we used to perform rename by synchronous RPC to hh_server which couldn't be interrupted while underway. But with ide_standalone we instead to an asynchronous shell-out to `hh_client --ide-rename`, and if a subsequent rename or find-all-references comes along, then we cancel any outstanding one before proceeding. (that's because we don't want to inadvertently spawn lots of concurrent calls to `hh_client` most of which won't be needed). To accommodate this, I changed the test to wait for each rename response before issuing the next one.
   1. Still to do T92870399 - if a new shell-out comes along and we cancel the previous one, we should give an Error.RequestCancelled LSP response for it
2. ide_standalone gives the renames in a different order. This is immaterial since (per the LSP spec) all renames are non-overlapping and are taken to refer to locations in the original document before any have been applied. (The LSP spec used to explain that they were applied bottom-to-top regardless of which order they were listed in). I could have changed the code to always produce a deterministic order of renames, but that's beyond the scope of this diff.
