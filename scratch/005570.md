[Diffstack overview: my plan is (1) one by one, port all the tests over to ide_standalone, doing them gradually because different ones require different levels of detail. (2) once that is done, hard-code test_lsp.py to always use ide_standalone, and clean it up. This diff is part of phase 2.]

Most tests start with something like this:
```
self.initialize_spec(
    LspTestSpec("optional_param_completion"),
    use_serverless_ide=True,
    supports_status=True,
    supports_init=True
```
They're constructing a declarative structure which declares which messages it will send to the LSP server, and which messages it expects to get back.

I found the names confusing, because they refer to how the declarative structure is intended to be used rather than what it does, so this diff renames them...
```
self.initialize_spec(
    LspTestSpec("optional_param_completion"),
    has_status_capability=True,
    wait_for_init=False
```
* `use_serverless_ide` used to control (1) do we pass a naming-table, (2) do we expect the LSP server to send us a client/registerCapability message. I've changed it to always do these things.
* `supports_status` (now `has_status_capability`) sets a flag in the initialize message to say that this test (i.e. the LSP client) supports the "status" capability. If set, then LSP servers will know they're able to send window/showStatus messages. With this precise name, there's no confusion as to whether the flag stops LSP servers from sending status message, or allows them to be sent but simply ignores them. (the former).
* `supports_init` (now `inverted as wait_for_init_done`) controls (1) whether the LSP server introduces a small artificial delay after loading saved-state off disk, to better represent the kind of asynchrony that it will experience when downloading, (2) whether the wait for the LSP server to send "Finished init" before doing any other test work. This determines whether the test wants to test what happens when we send a request before clientIdeDaemon has finished initializing.
