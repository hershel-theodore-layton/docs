Commit title: ProviderContext.entry shouldn't always override naming table
Commit body:
Summary:
With this diff, code that uses Provider_context.entry (e.g. `hh --single`, clientIdeDaemon.ml) will now be able to get the same errors as that which doesn't (e.g. typing_check_service).

## Context

The design of hh_server is that it has a single central naming-table and decl-cache reflecting the truth of the repo on disk.
* But we also use `Provider_context.t` and `Provider_context.add_or_overwrite_entry_contents` as a way to entertain temporary questions "how would this file typecheck if it were different from what's on disk"? We use this for HackIDE while working on unsaved files, and also stdin-supplied input `echo CONTENT | hh --type-at-pos line:col`.
   * We use `Provider_utils.respect_but_quarantine_unsaved_changes` in cases where the content is different, so that anything we derive from it (decls, folded-decls) can be undone at the end. There's no need for quarantine if the contents are the same as what's on disk.
* `Provider_context.entry` has a second function of maintaining a per-file cache of TAST. This is necessary to get HackIDE perf under 50ms by caching TAST between user interactions. It's also used in hh_server, for instance --type-at-pos-batch uses `entry` to cache the TAST for each file, so when it iterates over the argument list then it doesn't need to recompute TAST for each one.
   * Even if we want `entry` solely for cache, we still end up using the whole machinery, typically populating `entry` from what's on disk anyway.

## Problem statement prior to this diff

The `entry` mechanism introduces behavioral differences in Naming_provider. I landed D46051122 to document these differences. They stem from the fact that (1)  we overlay names defined in `entry` over the top of those in the central naming-table, (2) we power that overlay with AST, while the central naming-table is powered by direct-decl-parser.
* Naming_provider.get_const_pos returns different spans, because AST and direct-decl-parser disagree on whether to give span of identifier or entire constant
* **[SUBJECT OF THI DIFF]**. In case of duplicate definitions, Naming_provider will always treat one defined in `entry` as the winner, even when the central naming-table considers it the loser. This changes the results of most functions, e.g. Naming_provider.{fun_exists,get_fun_pos,get_fun_canon_name}. Also, for duplicates in the same file, `entry` sometimes picks a different winner.

## Solution implemented in this diff

I changed the behavior of `Naming_provider.find_symbol_in_context_with_suppression`.
* Before: it used to overlay the names defined in `entry` over the top of those in the central naming-table. Implementation was that if a symbol was defined in `entry` then take it as the winner.
* After: it now does a "winner-sensitive overlay". The implementation in serverTypeCheck.ml ends up making the winner in the global naming table be the one with the alphabetically first filename. To maintain the same notion of winner when doing an overlay, we look up the position according to `entry` and also according to the global naming table, and pick the alphabetically first one as the winner.
