Commit title: fix deadlock: avoid retiring under shared-lock in HazptrObserver
Commit body:
Summary:
In general, it is good to minimize lock scopes (1) to reduce lock contention possibility and (2) to avoid triggering any possible unanticipated side-effects.

The concrete deadlock scenario that this addresses:
* Hazard pointer reclamation is inline (using some inline executor, such as the default hazptr executor).
* Hazard pointer reclamation is currently deferred (the number of retired objects is below the reclamation threshold).
* A `HazptrOberver` instance, or the object owning the instance, is retired.
* Time passes....
* Hazard pointer reclamation becomes immediate (the number of retired objects is at but not past the reclamation threshold).
* The `HazptrObserver` instance refreshes, obtaining a shared lock on its `alive` shared variable (the instance is currently retired but not yet destroyed).
* Refresh causes a new `State` to be exchanged into the instance and the old state to be made available for retirement.
* The old state is retired while the shared lock remains held. The bug lies here.
* Retirement of the old state triggers immediate hazard pointer reclamation of all retired objects, including the old state and the `HazptrObserver` instance.
* Reclamation of the `HazptrObserver` instance attempts to acquire an exclusive lock on its `alive` shared variable while the shared lock remains held.
* Deadlock.

Includes a unit-test that constructs this deadlock scenario.
