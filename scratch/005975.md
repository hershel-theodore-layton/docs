Commit body:
Summary:
Notionally, "hh_client lsp" doesn't know ROOT until after it's received the initialize message,
```
{
    "jsonrpc": "2.0",
    "id": 1,
    "method": " initialize",
    "params": {
        "processId": null,
        "rootUri": "file:///Users/stefano/Testing/PHPSources",
        ...
```
We therefore delay a lot of initialization (for several HackEventLogger fields including Root and Hhconfig_version, for Hh_logger, for RelativePath) until after we've received the initialize message.

On the other hand, find_hh.sh requires to know the ROOT before "hh_client lsp" has even been launched. It needs this to read .hhconfig, find the version= line, and learn each version of the hh_client binary to launch.

(1) Do we ever get it wrong in practice? Do we give a ROOT in the initialize request which differs from what find_hh.sh got? That would lead to us running the wrong binary.

(2) Can we simplify startup code, by requiring "hh_client lsp" to be started in a place where it can find root (either through CWD or through an explicit final argument).

This diff gathers telemetry to solve both problems.

It was prompted by https://fb.workplace.com/groups/hacklang.oncall/posts/673602944606260?comment_id=673618511271370&reply_comment_id=673632781269943, where the lack of Hhconfig_version in a scuba row was needlessly confusing.
