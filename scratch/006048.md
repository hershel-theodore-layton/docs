Summary:
[I wrote this diff to factor out common code needed to land the improvement in the next diff.]

When we receive didOpen/didChange, then we send the current file contents to clientIdeDaemon and ask it to recompute errors.
* A few days ago in D46585435 (June 8th) I had done a "leaky bucket" for didChange. Users had observed that when they had a big file and typed more than one keystroke a second, then it took a long time to catch up. The fix was that if we have a didChange, and there are further didChange for the same file further on in the LSP queue, then we don't bother recomputing TAST/errors for the first one.
* didOpen doesn't have that affordance, but is otherwise identical.

With this diff,
1. I factored out the behavior from the didChange handler into a separate function, `send_file_to_ide_and_get_errors_if_needed`.
2. I figured that didOpen would benefit from the exact same affordance, so I made didOpen call the same routine
3. With this done, the behavior for didOpen and didChange are now identical on both the clientLsp and clientIdeDaemon side. I therefore combined the two functions into a single one, called `Did_open_or_change`
4. I also did some renames of events defined in clientIdeMessage.ml and consumed in clientIdeDaemon.ml, in the hope that the new names are closer to those in LSP and clientLsp.ml and hence easier to remember.
```
ClientIdeMessage.Ide_file_{opened,changed} -> Did_open_or_change
ClientIdeMessage.Ide_file_closed -> Did_close
```
