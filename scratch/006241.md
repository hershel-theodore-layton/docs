Commit body:
Summary:
This diff addresses two related issues. Background: when users invoke "hh" it actually goes through "find_hh.sh" which sometimes invokes hh_client once, gets an error message "should retry", then invokes it a second time or more. We want to know the end user experienced duration, so find_hh.sh actually sets an environment variable FIND_HH_START_TIME and FIND_HH_RETRIED. That way, when we log CLIENT_CHECK, we can record the true user experience.

**Problem 1:** when clientLsp in ide_standalone mode shelled out to "hh_client --from clientLsp:ide-find-refs --ide-find-refs ..." then it bypasses find_hh.sh, hence never overrides those variables, and instead inherits the ones pertaining to the original invocation of "hh_client lsp". The end result, I observed in telemetry, is that the "retry_time_taken_ms" column in scuba wasn't meaningful for "--from clientLsp:" events.

This diff fixes it by having clientLsp overwrite those two environment when shelling out. This all feels a bit unsatisfactory, a bit messy. I can't see any better way to do it right now though.

**Problem 2:** sometimes find_hh.sh has to do fbpkg fetch to get new hack binaries, and we have data its impact for CLIENT_CHECK events, but we don't have data for its impact on LSP. This diff adds two measures: (1) the CLIENT_LSP_METHOD for "initialize" will now record retry_time_taken_ms, same as CLIENT_CHECK does. (2) In case the LSP client had sent off a volley of requests before initialize had even returned, then the ones that were slow due to fbpkg fetch will now indicate that in the lsp_error_message column. (I believe though that VSCode doesn't do anything until after initialize has returned.)
