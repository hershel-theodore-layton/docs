# Motivation
This diff introduces a new AsyncProcessor interface called NestedAsyncProcessor.

It is a very popular pattern that takes in the code generated AsyncProcessor which does the main request processing.

```
class MyAsyncProcessor : public AsyncProcessor {
 public:
  MyAsyncProcessor(std::unique_ptr<AsyncProcessor> delegatedProcessor);
  void executeRequest(...) {
    // does some pre processing
   delegatedProcessor->executeRequest(...);
   // does some post processing
  }
};
```

# Internal

Such custom AsyncProcessor will break service framework event handler installer because installer will not install TProcessorEventHandler in the **inner** AsyncProcessor which invoke the ContextStack that runs event handlers. Instead **outer** AsyncProcessor will be installed with event handlers and does nothing.

Existing AsyncProcessor that follow this pattern can be roughly [identified here](https://www.internalfb.com/code/search?q=repo%3Afbcode%20%3A%20public%20apache%3A%3Athrift%3A%3AAsyncProcessor) where user create a wrapping AsyncProcessor to add additional functionality (like tracing, profiling etc)
