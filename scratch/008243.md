Summary:
(This diff continues my project to delete SqliteIndex, started+described at the base of this diffstack D47867455)

If hh.conf doesn't specify an index provider, then it falls back to SqliteIndex. I think this is used in two places:
1. OSS users
2. there may be some tests which provide their custom hh.conf but don't specify an index.

The behavior of SqliteIndex is, upon startup, it does a Facts index-build of the repository to create a sqlite file, and then powers symbol search questions (like top-level autocomplete) from that sqlite file plus a local delta arising from subsequent disk changes:
* for OSS hh_server, this index would only ever be used if someone writes "hh --search". I don't think it's worth providing that functionality.
* for OSS clientLsp, this index would be used when someone does a Cmd+Y symbol-search in VSCode.

The OSS clientLsp end-to-end initialization is kind of crummy. That's because, in addition to building the symbol index, OSS clientLsp also needs to build a naming table. Guess how it builds a naming table? -- answer, by doing a SECOND whole-repo parse, and writing that into a naming-table sqlite file. Oh, in addition, that second whole-repo-parse also sticks every single top-level symbol into the SqliteIndex "in-memory delta". https://www.internalfb.com/code/fbsource/[799709fcd870]/fbcode/hphp/hack/src/client/ide_service/clientIdeInit.ml?lines=120-133

This diff switches over to LocalIndex.
* for OSS hh_server, it means that "hh --search" will now be broken. Indeed I remove this flag entirely in a few diffs up the stack. I don't think we need care to support it.
* for OSS clientLsp, we didn't even need the SqliteIndex. This diff therefore removes the first whole-repo parse. It retains the second whole-repo parse, the one which builds the naming-table and also updates the in-memory LocalIndex.
