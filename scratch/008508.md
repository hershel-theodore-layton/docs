Commit title: PathId -> RelativePath
Commit body:
Summary:
Most of the hack codebase uses RelativePath to juggle paths, with the suffix
represented either as an interned string (pos::RelativePath) or an owned PathBuf
(relative_path::RelativePath).

For historical reasons, hh_distc used PathId, a component-wise interned representation
that was more space efficient (parent directory components are shared); each interned
component contained a filename and id of the parent dir (bottom-up linkage).

PathId had some disadvantages:
* more expensive to intern: O(components) instead of O(1)
* more expensive to sort/compare, because path components must be traversed
top-down instead of bottom up, requiring two passes over the component list
* more cpu intensive to serialize/deserialize, even though it saved some space
* integrating with other code that already uses PathBuf or RelativePath was awkward
and sometimes required ad-hoc ways to keep track of the Prefix.

Since neither hhvm nor the rest of hack use component-wise interning and get along "fine",
lets use pos::RelativePath throughout hh_distc.
