Commit title: hhstc --custom-hhi-path requires --no-builtins
Commit body:
Summary:
Consider the following scenario:
1. TestA runs `hh_single_type_check --custom-hhi-path $(location XYZ)`
2. TestB also runs with the same `--custom-hhi-path $(location XYZ)`
3. TestA starts writing its builtins like `hh_single_type_check_magic.hhi` to the specified path, e.g. "fbsource/buck-out/v2/gen/fbcode/f88b3f368c9334db/hphp/hack/hhi/__pessimised_hhi_hsl__/out/pessimised_hhi_hsl"
   1. ***It feels dodgy to be writing into buck out directory***
4. TestA finishes writing its builtins
5. TestB starts writing its builtins. It will write them to the exact same filename+location.
   1. ***Unix behavior is that the `fopen` call will truncate the existing file***
6. TestA proceeds to read its HHI directory.
   1. ***TestA will read an empty file for hh_single_type_check_magic.hhi***
7. TestA finishes with failure
8. TestB finishes writing its builtins.
9. TestB runs and completes okay.

This race will sometimes manifest with stress-tests (where we run the same test usually 18 times concurrently). That's where I spotted it D49341464. It might also manifest from different tests which share the same --custom-hhi-path, though I've not yet seen that in the wild.

This diff
1. changes some `--custom-hhi-path` tests to also pass `--no-builtins`
2. changes hh_single_type_check to error if you use `--custom-hhi-path` but fail to pass `--no-builtins`
3. There are some tests which use --custom-hhi-path but require builtins. These have the potential for flakiness, and should be fixed, but that's beyond my scope. For now I added a flag `--force-allow-builtins-in-custom-hhi-path-FLAKEY` which suppresses the error from step 2.
