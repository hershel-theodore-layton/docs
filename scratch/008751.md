Commit title: fix bug with printing types in "extract into method" code action, better type printing for code actions
Commit body:
Summary:
User-facing changes:
- Fix bug where extracting a method that should return `vec<int>` was instead emitting `_` for the return type (see test case and video in {D49315938})
- "Extract into method" can now print large types, rather than a message saying it ran out of fuel. I borrowed the code from extract_shape_type and will dedupe in {D49315936}
- Start emitting non-denotable types like unions. Reasoning:
    - If a type in an extracted method has a shape with four fields and one of the fields has a union in it, we save the user work by emitting three "good" fields and one field that needs some touch-up to satisfy the type-checker.
    - Giving the user more information may help them: if we extract `foo(): int | bool` the user can reflect on whether they should change the implementation or return `mixed`.  We already show non-denotables in hovers and for "extract shape type", so emitting non-denotables in "extract into method" introduces nothing really new.
   - The existing behavior of returning `_` could be confusing, since the error message users would see was about an unexpected type wildcard

Implementation notes:
- The module introduced here is reused later in the stack so we end up with a standard way to stringify types in code actions
- Converting a type string to a string is done lazily because we want to only do the work of expanding and printing a big type if the code action is selected. Code actions are computed lazily, see {D45828606}
