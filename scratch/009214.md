Summary:
The purpose of this minor refactoring (besides slightly improving readability by splitting logic of a long-ish function into separate functions) is to split the logical steps of (parse + validate) and (generate). In practice, I locally played around with the output of the first phase in a debugger, which helped me understand some aspects of our AST parsing.

# Description of changes

1. In `compiler.cc`:
   1. Extracted the parsing and validation logic out of `compile()`, to a new internal function (`parse_and_validate()`) whose output is the validated AST (that will then be generated). The motivation for this change was two fold:
      * First, by moving the non-trivial parsing and validation call logic from `compile()`, it simplifies code and allows the maintainer to better capture the intent of each method.
      * Second, it lays down ground work for potentially testing directly the AST output of the compiler (instead of, say, the resulting generated code and/or diagnostics, as current unit tests do).
      * That being said, there is [valid feedback](https://www.internalfb.com/diff/D49846179?dst_version_fbid=291409360366713&transaction_fbid=313297011434511) regarding the fact that this introduces one more "`parse*(`" method to this file (which already has 4 such methods in its public API). At least the one introduced here is internal, but I agree with viz's overall point that we should be reducing the number of parsing APIs. I'm hoping to do so in subsequent diffs, through a combination of:
        1.  Removing unused methods (if any)
        2.  Refactoring some of the compiler logic to better encapsulate concepts (like parsing, generation, etc.) rather than having them all laid out in a single namespace/file.
   1. Renamed and refactored the two existing internal, overloaded `generate()` methods to better capture their differences. The resulting methods hopefully make it easier to understand their respective purposes:
      * `generate_code_recursively(...)`
      * `generate_code_for_single_program(...)`
      * `generate_code_for_program_bundle(...)` (which calls one of the two above - depending on whether recursive generation was requested).
      * Note on naming: I added a mention of "code" in the name to address [prior feedback](https://www.internalfb.com/diff/D49846179?dst_version_fbid=1915654455485041&transaction_fbid=251254494562917). I'm well aware that generators do not necessarily produce code, but hopefully providing a direct object to the action ("generate") helps address the concern raised in that comment.
   2. Moved some common or well-isolated logic out of `generate*` methods to new internal helper functions, to better capture the specific steps and "spread" the complexity across (documented) methods:
      * `parse_generator_name_and_options(...)`
      * `make_and_init_generator(...)`
      * `validate_program()`
