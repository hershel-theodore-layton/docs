Commit title: require CWD set correctly prior to launching LSP
Commit body:
Summary:
> This diff has a change in behavior which will affect OSS hack LSP. Previously, it allowed the VSCode extension (or other client) to launch `hh_client lsp` from any directory. Now it has the same requirement as `hh_client check` and other commands -- it must either have a final "WWW root" command-line argument, or failing that it must have CWD to be either the project root (where .hhconfig is) or a subdirectory.

I first wrote clientLsp with the conceit that it doesn't know what the project root is until after it has received an "initialize" LSP request -- this request contains project root. Notionally, the VSCode can invoke `hh_client lsp` from any CWD, and clientLsp.ml would hold off doing anything involving root until after it had received the initialize LSP request.

But at Meta this isn't true: when VSCode invokes `hh_client lsp`, in reality it looks at the CWD, finds the current .hhconfig, reads the version= line, uses that to fetch the correct hh_client binary, and continues. And if we subsequently receive an LSP initialize request with a different project root? There's no good way to reconcile the behaviors. What it's been doing since D46501268 (June 2023) is at least logging telemetry if this happens, and it has happened only once https://fburl.com/daiquery/tzh8fj1q in an inexplicable way.

This has led to irritating workarounds: instead of being able to initialize a load of things early, we deferred them until after root was known, i.e. after the initialize request had been received. There was lots of "if root isn't known yet then skip else do something" code.

In this diff I've at last deleted all that. I simply require CWD to be set correctly at the start. That means we can load `local_config` from hh.conf early, and set up Hh_logger early, by having `hh_client lsp` behave just the same as `hh_client check`. For the immutable information which we learn from root, I stored it in a global value `env`, which is initialized to a dummy placeholder but then immediately assigned as one of the first things in `ClientLsp.main`. That way the code doesn't need to worry about a 'None' case.

I made one other simplification. For Meta's Atom client "Nuclide", there was a bug where it passed the CLI argument `hh_client lsp --from vscode`. And Atom was frozen, so we could never fix that. Instead we distinguished whether the initialize request had `client_capabilities.textDocument.declaration` (since Atom never got that, but VSCode already had it by the time of the transition from Atom to VSCode). And we used that to overwrite the global mutable variable which stored the `from` argument, plus change the state of HackEventLogger to write it correctly. Well, all of that mess might as well be deleted now since Atom is history. Let's just accept `--from` at face value, and don't mutate it.

One other thing that irritated me is that it used to display `hh_server is stopped` in the status bar for too long during initialization. That's because it couldn't query the state of hh_server until after it knew root. Well, now it can, and it figures out hh_server state almost immediately during `ClientLsp.main`, so I think it should display a more useful status right from the start. It certainly seems to in my tests.

Why am I doing this now? Because I'm working on "pull diagnostics", where the didChange method handler needs to know the value of a flag from `local_config`, but there was no good place for it to get that from. I figured I'd rather spend time better engineering the code, than to hack in an ugly new place where `local_config` could be obtained.

Stylistically, in this diff, I stored all of the environment stuff which is calculated at the start of `ClientLsp.main` and thereafter immutable, in a single mutable record named `!env`. I thought this was the easiest cleanest way to group it, make it searchable, understand where+how it was initialized.
