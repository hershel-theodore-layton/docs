Summary:
It turns out our first extract method plugin will need the concrete syntax tree and path, so make these available. See later in the stack for how they are used.

I also took this opportunity to add doc comments and make parameters a bit more consistent.

## Alternatives considered

I considered removing the burden of API design by making the signature of an extract method plugin the same as for any other refactoring (plus some more information using `Extract_method_types`).  I didn't do this because:
- The provider context is mutable and has footguns (like reading values directly rather than using the functions to get memoized versions)
- There's just too much non-discoverable boilerplate involved in (for example) getting a syntax tree and I want the API to be at least somewhat usable
