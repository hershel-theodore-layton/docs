Commit title: refine search for rust.type in typedef hierarchy
Commit body:
Summary:
compiling a thrift type `T` will result in the generation of instances of `fbthrift::Serialize` and `fbthrift::Deserialize` for `T`
```
impl<P> ::fbthrift::Serialize<P> for self::T { ... }
impl<P> ::fbthrift::Deserialize<P> for self::T { ... }
```

when `T` has a member `data` of type `U`, if `U` is deemed nonstandard then serialization of `data` will be achieved by
```
crate::r#impl::write(&self.data, p);
```
and in the `r#impl` sub-module the `read` and `write` functions involve locally generated instances of serialization functions for `U`
```
impl<P> ::fbthrift::Serialize<P> for LocalImpl<U> { ... }
impl<P> ::fbthrift::Deserialize<P> for LocalImpl<U> { ... }
```
if on the other hand, `U` is standard we appeal to some stock `Serialize`, `Deserialize` instances for `U` like this
```
::fbthrift::Serialize::write(&self.data, p);
```
that is, no local `Serialize`, `Deserialize` instances for `LocalImpl<U>` are generated.

before D51049111, the implementation of `has_nonstandard_type_annotation` read
```
bool has_nonstandard_type_annotation(const t_type* type) {
  return type->get_annotation("rust.type").find("::") != string::npos;
}
```
and for a given type, the question of "do we write `crate::r#impl::write(...)` or `::fbthrift::Serialize::write(...)`?" answered by,
```
mstch::node rust_nonstandard() {
  return (
    has_nonstandard_type_annotation(type_) &&
    !(type_->is_typedef() && type_->has_annotation("rust.newtype")));
   }
```

so, if in the presence of thrift like this
```
typedef binary (rust.type = "bytes::Bytes") binary_t;
struct T {
  1: binary_t data;
}
```
`binary_t` will never be considered nonstandard [^1], serialization of `T::data` will be through `fbthrift::Serialize::write(&self.data, p)` and no
```
impl<P> ::fbthrift::Serialize<P> for LocalImpl<bytes::Bytes> { ... }
impl<P> ::fbthrift::Deserialize<P> for LocalImpl<bytes::Bytes> { ... }
```
generated.

[^1]: this is because `has_nonstandard_type_annotation()` (above) looks only at whether the immediate type is nonstandard and no further, even if that type is an alias for another type that is in fact nonstandard.

now if,
```
struct T {
  1: binary (rust.type = "bytes::Bytes") data;
}
```
and
```
typedef binary (rust.type = "bytes::Bytes") binary_t;
struct T {
  1: binary_t data;
}
```
are to be equivalent, `has_nonstandard_type_annotation()` has to change to
```
auto get_type_annotation(const t_type* type) {
  return t_typedef::get_first_annotation(type, {"rust.type"});
}
```
and now in the typedef case  `binary_t` will be considered nonstandard, serialization of `data` will be through `crate::r#impl::write(...)` and `impl<P> ::fbthrift::Serialize<P> for LocalImpl<bytes::Bytes> { ... }` generated. this is the fundamental change that D51049111 introduces.

all occurrences of `binary (rust.type = "bytes::Bytes")` in fbcode before and after D51049111 are in `typedef` position and after D51049111 "fixing" `get_type_annotation`, occurrences of
```
impl<P> ::fbthrift::Serialize<P> for LocalImpl<bytes::Bytes> { ... }
impl<P> ::fbthrift::Deserialize<P> for LocalImpl<bytes::Bytes> { ... }
```
are generated where before they didn't. that's the right behavior but the problem is in the case of `binary`, this newly generated code doesn't compile[^2]!

[^2]: `bytes::Bytes` does not provide `extend_from_slice` or `with_capacity` making it not a drop-in for `Vec<u8>`.

this led to phrasing D51049111 (a kludge knowingly entered into to unblock progress on D50818506) as
```
// Why does this behave differently for typedefs of containers and typedefs of
// binary? Yes.
auto get_type_annotation(const t_type* type) {
  return type->get_true_type()->is_container()
      ? t_typedef::get_first_annotation(type, {"rust.type"})
      : type->get_annotation("rust.type");
}
```
which "works out" in that it causes `binary_t` to be regarded as standard and the "bad" serialization code to not be emitted (that is, the behavior of the status quo for typedefs of binary to the nonstandard type `bytes::Bytes` prior to D5104911 ).

this diff takes the view that this implmentation of `get_type_annotation` is correct
```
auto get_type_annotation(const t_type* type) {
  return t_typedef::get_first_annotation(type, {"rust.type"});
}
```
and `bytes_t` now is thereby correctly classified as nonstandard and it is that `bytes::Bytes` is not compatible with the generated serialization functions that exercise it that is the real problem.

this diff then works-around this issue in the following way.
```
auto get_type_annotation(const t_type* type) {
  return t_typedef::get_first_annotation(type, {"rust.type"});
 }

mstch::node rust_nonstandard() {
  return (
      has_nonstandard_type_annotation(type_) &&
      !(get_type_annotation(type_) == "bytes::Bytes") &&
      !(type_->is_typedef() && type_->has_annotation("rust.newtype")));
}
```

it's still a hack (and something needs to be done about this) but it's a better understood hack.
