Summary:
My goal is to support cancellation. This is motivated by the observation that P95 autocomplete times are losing 220ms to finishing off preceding requests.
* post: https://fb.workplace.com/groups/342676619986174/posts/1394664301454062/?comment_id=1394664914787334
* scuba:

What we ultimately need is this:
1. while the ClientIdeDaemon process is engaged in CPU-bound decl-fetching or tast-computing work
2. while the ClientLsp process is awaiting a response from ClientIdeDaemon
3. we need ClientLsp to peek ahead in the LSP queue and find a mechanism by which it can signal to the ClientIdeDaemon process to terminate.
4. we need Tast_provider.compute_tast to be able to respond to that mechanism by terminating.

A mechanism for (3/4) already exists in hh_shared.c: there's a bit in shmem, which hh_server main process sets in response to a watchman notification, and all hh_server worker process used to read each time they read/write a decl into shmem. This is perfect and exactly what I need.

In this diff I'm making ClientLsp and ClientIdeDaemon both map a shmem segment between themselves. It uses SharedMem.empty_config, hence will be two pages big. There'll be no GlobalStorage area, no hashtable, no heap.
