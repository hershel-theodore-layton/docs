Commit title: Treat top-level statements as wrapped in a function.
Commit body:
Summary:
### What

 Hack is pretty good at type-checking top-level functions, so handle top-level statements as if they are in a function. This is true to how top-level statements are executed in both the debugger and notebooks and is (I hope) easier to reason about than the alternative considered.

User-facing changes:
- Fix T170614550 (top-level await not having completions or expected squiggles Hack notebooks)
- Fix T171522422 (error about undefined `$#capability` in notebooks)
- There are more completions when the user types `f` at the top-level of a namespace, since the autocomplete no longer distinguish whether we're in a top-level statement in a namespace or a function in a namespace. This is arguably a minor devX regression for a case that doesn't arise much in practice. We may be able to add more logic to handle this case, but it would get gross for minimal benefit. see fb-only note below for more info

### Why

- Better handling for potential edge cases such as type checker timeouts
- Fix for T171522422 and (coming later in this stack) T170614550

### Background

Top-level statements are technically not supported, but are expected to work in Hack notebooks. We're trying to best-effort support the notebooks use case while being careful to not add much maintenance burden to our stack.

### How

Pretend top-level statements are wrapped in a top-level function.
This way, we are less likely to violate subtle invariants and safety checks that we currently have when checking the bodies of functions. We piggyback on the logic for checking functions and get the following:
- Type-checking with a timeout (`Typing_helpers.with_timeout`)
- Whatever `Reason.reset_expr_display_id_map ()` does
- Setting special local variables for coeffects (`$#capability` and `$#local_capability`) using multiple functions from `Typing_coeffects`
- other things I don't know about yet

## Alternatives considered

- Alternative: repeat relevant logic from function typing. This seems error-prone and hard to maintain. This direction was started in {D51028939} but I noticed it is already wrong (for example, missing `Reason.reset_expr_display_id_map ()` and not setting implicit capability variables–see above)
- Alternative: factor out common logic. Perhaps more pleasing to the eye, but:
    - This would make the type-checking logic for functions harder to follow and make it harder to delete the typing for top-level statements if we end up taking a different approach.
    - We would lose the nice correspondence between how top-level statements are executed and how they are type-checked: the HHVM debugger bundles top-level statements up into a function.
