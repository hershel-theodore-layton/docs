Commit title: Require non-unique instantiation interface extends/implements to be ordered wrt subtyping
Commit body:
Summary:
# Current Behaviour

A class can implement a generic interface indirectly with multiple instantiations of the generic, for example:
```
interface I<T> {}
class A implements I<int> {}
class B extends A implements I<string> {}
```
`B` implements both `I<int>` and `I<string>`.
## How hh deals with this
It only considers the first instantiation encountered when traversing ancestors depth-first, and plainly ignores all the other ones. AND it starts traversing ancestors with `extends` parents, then `implements`, then `use`.
So in this example, `I<int>` "wins" over `I<string>`.

# Issues with the current behaviour

* The fact that we ignore some instantiations breaks transitivity of subtyping, which allows to create **type holes** like P474546997.

  * It also prevents optimising the fanout algorithm when adding a parent, which has the potential to save between 20% and 50% average fanout sizes.

# Proposal (this diff)

The proposal is: Make sure any ignored instantiation is a supertype of the winning instantiation. Error otherwise.

We would for example allow:
```
interface I<+T>
interface J extends I<num> {}
class B implements I<int>, J {}
```
Because the winning instantiation `I<int>` is a subtype of the losing one `I<num>` (because `I` is covariant).

But we would not allow this code:
```
interface I<+T>
interface J extends I<int> {}
class B implements I<num>, J {}
```
Because now `I<num>` wins and `I<int>` loses.

## Other options and why we rejected them

Andrew wrote a discussion on other options and why he rejected them here: https://docs.google.com/document/d/19FeaYclaHrIXpNXv8cmGHvA5QqYysWojSCRShy8NlTo/edit?usp=sharing

And this document describe how he arrived at the current plan: https://docs.google.com/document/d/1tA1_NPX42M3d7LZdspAUwEEjYonphLalWmIm3EEVymA/edit?usp=sharing

# Path to production

As is, this diff causes 600,000 errors in www. For more than half of them, there is no instantiation that is a subtype of the others, so it is hard to think of a manual fix. A lot of the errors are in generated code.

However, there are only about 70 interfaces used illegally with multiple instantiations. We propose to annotate them with a new attribute `<<__AllowMultipleInstantiations>>` which will silence the errors related to those interfaces. These 70 attributes are enough to eliminate the 600,000 errors.
