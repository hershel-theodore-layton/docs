Commit title: More determinism for expression IDs
Commit body:
Summary:
In Typing_reason, we maintain a map `expr_display_id_map` from expression IDs to integers that will be used to display expression IDs in errors (so instead of displaying some seemingly random <expr#1234>, we display some nice small and consecutive numbers.

However, **the way this map is used is extremely dodgy**. When comparing TAST hashes and errors (e.g. for mass replays), I sometimes see random discrepancies in expression IDs. When I remove the display map entirely, I get rid of that non-determinism.

Why it's dodgy:
* because it's not just used for errors, it's used in particular by DependentKind.to_string, which flows into all sorts of things, including `Tgeneric`. That leads to horrendous logic like this one in Typing_escape: https://fburl.com/code/08z3wyk1. Quentin was smart enough to spot the complexity, but surely the subtlety was missed in other places.
* The observed non-determinism is a smell.
* It's hard to make sure the display map is reset properly. Before D50271708, the map would be reset for each method, but then stay as it was for the last method for TAST checks, and possibly other paths.
* Using the display map for DependentKind.to_string defeats the goal of cleaner error messages. It's frequent that errors don't start with <expr#1>.
  * I've tried to create another flavour of DependentKind.to_string which does not use the map, but that leads to inconsistent error messages (e.g. "but got <expr#23>::T ... where <expr#1> refers to this expression"). (My attempt: D52253238).

**I think we should remove the map**, trading simplicity and likely correctness for a bit more quirkiness of error messages, which I think is a fine trade.

This diff is an attempt at removing the non-determinism but still keeping the display map. Another RFC diff will remove the map.

Main changes in this diff:
* Add abstract type Expression_id.t, use it for expression IDs instead of Ident_provider.Ident.t
  * Expression_id.t is under the hood Ident_provider.Ident.t, but abstract, i.e. cannot be used instead of other Ident.t like type vars.
* The expression ID display map from Typing_reason is moved to Expression_id, and is reset when creating a new expression ID provider. Since providers are per env, the display map is also reset whenever we create an env. Env creation can happen in odd places, e.g. before doing TAST checks. Before, when starting TAST check, the display map would still contain the mapping for the last method, which surely would produce odd results.
* The provider is reset for each method. Before it was reset for each class with the display map reset for each method.
  * This is to have the same behaviour/test outputs as before, but I don't like it because
    * when doing TAST checks, we don't reset the provider for each method. So we might have <expr#1> in multiple methods (but not referring to the same expression), but the display ID map will be the same across methods, which might give odd numbering in error messages.
  * I'm killing resetting the ID provider for methods in the next diff, as an RFC.
