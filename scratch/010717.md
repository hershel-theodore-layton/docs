Summary:
## Design considerations
- We do NOT remove Gallium code . We mark deprecated. Removing the features needs significant work to preserve the correctness.
- The Native Neon aims to be **a drop-in replacement** for the **asset scoping** analysis. The first implementation is to provide `call_history` and `matched` fields (`neon_request_profiles` table), which are compatible with Hack Neon. So, we can use the current asset scoping pipeline without any modifications.
- This diff does not implement additional features for HAGVAH memoization like `caller_history` and `pz_history`. We still use Hack Neon for these purposes.

## Implementation

Recap on how Native Gallium is implemented:
- On a profiling start, initiated by the Hack-side [driver](https://www.internalfb.com/code/www/[cd5d0f5d27e89849721075379d61f8e18020b4f6]/flib/profiling/hack_call_trace/HackCallTraceProfiler.php?lines=1533), install a function call hook: `EventHook::EnableInternal`.
- On every function events (call, return, resume, suspend, and unwind), log a bunch of information. There's a partial trace mode, but basically Gallium records entire function executions.
- On PSP time, when profiling ends, compress the trace and [pass it](https://www.internalfb.com/code/www/[cd5d0f5d27e89849721075379d61f8e18020b4f6]/flib/profiling/hack_call_trace/HackCallTraceProfiler.php?lines=815) to the Hack.

Native Neon is much simpler than Gallium:
- Unlike Gallium, Neon only records the call/resume (no exits) events of **specific functions**. And we only simply log function ids.
- On PSP time, we convert the raw `FuncId` trace into the `matched` and `call_history`, using the same data format of the current Hack Neon.

The implementations are straightforward: `logForNeon` and `computeMatchedAndCallHistory` are the main implementations. However, a few issues are there:
- Note that both Gallium and Neon pay the same price of hooking every uninlined function calls using [the surprise flag](https://www.internalfb.com/code/fbsource/[d632403944db]/fbcode/hphp/runtime/vm/event-hook.cpp?lines=85).
- To record only specific functions, Neon is taking [a config from users](https://www.internalfb.com/code/configerator/[2c3253bb3ed7]/source/high_fidelity_lineage/hb_discovery_ent_probes/hb_discovery_ent_probes_sink_1_batch_1_autogen.cconf?lines=1). Here Neon can load up to [420K function names](https://fburl.com/code/hbyu1pu4)! Gallium was also doing a similar work: getting a list of functions of interest from users. But it was only a handful of the functions. So, this loading huge user-provided functions can be heavy. But it is still the same overhead of Hack Neon's.
  - You might consider using class-name-based matching, but it has also other trade-offs such as longer call history, etc. We keep the same approach of what Hack Neon does, detecting exact function names.
