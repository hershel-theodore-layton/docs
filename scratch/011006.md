Commit title: use CLIENT_LSP_METHOD.exit_code column for lsp error codes
Commit body:
Summary:
Currently in hh_server_events CLIENT_LSP_METHOD we record `message` and `data` parts of the LSP response, but we fail to record the third part `code`.

This is irritating! It means that loads of charts have to reconstruct which responses were RequestCancelled responses by enumerating all the different messages that ClientLsp.ml happens to use. I recently broke this by adding yet another message that ClientLsp.ml uses in a new area of cancellation. Well, in mitigation, iData has derived columns `lsp_is_ok`, `lsp_is_cancel`, `lsp_is_error`. So at least there's one central definition for folks using scuba.

Actually, that kind of reconstruction is probably necessary. Consider what happens which hack is loading saved-state. We respond with an error, and lsp_error_message "IDE service has not yet completed init". But the only LSP error code we can respond with which VSCode won't pop up a notification box for is RequestCancelled. So we use that error code even though it's not truly a RequestCancelled. (Actually, last year, VSCode changed it so that RequestCancelled does pop up a notification box I think? And mroch fixed this by intercepting RequestCancelled and turning it into an Ok response with null or empty-list?)

And also, for our historical charts, we'll want reconstruction for all the years prior to this diff.

Anyway, even though it's no practical use, this diff adds error code to our scuba data. But maybe once this diff has landed, then five years from now we can benefit from it. It adds the error code for CLIENT_LSP_METHOD by re-using two existing columns, `exit_code` for the integer LSP error code and `exit_kind` for the string.
