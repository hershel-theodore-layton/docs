Commit title: Improve heuristic for checking function calls involving lambda expression arguments
Commit body:
Summary:
The existing scheme for check arguments in function calls is as follows:

1. Check, from left-to-right, all argument expressions that are not lambda expressions. This is intended to gather constraints on type variables that may appear in the expected types (particularly argument types) of lambdas.
2. Check, from left-to-right, all lambda expression arguments.

Unfortunately there is a nasty interaction with like types. Consider the following generic, higher-order function:
```
function any<T>(vec<T> $v, (function(T):bool) $p):bool;
```
and a call `any($v, (C $x) ==> body)` where `$v` has type `vec<~C>`.  We will generate a fresh type variable, say `#1`, standing for `T`. Then we will check the non-lambda argument, namely `$v`, doing `vec<~C> <: vec<#1>` so producing a constraint `~C <: #1`. We'll then check the lambda, producing a type `(function(C):bool)`, and try `(function(C):bool) <: (function(#1):bool)` i.e. `#1 <: C`. But now we have an inconsistency, because in essence we inferred a like type for the type parameter.

If we had instead checked the lambda first, we would have realized that we could infer `C` for the type parameter, and apply like-pushing to the first argument.

So the new strategy is as follows:

0. Check, from left-to-right, all argument expressions that are lambdas with explicitly-typed parameters. We don't lose anything by doing this - all we need to infer are return types.
1. Check, from left-to-right, all argument expressions that are not lambda expressions.
2. Check, from left-to-right, all remaining lambda expression arguments.
