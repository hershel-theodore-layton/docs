Commit title: compiler error enforces IWYU
Commit body:
Summary:
unlike C++ thrift, thrift-rust can experience unexpected compilation failures when there are "transitive" dependencies in a thrift module. A "transitive" dependency refers to a type e.g., `common.SomeStruct` whose parent module is not explicitly `include`d in the thrift module. This may happen to work if the thrift file `include`s `intermediate.thrift`, which in turn `include`s `common.thrift`. The thrift behavior mimics C++'s transitive includes behavior.

thrift-rust uses full crate names to refer to types, which makes it relatively resilient. However, an explicit `thrift_library` `dep` is still required on the `thrift_library` "target" that contains `common.thrift`. Otherwise, the thrift-generated `rust_library` target will experience a compilation failure.

There are only a few thrift-rust modules that violate IWYU currently, so I suggest we start enforcing direct IWYU at the compiler level. Benefits include:
1. Better, simpler tooling. It's easier for tools like `rust-guess-deps` to add deps if `include`s are explicit!
2. Safely refactor build graphs. Some of the thrift files in this target happen to work because they depend on `thrift library` targets that contain multiple sources. If someone decided to split apart these `thrift_library` targets, there would be unexpected build breakages.
3. Easier to understand a one-line thrift compiler error than a rust compiler error resulting from missing dependencies.

The current implementation checks *all* types, and
1. raises `error` diagnostic (hard build fail) for most types, when run for a `rust-thrift` invocation.
2. raises `warning` diagnostic for structured annotation includes. There are a good number to fix, and someone is working on making a "linter" to auto-add the include.
