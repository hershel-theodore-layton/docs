Commit title: Execute ThriftServer-scoped TProcessorEventHandler alongside global ones
Commit body:
Summary:
This is a follow-up from {D51483688} which caused S383224. In this diff, we don't touch how globally registered event handlers are treated. Instead, we only *add* `ThriftServer`-scoped event handlers to the existing set.

Here's how it works before this change:
1. `AsyncProcessor` is created and a snapshot of the global set of event handlers is taken from `TProcessorBase`.
2. In `AsyncProcessor::executeRequest`, we create a `ContextStack` object from this set.

This diff changes it to add step 1.5 — `coalesceWithServerScopedLegacyEventHandlers` will take `ThriftServer`-scoped event handlers (added via `ThriftServer::addModule`) and merge them into the existing set from step 1 (via `addEventHandler`).

This means that, unless there are `ThriftServer`-scoped event handlers registered, there is no change in behavior. Therefore, this change is much safer than the original diff (which took a snapshot of the global set at server startup).

`clearEventHandlers` will work correct (unlike D51483688), except that it will not be possible to ignore `ThriftServer`-scoped event handlers. This is by design — we want to eventually rid ourselves of these `clearEventHandlers` shenanigans and instead ask users to remove `ServerModule` objects if they wish to bypass some logic. This stance make sure that no one accidentally removes ACLChecker or something. It also aligns with the upcoming `ServiceInterceptor` proposal.

Why does `coalesceWithServerScopedLegacyEventHandlers` mutate the `AsyncProcessor` object instead of creating a new list?
Because we cannot do that without (a) performing an allocation or, (b) changing how globally-registered event handlers are collected. D51483688 was already known to cause a regression to an important service so we are extra cautious here. Furthermore, this merging happens once per connection now.
