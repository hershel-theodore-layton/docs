improve representation of Quickfix.t

## Changes

- no-op from the user's point of view
- `hh_single_type_check --fix` now prints a warning if used on non-eager quickfixes. It previously "worked" but had its own version of the logic for handling non-eager quickfixes that could differ from that in prod.  Tests that use `hh_single_type_check --ide-code-actions` exercise much more of our logic and show more user-facing behavior (including the range that triggers the code action and what other code actions are offered for the range).

## Details

Update our quickfix representation to remove debt and make upcoming work on bulk  quickfixes more straightforward to achieve.

The main change is in Quickfix.ml, in type `t`, where we explicitly model whether a quickfix is eager (all information available without further calculation). Other constructors can be used for lazily computed quickfix positions, of which Class_end is one example

Everything else follows from that change, with a few clean-ups that emerged naturally:
- Override_method.ml was creating a quickfix just to convert it to a refactor, and leaked its concerns into the representation of quickfixes. Fix by using a private data structure in override_method.ml
- Nearly half of Quickfix.ml was dedicated to a test utility used only by hh_single_type_check that repeated implementation details of how we manage class positions and doesn't seem to test very well (our //hphp/hack/test/quickfix doesn't test error positions or handle the case where multiple quickfixes are offerred for a given range). Move the test utility to hh_single_type_check.ml and adapt it for the new representation of quickfixes.

An advantage of this work (besides enabling upcoming bulk quickfixes work) is that it removes tech debt:
- threading-around of ~classish_information any time we want to use quickfixes
- I can make a follow-on to remove debt I introduced in D53813494, details below
