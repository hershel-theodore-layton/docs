Commit title: SmallSerialExecutor
Commit body:
Summary:
D10345872 switched `SerialExecutor` to `UnboundedQueue` claiming "reduced contention", but there is no test that demonstrates any actual impact. Instead, `UnboundedQueue` comes with large memory overhead, due to [counterintuitive behavior of hazptr cohorts](https://fb.workplace.com/groups/560979627394613/posts/2672435996248955). At the same time, there is no reason for the queue to be contended: the whole point of `SerialExecutor` is to limit concurrency to 1 thread, and if there were a large number of concurrent submitters, the 1 consumer would not be able to keep up no matter what queue is used.

People have ran into this issue and used workarounds, for example D48412352 which makes the segment size configurable, and others are experimenting with pooling the `SerialExecutor` (which can cause all kinds of other problems).

This diff instead uses a simpler MPSC queue implementation that frees immediately the consumed segments, except for one that is kept cached. The producers are serialized using a mutex, but in common applications of `SerialExecutor` no contention is expected on the writers.

Eventual goal is to encourage people to run coroutine Thrift handlers in `SerialExecutor`, avoiding thread ping-ponging.
