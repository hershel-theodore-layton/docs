Commit title: Factor function name out of error type's SerializeExn impl
Commit body:
Summary:
The purpose of this diff is to unblock reusing the same Thrift-generated server Exn types in the signatures of multiple service methods.

Today, every service method gets its own unique error type. Often times all those error types are structurally identical for all the methods in the same service, because all the methods return the same set of Thrift exceptions with the same names; but the Rust signatures are still generated with distinct error types.

```lang=thrift
service MyService {
    void foo() throws (1: ServiceException ex);
    void bar() throws (1: ServiceException ex);
}
```

```lang=rust
pub trait MyService: Send + Sync + 'static {
    async fn foo(&self) -> Result<(), crate::errors::my_service::FooExn>;
    async fn bar(&self) -> Result<(), crate::errors::my_service::BarExn>;
}

pub mod errors {
    pub mod my_service {
        pub enum FooExn {
            ex(ServiceException),
            ApplicationException(ApplicationException),
        }
        pub enum BarExn {
            ex(ServiceException),
            ApplicationException(ApplicationException),
        }
    }
    pub use self::my_service::*;
}
```

I am interested in generating instead something like:

```lang=rust
pub mod errors {
    pub mod my_service {
        #[doc(inline)]
        pub use super::_ex::Exn as FooExn;
        #[doc(inline)]
        pub use super::_ex::Exn as BarExn;
    }
    mod _ex {
        pub enum Exn {
            ex(ServiceException),
            ApplicationException(ApplicationException),
        }
    }
    pub use self::my_service::*;
}
```

The primary benefit is to allow the use of short names (`my_services::errors::FooExn`) for error types that would have been ambiguous in the prior approach, when 2 services from the same Thrift library have methods with the same name and same `throws` declaration.

A secondary benefit will be reducing monomorphizations of generic serialization code with a bunch of structurally identical error types, which will improve compile time.

In the new design, a single Exn type no longer corresponds with a unique choice of `write_struct_begin` argument string. So the string to use needs to be passed in by whatever code is serializing the Exn type and knows what method it's for.
