Commit title: Fix Identify Symbol for Labels
Commit body:
Summary:
# Context
D55829619 changed the type in the TAST that will appear for expression like `get(#Label)`. This broke IdentifySymbolService which is used to power things such as Go-To-Def for the LSP.

# Mitigation
The code that handles EnumClass\Labels in IdentifySymbolService is extremely sensitive to changes in the types we infer because it uses pattern matching on the type in a very simplistic way. To make this more robust I made two changes:
1. I changed to utilize `typed_member_id`. This is used for identifying symbols for expressions that involve accessing a member of the receiver. This allows us to successfully identify symbols if the type is of the form `EnumClass\Label<this::T, _>` or other none simple forms for the first type argument. This is necessary because the new inference in D55829619 properly instantiates the `this` type, so we will have instances where the type could be an expression dependent type. `typed_member_id` already handles these cases. This required making some changes to `process_member` to have it produce a `SymbolOccurrence.EnumClassLabel`. I'm not sure why we need `SymbolOccurrence.EnumClassLabel` in the first place, instead of re-using `SymbolOccurrence.ClassConst` but I'll leave it as is for now

2. I added a new function `Tast_env.get_label_receiver_ty` that attempts to extract the type `T` from within `EnumClass\Label<T, _>`. The previous version used a simple pattern match to achieve this, but this means we would fail to identify the symbol if we inferred a type like `?EnumClass\Label` or a case type. What we do instead is utilize the constraint solver by constructing a type `EnumClass\Label<#1, nothing>` and check if the type of the expression is a super type. If it is then `#1` should be bound to the receiver type. We solve after adding the constraint and return the type bound to `#1`.
