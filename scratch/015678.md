Commit title: Pass service and method names to ServiceInterceptor::onRequest
Commit body:
Summary:
This diff adds to fields to `RequestInfo` passed into `ServiceInterceptor::onRequest` — `serviceName` and `methodName`.

We store pointers to these strings in `HandlerCallbackBase`. Why not just use the existing fields in `ContextStack`? Two reasons:
1. The method name in `ContextStack` and therefore `TProcessorEventHandler` includes the service name. In general, this is not what users want. Plus it's redundant since we also pass in the service name.
2. `ContextStack::create` has an optimization where it returns `nullptr` and there-by avoids a `malloc` when the set of `TProcessorEventHandler` is empty. We want to continue to have this optimization. However, it's possible that there are no `TProcessorEventHandler`s but there *are* `ServiceInterceptor`s. Therefore, it's best to avoid complicating the `ContextStack` machinery.

There should be no added binary size because the compiler should be interning every string used here. `HandlerCallbackBase` just increases in size by two pointers.

Why not `string_view` instead of `const char*`?
- `AsyncProcessor::getServiceName` is `virtual` and returns `const char*`. We don't want to force a `strlen` because the user might just choose to ignore it.
- Consistency with `TProcessorEventHandler` to make migration easier (`std::string_view` is not guaranteed to be NUL-terminated).

We can attempt to clean this up in a future diff.
