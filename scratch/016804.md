Commit title: Unhack set/map key diagnostic in Hack
Commit body:
Summary:
Diagnostic for invalid set elements and map key is spectacularly broken in Hack. Fix it:

* Fix a UB due to static casting of a list type pointer to a set type pointer:

  ```
  if (type->is_map()) {
    ktype = static_cast<const t_map*>(type)->get_key_type();
  } else {
    ktype = static_cast<const t_set*>(type)->get_elem_type(); // UB if type is a list
  }
  ```

This was obviously broken but happened to "work" because list and set types had similar layouts.

* Report it as a proper diagnostic instead of an exception and add location information. To this end pass the diagnostics engine to the generator which is a good idea anyway as it avoids duplication of checks (mainstream compilers do the same).
* Move diagnostic from various places to the type check where it belongs, reducing duplication.
* Fix diagnostic message by adding enum and binary which was previously missing.
* Remove the useless link to FAQ which doesn't provide any additional information.
* Specify the correct type in the diagnostic instead of the top-level type which was particularly confusing when the type contained multiple sets/maps.

The following example illustrates diagnostic improvement.

Thrift:

```
enum E {
}
struct S {}

struct T {
  1: map<E, set<S>> m = {};
}
```

Before:
```
[ERROR:test.thrift:1] InvalidKeyType: Hack only supports integers and strings as key for map and set - https://fburl.com/wiki/pgzirbu8, field: map<test.E, set<test.S>> m
```

After:
```
[ERROR:test.thrift:6] `S` cannot be used as a set element in Hack because it is not integer, string, binary or enum
```

Cache validity of container types since to avoid redundant checks - in a simple test recursive type checks were made 12 times! Now they are only done once.
