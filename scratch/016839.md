Commit title: Observe unbalanced DecRef in reduce_support_bit
Commit body:
Summary:
Ignoring an implicit unbalanced decref caused here when memory effects indicate an aset with a `lower_bound` of zero may incur a decref is unsafe. Consider the following example (prior to this change):

```
t1 := DictGetK t0, Int(1) ; lb(t1) = 1, memory_support[t1] = {t0:EI(1)}
IncRef(t1) ; lb(t1) = 2
...
t2 = Phi t1, ... ; lb(t2) = 0
StStk t2, ... ; lb(t2) = 0 memory_support[t2] = {Stk}
Call ; lb(t1) = 1, lb(t2) = 0, memory_support[t1] = {} ; memory_support[t2] = {Stk}
...
IncRef(t1) ; lb(t1) = 2
DecRef(t0) ; lb(t1) = 2
BespokeGet ..., t1
DecRef(t1) ; lb(t1) = 1
```

Notice here that the call caused us to adjust the lower_bound on t1 to 1 and drop our support bits from the `DictGetK` operation, however, as the lower_bound on t2 was already zero we left both the stack support bits and lower bound untouched. This is incorrect as we have now failed to account for a reduction in lower_bound of t1 via t2 (recall that they are may-alias sets) and while the lower_bound on t1 appears to be temporarily correct (1), we have actually already dropped a support bit from the array element, meaning that `DecRef(t0)` will not cause us to adjust the lower_bound on t1.
