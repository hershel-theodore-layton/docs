Commit title: Type splat: representation inside tuple types
Commit body:
Summary:
The original design for type splatting supported splat syntax `...T` only in a function type, on the last parameter, and preceded only by required parameters. Ignoring calling `inout` and `readonly` calling conventions, the "parameters" bit of a function type consists of

1. EITHER types for required parameters (i.e. `t1,_,tn`), followed by optional parameters, (i.e. `optional u1,_,optional um`) followed by a variadic (i.e. `t...`, where `t` is `nothing` if there are no variadics),
2. OR types for required parameters (i.e. `t1,_,tn`), followed by a single splat type (i.e. `...u`)

Syntax for open tuples supports 1 but not 2 i.e. type splats are not legal in tuples.

For completeness, it makes a lot of sense to support type splats in tuples. They arise naturally in function subtyping e.g. consider `(function(int,...T):void) <: (function(...U):void)` which is only possible if we allow `(...U) <: (int,...T)` i.e. subtyping between tuples that include splats. Here the lhs simplifies to `U`, but the rhs does not.

Another reason to include them in tuples is that it lets us simplify the story around expression level splats i.e. `...$x`. In principle, we should be able to treat a call `f(e1,_,en,...e)` where the arguments have types `t1,_,tn,t` by just doing tuple subtyping `(t1,_,tn,...t) <: p` where `p` is the "tuple type" of the parameters for `f`. In practice, splat expressions also allow spreading of traversables, not just tuples, but nevertheless it's easier to deal with expression splats in the presence of type splats in parameters if we also support type splats in tuples.

This initial diff just rearranges the representation of tuples (again) to make precise the mutual exclusion between options 1 and 2 above. Forthcoming diffs will introduce user syntax, subtyping, for the generalized tuples, followed by typing of expression-level splats.
