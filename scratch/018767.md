Commit title: Optimize `CancellationToken::merge` when tokens are empty or repeated
Commit body:
Summary:
## High-level context

`CancellationToken`s are merged in higher-complexity async code, most typically when using background tasks -- or doing scatter-gather operations -- that need to be cancelable both by "the parent coro" and also "separately, at the level of an async scope", and occasionally even "at the level of one sub-task".

The typical operation merges tokens (A, B) or (A, B, C), where any of those tokens might be empty, and (less likely) "duplicate" -- pointing to the same underlying cancellation state.

Ideally, one can write user code as-if `CancellationToken` is optional -- its empty state is already very cheap. However, today's `merge()` ruins this picture: `merge(empty, std::move(active), empty)` will allocate > 350 bytes, and invoke some atomic ops just to wrap a single `active` in a "merging" cancellation token.

So, today, callers either need to accept the above inefficiencies, or manually filter the args that they pass to `merge()`.

## Proposed fix

The previous code has one fast path, chosen via a runtime branch:
- (fast) If all tokens are empty, return an empty token.
- (costly) Allocate heap object with a `CancellationCallback` for each token in the user-provided pack.

The new code does a lot better at avoiding allocations and atomic ops:
- (compile-time) `merge()` returns an empty token
- (compile-time) `merge(tok)` moves or copies that one token
- (runtime fast) If all input tokens are empty, you get an empty token back
- (runtime fast) If, after deduplicating adjacent token states, there's only 1 nonempty token, you get it back
- (runtime) We now allocate a merging state + `CancellationCallback`s only for the nonempty, distinct tokens.

*Implementation notes:*
 - I first tried a version with `std::unique` + `std::sort`, which would give full deduplication with less code. For the crucial case of `merge(a, b)` distinct, this resulted in a 25+% instead of an 8% slowdown, so I looked for better ways.
 - I don't like the specialized `create{Copy,Move,CopyMove}` constructors, but -- compared with just `CopyMove` -- this helps take the `merge(a,b)` case down 3% in my micro-benchmark, and I really wanted to try to make the cost acceptable here.
 - I moved as much into the `.cpp` file as I could without impacting micro-benchmarks. Smaller binaries should be cheaper in production, but I expect this gain to be too small to measure, so I won't try.
## Actual performance: before & after

I don't measure the memory savings, but that math is simple. A `MergingCancellationState` is 48 bytes in both versions, and it attaches a list of 112-byte `CancellationCallback`s.
 - Before this diff, a `merge()` with N arguments would allocate 48 + N * 112 bytes, unless it had a single argument OR all of its arguments were empty.
 - After this diff, `merge()` **only** allocates if out of the N arguments supplied, M >= 2 are nonempty and distinct. Then, it allocates 48 + M * 112 bytes.

In terms of CPU, I focused on **minimizing the regression** to the most-likely-affected merge-distinct-nonempty cases, primarily `merge(a, b)` and secondarily `merge(a, b, c)`. This looks to be under 4%, and less in other cases. I do not have further ideas for shrinking this overhead.

In practice, I suspect that we will quite often be in the scenario where some all arguments are empty or repeated, so I expect it'll be a overall improvement in cost of production.
