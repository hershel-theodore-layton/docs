The issue seems to stem from the improper closing of the work queue in the thrift server which does not appropriately drain the channel before closing it and creates a race condition between goroutines. Everytime the thrift function recieves a request, it queues the request along with appropriate handlers via the [scheduleResponse function](https://fburl.com/code/bfsu1upp) . This function feeds `workItems` into the job queue but this queue is closed when the server recieves a [context cancellation](https://fburl.com/code/lsei9e8e) , which closes the channel and ignores requests which are already being served by scheduleResponse.

My solution to this problem is to ignore the channel close and instead use the server context to avoid dangling goroutines.
Channels can be garbage collected (unlike goroutines) and in the worst case some of the requests will be dropped on the floor if the context cancel statement is randomly selected and work is still available to be done
