Commit title: Tolerate syntax errors when generating Hack from notebooks
Commit body:
Summary:
## What

When generating Hack (.php) from a notebook (.ipynb), tolerate syntax errors in cells of the notebook.

**User experience before**: A syntax error would prevent a .php file from being generated from the notebook. The user would see a pretty obscure error message that didn't pinpoint the problem.

**User experience after**: We can generate Hack (.php) with syntax errors. Users will have to use standard tooling to fix the errors before landing their diff.

> Note that Bento side isn't implemented yet, so you can't actually see the difference in behavior.

## Background

https://fburl.com/source-controlled-notebooks-for-hack-project-2024

Syntax errors are likely when converting from notebook to Hack:
- We tolerate `=$x` syntax to print things in notebooks, but this isn't valid Hack
- We tolerate missing final semicolon in notebooks. iuc, this happens because we use the HHVM debugger under the hood and the debugger is a little tolerant in this area
- A notebook can consist of multiple cells: the user may have several "working" cells and some that can't run yet due to syntax errors.

## Why

Our standard tooling (language server) provides our best experience for working with syntax (red squiggles for errors, completions, some quickfixes). By leaning on this tooling, I believe we can provide a better experience.

## Further Considerations

I want to continue to disallow generating notebooks from invalid Hack. Here's why:
- Theoretically the Hack code won't be hand-edited (except to fix up syntax errors before landing), so it shouldn't have syntax errors: if it does, we should imo fail fast.
- The conversion Hack->notebook involves some delicate parsing. I don't really trust that we can always do something sensible with ill-formed code.
- We have some validation that we don't introduce syntax errors when round-tripping. I don't want to lose the safety we get from the validation.
