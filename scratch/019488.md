Commit title: Fix bug in `like_t` / `forward_like` -- do not strip `const`
Commit body:
Summary:
The C++23 spec of `forward_like` says:

> If `std::remove_reference_t<T>` is a const-qualified type, then the referenced type of the return type is `const std::remove_reference_t<U>`. Otherwise, the referenced type is `std::remove_reference_t<U>`.

Example showing `std::forward_like` doesn't strip an underlying `const`: https://godbolt.org/z/GxafMvbPs

Unfortunately, prior to this diff, `folly::like_t` and therefore `folly::forward_like` do strip the underlying `const`.

The `forward_like` change should be safe, and this bug shouldn't have caused any runtime UB -- both of these because `forward_like` uses `static_cast`, which ought to fail to compile when attempting to remove an underlying `const`.

For the `like_t` change, I manually audited existing callsites -- see test plan. After discussion with yfeldblum, `function_traits` was the only callsite where the old behavior of "fully clone the cvref category" made sense. So, for that use-case I introduced `copy_cvref_t`.

All other use-cases of `like_t` appeared to be fine with the new, C++23-aligned semantic of `like_t`.
