Summary:
# What?
With mutable python enabled, type-checks of `__iter__` fail if one of the fields in a structured type is of type map with a structured key.

Consider this example (abridged thrift file)
```
struct Baz {}

struct Foo {
    1: int32 some_int;
    1: Baz baz;
}
```

This will result in errors like below.

```
Inconsistent override [15]: `python_test.adapter.thrift_mutable_types.Foo.__iter__` overrides method defined in `_fbthrift_python_abstract_types.Foo` inconsistently. Returned type `_typing.Iterator[_typing.Tuple[str, _typing.Union[int, _typing.Mapping[_fbthrift_python_abstract_types._fbthrift_unadapted_Baz, str]]]`  is not a subtype of the overridden return `_typing.Iterator[_typing.Tuple[str, _typing.Union[int, _fbthrift_python_mutable_containers.MutableMapping[_fbthrift_python_mutable_types._fbthrift_unadapted_Baz, str]]]`.
```

The key part here is
```
_typing.Mapping[_fbthrift_python_abstract_types._fbthrift_unadapted_Baz, str]
```
in the base-class and
```
_fbthrift_python_mutable_containers.MutableMapping[_fbthrift_python_mutable_types._fbthrift_unadapted_Baz, str]
```
in the derived class, where the key to the map, which is of thrift type `Baz`, is invariant.

# What to do?
To unblock current work, remove `__iter__` until there is an implementation that eliminates this error.

Build fixtures with
```
buck2 run fbcode//thrift/compiler/test:build_fixtures
```

# What are the consequences?
Uses of iteration via the abstract type will result in a type-check error like below.

```
Incompatible parameter type [6]: In call `set.__init__`, for 1st positional argument, expected `Iterable[Variable[_T]]` but got `TestStructAbstract`
```

The workaround until the fix is to add a `pyre-fixme[6]` like below.
# pyre-fixme[6]: For 1st argument expected `Iterable[_T]` but got
`TestStructAbstract`.

Once again to reiterate, there are no run-time consequences of this change.

See the `test_iteration` test case in `abstract_types_test.py` in this diff for how this looks in code.
