Commit title: Split scope into Program & Global scope
Commit body:
Summary:
This diff changes the thrift identifier resolution implementation from a single global scope where each definition was available as `<program>.<definition>` to a hierarchical set of scopes where each program owns its local definitions.

## Scopes

`t_scope` has been split into `t_global_scope` & `program_scope`. The global scope object is shared between all programs & mainly functions to dispatch lookups to the relevant program, e.g.
for `foo.Bar` find any programs named `foo.thrift` & look for a `Bar` definition. It also provides a fallback to search through all defined programs for any unresolved identifiers.

The program scope contains the local definition for each program. Each program has access to a list of available scopes based on the includes. In case of name conflicts the current behavior is maintained, i.e. the last include (in order of parsing) to provide the definition wins. These available scopes now take aliasing into account.

## Fallback to global resolution

As there are currently many violations of the proposed scoping rules, there is a fallback to allow resolving otherwise unresolved identifiers on a global scope, e.g.
- Implicitly included types, i.e. a downstream program provides a definition, but that scope name isn't specified explicitly
- Unspecified scope, i.e. an external definition not specified by any scope is resolved to its global definition on a FCFS basis.

## Identifiers

Identifiers are always one of the following:
- `unscoped`: e.g. `Bar`
  - This is always a local definition
- `scoped`: e.g. `foo.Bar` or `Foo.Bar`
  - This is either a reference to a definition of `Bar` in a program called `foo.thrift`
  - Or an explicit reference to enum called `Foo` with a value `Bar` in the local scope
  - Or lastly, a reference to a local definition of `Bar` in case the local program's name matches `foo`
- Fully qualified enum value, e.g. `foo.Bar.Baz`
  - This always refers to an enum called `Bar` with a value `Baz` either in an included program `foo` or the local program if it is called `foo`

To help differentiate the various resolution scenarios, a `scope::identifier` class was added.

## Misc

As include resolution is done on the AST-level & does not need to outlive the AST itself, there's no reason to perform string allocation for each identifier. Instead all identifiers are based on `std::string_view`, significantly reducing the amount of allocations.
