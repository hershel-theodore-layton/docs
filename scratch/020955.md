Commit title: Add `lite_tuple::tuple` with good ctor/dtor ordering & better build speed
Commit body:
Summary:
This description is "the backstory", but the actual docs are in `tuple.h`.

 ---

For `async_closure` to behave as users would expect, I really needed a tuple type that had a specified construction & destruction order. Unfortunately, `std::tuple` behaves the **opposite** way between `libstdc++` and `libc++`.

The C++ standard left this order unspecified. [Issue 2528](https://cplusplus.github.io/LWG/issue2528) has been open since 2015 -- and possibly forevermore, since C++ is so hesitant to plan for ABI breaks.

So, I wrote a small `lite_tuple` mimic that serves my needs. It has 108 lines of code (minus comments and blanks).

This may be used elsewhere in `folly` as an implementation detail, but the docblock discusses why I have no definite plans to make it a public API.

Besides defined ordering, this has some speed benefits:
 - The compile + link speed for `:async_closure_test` dropped about 13% after I replaced all implementation-internal tuples with `lite_tuple`.
 - For types with nontrivial copy ctors -- since `lite_tuple::tuple` is an aggregate type,   we get prvalue semantics copy elision when these tuples are constructed with prvalues (while `std::tuple` perfect forwarding breaks that).
 - [`codeinred/tuplet`](https://github.com/codeinred/tuplet/) is another "aggregate type tuple" with a similar implementation. It claims in the "Benchmarks" section that compilers often emit faster code for `tuplet` over `std::tuple`. Caveats:
    * `tuplet` did some explicit implementation tuning for GCC vs clang, which I did not do (preferring brevity & clarity).
    * I didn't attempt actual A-B runtime benchmarking, so this benefit is just "potential".
