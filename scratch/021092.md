Commit title: demonstrate Union.fromValue bug risk
Commit body:
Summary:
Thrift-py3 uses field declaration order when iterating over fields, while thrift-python uses key (field id) sorted order.

As a result `Union.fromValue` can produce different results when migrating between thrift-py3 and thrift-python. This is only a risk if:
1. a `union` has non-monotonically increasing field ids. I.e., the declaration order doesn't match the id-sorted order.
2. If a field is out-of-order, then it's type is python equivalent to the type of another field with a lower field id.

Python equivalent means:
1. i64 <-> i32 <-> i16 (all python `int`)
2. float <-> double (all python `float`, which is equivalent to cpp `double`).
3. `cpp.Type` is usually ignored, but `cpp.Type{name = "folly::IOBuf"}` and `cpp.Type{name = "std::unique_ptr<folly::IOBuf>"}` are both translated to python `folly.IOBuf`.
4. Regular `binary` (python `bytes`) is not equivalent to `IOBuf`.
