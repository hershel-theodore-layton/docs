Commit title: Add initial support for processing SINK requests
Commit body:
Summary:
The main goal of this diff is to add Sink reply support to the ReplyState which is threaded through the code generation logic. Sink's are somewhat evil in that

1. They must return a single payload struct, not a stream
2. The async generator only runs, populating items, during the "send sink reply" flow.
3. The generator that runs, requires a returned final record, which is the final reply of the processing (i.e. the return value from the user code post-stream completed).

All this together, with the folly/tokio bridging logic to make sure executors aren't blocked anywhere, made this exceedingly evil. That being said it compiles?

Some design decisions made here are:
1. To use a single-item bounded channel for populating the sink stream. This means that C++ can't get "ahead" of the Rust processing logic by more than a single, undecoded item.
2. In order to not block the folly executor, we don't use the `blocking_send()` call from the tokio channel. We thread a folly promise along with the request to send, which async blocks both tokio waiting on the send to complete *AND* folly waiting on the send to complete, and trigger the promise on the other side. This "synchronizes" the two streaming logix.

Code generation will follow later.
