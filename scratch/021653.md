Commit title: Add module for accessing typedef's and enum's constructor functions
Commit body:
Summary:
Previously, the following Thrift code:

```
rust.NewType
typedef i64 Int64

typedef Int64 Int
```

would generate this pair of Rust definitions:

```lang=rust
pub struct Int64(pub i64);

pub type Int = Int64;
```

This is inadequate because it defines `Int64` in both the type namespace (`let _: Int64;`) and value namespace (`let _ = Int64(0);`) but only defines `Int` in the type namespace, making its usage in expression position like `Int(0)` or pattern position like `if let Int(0) = i` invalid.

Generating instead `pub use path::to::Int64 as Int` is a poor fix because of how rustdoc treats documentation on re-exports. The better thing to generate would be something like:

```lang=rust
/// docs go here
pub type Int = Int64;
#[doc(hidden)]
pub use path::to::constructor_for_Int64 as Int;
```

This diff adds logic for identifying which types need a value-namespace component, namely enums and newtypes and typedefs of either. It also adds a module from which the constructor functions can be re-exported in the value namespace by a followup diff.

This work is a prerequisite for solving the `rust.Type` problem mentioned in D71433487. The Rust Thrift implementation is too eager to jump through typedef definitions in certain contexts, losing information about type annotations that aren't on the very last type. But in order to not jump through typedef definitions when compiling a `const` or struct field's default value, it needs to be able to instantiate constants using the typedefs name rather than the inner type's name, which requires typedefs' constructor functions in the value namespace.
