## Implement [`__NeedsConcrete` checks](https://fburl.com/hack-needs-concrete)

**Definitions**:
- **`abstract`-safety**: we're abstract-safe if we prevent the runtime from attempting to call a constructor that doesn't exist, call an unimplemented abstract method, or access an unimplemented abstract constant.
- A **concrete class** is a class that is either non-abstract or is final+not-`__ConsistentConstruct`. The intuition behind this definition is "in a concrete class there are no unimplemented members".

**Invariant**: In a `__NeedsConcrete` method, we know that `static` points to a concrete class.

The checks introduced in this diff all follow from leveraging or enforcing the invariant to get more abstract safety:
 - preserve the invariant  (example) :
     - If method `Abs::m` is marked `__NeedsConcrete`, and `Abs` is an abstract method, then `Abs::m()` is not allowed
  - leverage the invariant (example):
      - In a `__NeedsConcrete` method, `static::abstract_method()` is allowed

## Follow-on work

- potentially improve error messages based on feedback
- be more restrictive about where __NeedsConcrete is allowed: the attribute doesn't make sense on constructors nor inside final classes
- adjust pre-exiting error messages to be more careful about how we use the terminology "concrete"–"non-abtract" may be better terminology in some cases where we currrently say "concrete"
- quickfix to add `__NeedsConcrete`
- roll-out: codemod, update the default to `--config needs_concrete=true` then remove the flag
- checking for class names and class pointers (separate+dependent proposal, to be controlled via `--config safe_abstract=true`)
