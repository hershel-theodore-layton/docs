Commit title: TransportPeeker: avoid use-after-free in dtor
Commit body:
Summary:
When using AsyncIoUringSocket as the underlying AsyncTransport, it is possible for TransportPeeker::transport_ to be freed before ~TransportPeeker() is called. The dtor will unconditionally access a freed transport_ and trigger a "pure virtual method called" abort without ASAN:
```
E0408 20:17:10.456899  5413 PeekingManager.h:210] peekSuccess failed, dropping connection: apache::thrift::transport::TTransportException: Channel is !good()
pure virtual method called
```
The stack trace leading up to the abort:
```
    frame #7: 0x00007f6cf4ea2ad3 libstdc++.so.6`__cxxabiv1::__cxa_pure_virtual() at pure.cc:50:18
    frame #8: 0x0000000020e8ac27 ucache`wangle::TransportPeeker::~TransportPeeker(this=0x00007f5fe3f118e0) at SocketPeeker.h:51
    frame #9: 0x0000000020e8abe1 ucache`non-virtual thunk to wangle::TransportPeeker::~TransportPeeker() [inlined] wangle::TransportPeeker::~TransportPeeker(this=0x00007f5fe3f118e0) at SocketPeeker.h:50
    frame #10: 0x0000000020e8abd9 ucache`non-virtual thunk to wangle::TransportPeeker::~TransportPeeker() at SocketPeeker.h:0
    frame #11: 0x00000000209508df ucache`wangle::TransportPeeker::readDataAvailable(unsigned long) [inlined] folly::DelayedDestructionBase::DestructorGuard::~DestructorGuard(this=<unavailable>) at DelayedDestructionBase.h:94
    frame #12: 0x00000000209508d1 ucache`wangle::TransportPeeker::readDataAvailable(this=<unavailable>, len=<unavailable>) at SocketPeeker.h:100
    frame #13: 0x000000000d92645d ucache`folly::AsyncIoUringSocket::ReadSqe::sendReadBuf(this=0x00007f5eee3457c0, buf=0x7f5fe77fac88, overflow=nullptr) at AsyncIoUringSocket.cpp:819
    frame #14: 0x000000000d922564 ucache`folly::AsyncIoUringSocket::ReadSqe::callback(this=0x00007f5eee3457c0, cqe=<unavailable>) at AsyncIoUringSocket.cpp:0
```
* TransportPeeker::readDataAvailable() calls TransportPeekingManager::peekSuccess().
* TransportPeekingManager::peekSuccess() prepares TransportPeeker and TransportPeekingManager for delayed destruction.
* Neither are destroyed just yet as DestructorGuards are held in TransportPeeker::readDataAvailable() and TransportPeekingManager::peekSuccess().
* TransportPeekingManager::socket_ is moved into a handler->handleConnection().
* An exception is thrown somewhere inside of handler->handleConnection() and the socket has been freed as a result.
* The exception is caught and logged. When TransportPeekingManager::peekSuccess() returns, TransportPeekingManager is destroyed via ~DestructorGuard().
* TransportPeeker::readDataAvailable() returns, and TransportPeeker starts to be destroyed in ~DestructorGuard().
  * At this point, TransportPeeker::transport_ is dangling.
* ~TransportPeeker unconditionally calls transport_.

To workaround this specific situation, set transport_ to nullptr _before_ calling TransportPeekingManager::peekSuccess(). The transport read callback has already been set to nullptr and ~TransportPeeker() does not need to do the same.
