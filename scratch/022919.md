Summary:
# Background

`operator<` is useful general (e.g., so that we can sort thrift structs), thus `operator<` is defined by default for all thrift structs (by comparing fields one-by-one).

How about custom types?

```
struct Foo {
  cpp.Type{template = "std::unordered_map"}
  1: map<i32, string> field;
}

struct Bar {
  1: Foo foo;
};
```

`std::unordered_map` does not have `operator<`, we can not compare `Foo::field` directly.

# Today's Behavior

Today's behavior depends on whether the structure (struct/union/exception) has a uri due to historical reasons (URI is a newly introduced feature, thus we bundled a bunch of other new features that are only enabled when URI exists).

If structure has no uri:

* It is only considered orderable if
  * All structure fields are orderable.
  * There are no set/map fields with custom types. (nested fields in another struct don't count).

If structure has uri:

* It is only considered orderable if
  * All structure fields are orderable.

(URI can be defined explicitly via `thrift.Uri`, or implicitly via `package` keyword).

If all fields in the structure are orderable, the structure itself will be considered orderable as well ([code](https://github.com/facebook/fbthrift/blob/v2025.05.05.00/thrift/compiler/generate/cpp/util.cc#L242-L325)).

We only define `operator<` for orderable structures ([code](https://github.com/facebook/fbthrift/blob/v2025.05.05.00/thrift/compiler/generate/templates/cpp2/module_types.cpp.mustache#L142-L149)). For custom types that has no `operator<`, such as `std::unordered_map`, we put the value into a sorted `std::vector<pair<K*, V*>>` for comparison ([code](https://github.com/facebook/fbthrift/blob/v2025.05.05.00/thrift/lib/cpp2/op/detail/Compare.h#L419-L437)).

Note that `operator<` is always declared (unless `cpp.noncomparable` annotation exists: [code](https://github.com/facebook/fbthrift/blob/v2025.05.05.00/thrift/compiler/generate/templates/cpp2/module_types.h.mustache#L305-L309)). The motivation is that users can implement their own `operator<` for custom types if needed without worrying about ODR violation.

In the example above,

* If `Foo` has no uri, we don't define `operator<` for Foo.
* If `Foo` has a uri, we define `operator<` for Foo.

How about `Bar`? In this case `Bar` has no custom types (Note `Foo` is not a custom type, it's a thrift structure), thus whether `Bar` is orderable solely depends on whether `Foo` is orderable, regardless of whether `Bar` has a uri or not.

# This Diff

The logic above coupled orderability and uri – they are two completely different concepts that should not be bundled together.

Another more concrete reason for de-coupling is that we can not rollout `package` easily without de-coupling – if we define `operator<` after adding `package`, it might conflict with user-defined ones and we have to fix that.

To de-couple them, we want to change the behavior so that if the structure has a non-structure field with custom type, adding uri should not make it orderable (or changing the orderability in any way).

However, we can't just drop defining `operator<` for existing code since that causes build failure for anyone to rely on it.

The Migration plan in this diff:

1. Create a new cpp2 option `disable_custom_type_ordering_if_structure_has_uri` which will stop treating custom types orderable even if the structure has a uri.
2. We define a new annotation `cpp.EnableCustomTypeOrdering` that makes non-nested set/map in the structure orderable.
   1. This doesn't make the structure itself orderable. A struct is still only orderable when all fields are orderable. (e.g., if there are nested set/map with custom types, the structure might still be non-orderable, in which case `cpp.EnableCustomTypeOrdering` is effectively no-op)
3. For all thrift structures in fbsource, if it is orderable today, but not orderable when `disable_custom_type_ordering_if_structure_has_uri` is enabled, add `cpp.EnableCustomTypeOrdering` to preserve the existing behavior.
4. Once we added `cpp.EnableCustomTypeOrdering` to all necessary places, enable `disable_custom_type_ordering_if_structure_has_uri` globally.
5. If there is no issue for a while, clean up the code and remove `disable_custom_type_ordering_if_structure_has_uri` .
