Commit title: Avoid expensive error merging when streaming errors from hh_distc
Commit body:
Summary:
D69985879 introduced accumulation of errors polled from hh_distc instead getting the final set from it at the very end to make sure that we don't get mismatch between streamed errors and the final result. Another potential approach would've been to just perform filtering on the final set of errors but if I understand correctly it wasn't done due to potential perf implications. There is a problem with current approach though caused by the need to merge errors while they're being accumulated since merging take linear time: https://www.internalfb.com/code/fbsource/[925735f623c8]/fbcode/hphp/hack/src/errors/errors.ml?lines=52. So what was happening is that whenever we were polling errors from hh_distc we were merging new errors with the old ones and when the list grew to hundred of thousand of warnings it resulted in the perf regression which was visible only with `hh --no-load` or potentially with large fanout changes. Interestingly enough calling ` hh --re --root . --show-warnings` directly wasn't affected by this regression which is hinting that the problem is on the hh side.

This diff gets rid error accumulation and performs filtering again when final set of errors from hh_distc is received to avoid the need of merging errors altogether.
By doing that `hh --no-load` is back to 15-20 minutes runtime compared to ~2 hours before these changes.
