## This diff
This diff adds support for streaming messages on the hphpd debugger client. It adds a `StreamStatus` flag to indicate whether more streaming messages may be sent, and changes the polling speed between the server and client.

### How the code works
```
enum class StreamStatus: uint8_t{
  NOT_STARTED,
  INITIALIZED,
  ONGOING,
  COMPLETED,
};
```
The `StreamStatus m_stream_status` flag describes whether the client should anticipate more streaming messages or stop waiting.

**Debugger Server (`debugger_proxy.cpp`):**
1. Before evaluation: `m_stream_status = INITIALIZED`
2. Before printing to stdout during evaluation:  `m_stream_status = ONGOING`
3. After evaluation and before sending final message to client: `m_stream_status = COMPLETED`

**Debugger Client (`debugger_client.cpp`):**
1. At initialization of class: `m_stream_status = NOT_STARTED`
2. In`DebuggerClient::eventLoop`:
i. Check if command is `KindOfEvalStream`.
ii. If so, update `m_stream_status` based on received message.  Calling `handleReply` then prints the output in the message.
iii. If  `m_stream_status == COMPLETED`, end the event loop.

### Why is the 100 ms necessary
The hphpd client currently doesn't really rely on message framing correctly. It just assumes that if poll(fds) says the file/socket is ready, exactly only one message is in the buffer, so
1) It resets the buffer after reading one message, so it ignores all of the latest messages read earlier. https://fburl.com/code/2l41j45t
2) The hphpd client expects only one message per poll, so it stalls out when there's messages in the buffer that have already been read from the socket (and no more messages are expected). https://fburl.com/code/b2bqwp3x

We can make streaming somewhat work without message framing or timing, but it's quite brittle since there's no way to determine whether the buffer contains a real message or not. "Fixing" issue #2 above isn't feasible without message framing either, since it makes the client read from the buffer even when there are no messages from the server. This makes the client think there's something wrong with the server (for good reason) and shut down.
