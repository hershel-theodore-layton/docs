Summary:
[Feature request and context](https://fb.workplace.com/groups/rust.language/permalink/1645795189463220/)

This diff creates a specific implementation for collections that contain a `u8` instead of implementing the `GetTType` trait for `u8` and relying on generics and trait bounds. This expands on already existing special case implementations for `u8`.

### Why no changes to deserialize.rs?
There probably will need to be. Right now there isn't a trait bound preventing it:
https://www.internalfb.com/code/fbsource/[221ce46a0a908e754a26369db769cfad206f6189]/fbcode/thrift/lib/rust/src/deserialize.rs?lines=299-305
but that will probably be added soon with D76188175. I'll add the `u8` specific implementations with that work if needed.

### Why remove `GetTType` from trait bounds on the collections?
This particular trait shouldn't impact the thrift type of the collection. For example, a `HashMap` will be a `TType::Map` regardless of the key or value within the `HashMap`

### Some alternatives explored
1) Implementing `GetTType` for `u8` and removing the `u8` specific implementations in serialize.rs in favor of the generic implementation. This breaks current code throughout our code base. Following through with this change would require a few different first party code changes throughout fbcode.

2) Adding a marker trait for everything but `u8` so we can maintain the `Vec<u8>` implementation of the GetTType trait. This required updating a bunch of mustache template files and some callsites within fbcode that directly use the `GetTType` trait for serializing objects. This was version one of this diff.

3) [Use unstable features](https://doc.rust-lang.org/beta/unstable-book/language-features/min-specialization.html). After internal discussions we decided not to opt into a potentially  unsound corner.

4) Use a crate that mimics this for stable rust. I couldn't find a good third party crate that didn't involve changing the `GetTType` trait away from const.
