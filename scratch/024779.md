Commit title: Add `strict_safe_alias_of_v` and `manual_safe_callable_t`
Commit body:
Summary:
In `folly/coro/safe/collect`, it is common for APIs to take callables, but we don't want those to assume that random stateful lambdas are safe, when they very often include unsafe captured refs.

In other words, when taking callables into async APIs, the current `lenient_safe_alias_of_v` (formerly just `safe_alias_of_v`) is too permissive.

Instead, I introduce `strict_safe_alias_of_v` which treats a type as `unsafe`, unless explicitly marked. This strict behavior is **recursive** for composite types. For example, `tuple<HasSafetyMark, LackSafetyMark>` is unsafe under the strict measurement.

To avoid excessive false-negatives, I also marked the following types as explicitly safe:
  - fundamental types
  - empty types
  - function pointer

Yes, I realize that globals are another avenue of unsafe aliasing, and that function pointers can theoretically point at dynamically generated code. But, both forms of unsafety are **far** out of scope for the simple heuristic that is `safe_alias`.

The game plan is to use `strict_safe_alias_of_v` to nudge users to `safe_bind`, which will be an `async_closure` like API for sync functions, whose primary job is to measure `safe_alias` of the stuff that it captures. The auto-measuring behavior of `safe_bind` should give a good balance between safety and usability.
