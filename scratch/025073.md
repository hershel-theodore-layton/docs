## Problem Statement

Performance benchmarking revealed significant inefficiencies in the squangle MySQL C++ client when fetching large blob data compared to the Go MySQL driver. The C++ implementation was 73.7% slower on average when retrieving 10MB blobs from the database.

## Performance Comparison

| Metric | Go MySQL Driver | C++ squangle::mysql_client | Performance Gap |
|--------|-----------------|---------------------------|-----------------|
| **Mean Latency** | 32.882ms | 57.115ms | **73.7% slower** |
| **P50 Latency** | 32.109ms | 50.814ms | **58.3% slower** |
| **P95 Latency** | 37.001ms | 71.601ms | **92.1% slower** |
| **P99 Latency** | 41.023ms | 197.245ms | **380.6% slower** |
| **Min Latency** | 27.019ms | 40.155ms | **48.6% slower** |
| **Max Latency** | 182.933ms | 218.926ms | **19.7% slower** |

## Root Cause Analysis

Performance profiling with `perf trace` revealed that the C++ client was performing excessive system calls in a tight loop (P1886678535):

```
epoll_ctl(ADD) → epoll_wait() → epoll_ctl(DEL) → read(5 bytes) → read(1524 bytes) → [repeat]
```

The inefficiency stems from the `mysql_fetch_row_nonblocking()` function only reading a single MySQL packet (typically ~1529 bytes) per iteration before yielding control back to the event loop. For large blob transfers, this results in thousands of unnecessary epoll operations and context switches.

## Solution

This diff introduces a socket readability check using `ioctl(SIOCINQ)` to determine if additional data is available in the socket buffer before yielding control to the event loop. The optimization:

1. **Adds `isSocketReadable()` function** that uses `ioctl(SIOCINQ)` to check buffered socket data
2. **Modifies the fetch loop** to continue processing when data is available rather than waiting for the next epoll event
3. **Maintains timeout handling** to prevent infinite loops

## Technical Implementation

The fix is minimal and surgical:
- Uses standard Linux `ioctl(SIOCINQ)` to check socket buffer status
- Only affects the fetch operation loop, preserving existing error handling and timeout logic
- No changes to the MySQL protocol implementation or connection management
- Maintains backward compatibility and existing API contracts

This optimization is particularly beneficial for workloads involving large result sets or blob data where the MySQL response spans multiple network packets.

## Event Loop Considerations and Safety Mechanism
----------------------------------------------

Since the MySQL client operates within an event loop environment, it's critical to avoid hogging the event loop for extended periods. To prevent this while still benefiting from the socket readability optimization, this diff introduces the `async_mysql_max_fetch_retries_on_socket_readable` flag.

**Flag Purpose:**

*   **Name:** `async_mysql_max_fetch_retries_on_socket_readable`
*   **Default Value:** 100
*   **Function:** Caps the number of consecutive fetch retries when the socket is readable

**Why This Flag is Necessary:** The socket readability check could potentially create a tight loop if data keeps arriving continuously. Since we're running in an event loop and must periodically return control to it, this flag ensures we don't monopolize the event loop indefinitely. After reaching the retry limit, the operation yields back to the event loop via `waitForActionable()`, allowing other operations to proceed.

**Behavior:**

*   When `slurp()` returns false (no more data to process) but the socket is still readable and we haven't timed out, the operation will continue up to the flag's limit
*   Once the limit is reached, the operation returns control to the event loop
*   This maintains the performance benefit for large data transfers while ensuring fair event loop scheduling

This approach strikes a balance between performance optimization and event loop responsiveness, preventing the client from becoming unresponsive while still dramatically reducing unnecessary epoll operations for large blob transfers.
