Commit title: Fix exhaustive switches
Commit body:
Summary:
https://www.internalfb.com/wiki/IOS_at_Meta/switch_statements_in_C_languages/

*Exhaustive Switches*, i.e. using `-Wswitch-enum` and `-Wswitch-default`, are the ideal default for all C language code at Meta.

This diff is part of the migration of *Instagram* to adopting *Exhaustive Switches* by default.  Currently only `-Wswitch-enum` is enabled for *Instagram* apps, but we want to add `-Wswitch-default` to prevent bugs from undefined/unpredicted behavior (which means adding these `default:` cases will NOT interfere with the compiler putting up an error when a new value is added to an enum, like we want).

We will follow the recommended solutions as outlined in https://www.internalfb.com/wiki/Apple_Build_Errors/Missing_switch_default_Label/

  1. **Fail Fast**: [the vast majority of cases] use an `abort()` to forcibly crash the app on unexpected values, `FB_SWITCH_UNEXPECTED_VALUE_ABORT()` for `fbobjc`, `folly::assume_unexpected()` for `folly`, `std::terminate()` or `abort()` or `assert(false)` for other `xplat` / `fbcode` code.  Always fail fast when the existing behavior would be unpredictable/undefined if you were to introduce `default: break;` -- in particular, if all `case` statements yield a `return`, you know you should fail fast.  Also use this if one of the other options do not fit.
  2. **Handle unexpected values (A)**: when there is minimal code after the `switch` that only the unhandled values would reach, pull it into the `default:`.  Sometimes, you\'ll have a minimal number of `case` statements that `break` to also reach that out-of-switch code, and you can move those cases to be above the `default:` case so they fall through to the default handling.
  3. **Handle unexpected values (B)**: when the code after the `switch` is safe for unhandled values but also needed for handled values (too much code or too much complexity to do #2), add a `default: break;` statement (usually with a `FB_SWITCH_UNAVAILABLE_VALUE_REPORT(type, value)`).
  4. **Handle unexpected values (C)**: when the enum type is from the platform itself (not our monorepo), and is an `NS_ENUM` type, we can make a judgement call if think the enum might expand and thus add a default handling behavior.  If there is a reasonable chance the platform could expand the enum in a future OS release, we can avoid crashing until we start building against the new SDK where the `-Wswitch-enum` will help us explicitly handle the new case.
  5. **Handle unexpected values (D)**: when the value being switched is coerced from an integer (coming from a dictionary or coersing a table view row into an enum), presume that it is more likely to switch on a value outside of the enum.  In this case, use add the the `default:` case with `FB_SWITCH_UNEXPECTED_VALUE_REPORT(type, value)` to introduce a Must Fix report but leave the default behavior as simply providing a `break;`.
  6. **Convert to *Flexible Switch* or to `if` checks**: on the rare occasion, it can be evident that we do not need an *exhaustive* switch and can use `FB_FLEXIBLE_SWITCH_BEGIN|END` or just use `if` checks.
