Commit title: replace manual reserve() calls with folly::grow_capacity_by() in Query string operations
Commit body:
Summary:
This change replaces manual `.reserve(size + extra)` calls with `folly::grow_capacity_by()` in MySQL query string building operations.

**Why `.reserve(size + extra)` is problematic:**

The issue with calling `.reserve(size + extra)` instead of using proper capacity growth is that it causes unnecessary allocations and copies during append operations. Here's why:

When you call `.reserve(current_size + extra)`, you're setting the capacity to exactly what you think you need right now. However, if subsequent append operations exceed this capacity, the string will need to reallocate and copy all existing data.

**Example scenario:**
```
// Bad approach - causes multiple reallocations
std::string result;
std::vector<std::string> parts = {"Hello", " ", "world", "!", " How", " are", " you?"};

for (const auto& part : parts) {
    result.reserve(result.size() + part.size());  // BAD: exact reservation
    result += part;  // May still cause reallocation if capacity was underestimated
}
```

In this example, each `.reserve()` call sets the capacity to exactly `current_size + part.size()`. But if there are rounding issues, memory fragmentation, or if the string implementation needs extra space for null terminators or alignment, the next append might still trigger a reallocation.

**What happens in the Query.cpp code:** The original code was doing exactly this pattern:
```
s->reserve(s->size() + d.getString().size() + 4); // Reserve exact amount
s->push_back('`');  // These operations might exceed reserved capacity
// ... more character appends
```

**Better approach with `folly::grow_capacity_by()`:**
```
folly::grow_capacity_by(*s, d.getString().size() + 4);  // Smart growth
```

`folly::grow_capacity_by()` uses exponential growth strategies and accounts for implementation details, ensuring that the container has sufficient capacity with fewer reallocations. It's designed to handle the common pattern of incremental growth more efficiently than manual reservation calculations.

This change eliminates the risk of unexpected reallocations during the character-by-character append operations that follow the capacity adjustment.
