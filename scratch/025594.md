Commit title: Fix pending task accounting in EDFThreadPoolExecutor
Commit body:
Summary:
`EDFThreadPoolExecutor` pending task accounting is incorrect in two ways:

- `numItems_` in `TaskQueue` is decremented *after* the popped task is ran, not *before*, which is inconsistent with the other `ThreadPoolExecutor` implementations. In fact, the `poolStats()` unit test was only instantiated on the other implementations. If instantiated on `EDFThreadPoolExecutor`, it fails.

- If a vector of tasks is added, that counts as 1, not as the number of tasks in the vector.

Both problems come from what appears to be an attempt at optimizing semaphore operations by accounting idle threads, but that is unnecessary since the semaphore implementations already do that (if there are no idle threads, the cost is comparable to an atomic increment/decrement), and furthermore it's not clear that the algorithm is correct.

The implementation can be simplified significantly by moving all the pending task accounting to the semaphore (as done in `CPUThreadPoolExecutor`), and by also copying the join handling from` CPUThreadPoolExecutor`.
