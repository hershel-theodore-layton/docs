Commit title: Allow calling static methods on `<<__Newable>>` T
Commit body:
Summary:
## What

**After**

When a reified `T` is `<<__Newable>>`, allow `new`ing it, but not calling static methods.

**Before**

When a reified `T` is `<<__Newable>>`, allow BOTH `new`ing it AND calling static methods.

## Why

Increases completeness:
- Adds completeness in a way that makes things easier for users in practice. See two posts linked in the attached task (T93870838). iirc there were other posts asking for this as well.

##  Safety argument

- If something is newable, then it must be non-abstract and non-abstract functions must have definitions for all methods.

## Implementation notes

I could have moved our checks for when-we-have-a-proof-that-static-methods-are-defined to reified_check.

Advantages:
- Arguably more consistent. In the existing code (unchanged), trying to `new` a non-newable generic produces a "new without newable" error in reified_check.

Disadvantages:

- I don't think the check for static methods being defined actually has much directly to do with reified generics
- Unlike the the situation with `new`, I don't want to nudge users to add `<<__Newable>>` *just* so they can access static methods. Newable is much stronger, and limits options elsewhere. Really, what I think we'd want here is `<<__Concrete>>`, where a "concrete" class is one that has no abstract methods. This would include even `abstract final` classes and be more concrete. `<<__Newable>>` could imply `<<__Concrete>>`. But that's for another day (https://fburl.com/safe_abstract_extended)
-  I suspect such an implementation would make the implementation messy and (tbh) is more work anyway that I want to put in for this side quest.
