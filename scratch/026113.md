## Context

We needed to update libheif from 1.19.1 to 1.20.1 to address a vulnerability (T227515321). When we did (D78889925), some tests got broken (T236724237), and the upgrade was reverted.

At first I thought that there was some bug introduced in libheif, but then I realized that Telephoto (which uses libheif too) is able to decode the images that had caused test failures:

```
buck run telephoto:tele -- -in /data/users/dzobnin/fbsource/fbcode/hphp/test/zend/good/ext/standard/tests/image/246x247.heic -out ~/test_image.png

BUILD SUCCEEDED - starting your binary
Graph has 1 outputs:
   0) Writing blob to /home/dzobnin/test_image.png

buck run telephoto:tele -- -in /data/users/dzobnin/fbsource/fbcode/hphp/test/zend/good/ext/standard/tests/image/246x247.avif -out ~/test_image.png

BUILD SUCCEEDED - starting your binary
Graph has 1 outputs:
   0) Writing blob to /home/dzobnin/test_image.png
```

This made me think it was not a library issue, but the way we work with it.

## Investigation

In Telephoto, there's [HeicCodec.cpp](https://fburl.com/code/lqpktzhu) that works with HEIC images using libheif. [HeicReader](https://fburl.com/code/9nk2qimk) class contains implementations of all required functions. When I compared them to what we have in ext_gd.cpp, I noticed that HeicReader's [waitForFileSize](https://fburl.com/code/1n1tsqcu) is much more sophisticated than ext_gd's. It actually checks if we can advance the cursor to the requested offset and returns different codes depending on the result of that check.

## This diff

Here I implement `heif_wait_for_file_size()` the same way we do in Telephoto: actually check if the requested position is beyond EOF and if so, return a proper status code.
