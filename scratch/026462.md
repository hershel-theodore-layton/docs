Summary:
We do actually rely on "promise-punning" today, as explained below. The assert in this diff is motivated by an ASAN failure I had to debug during development.

## How punning works today

 - `TaskWrapperPromise` wraps promise types by composition, not by inheritance.
 - `Task` expects to deal with `TaskPromise`, not a wrapped one -- and changing this is either rather annoying or prohibitive since it'd require type erasure and other mess.
 - Whenever a wrapped **inner** `TaskPromise` calls `coroutine_handle<...>::from_promise(*this)`, that is technically UB, since `this` is not the true promise pointer of the coro. For example, for a task with 2 outer wrappers, `this` points at `TaskPromiseWrapper{...}.promise_.promise_`.
 - Today, this UB works safely because the inner `promise_` is always at offset 0 in the promise wrapper, and there's nothing else in the wrapper layout.

## Broken punning UB -> ASAN failure

I wanted to add support for `TaskPromiseWrapper::getErrorHandle`. This adds a vtable to the wrapper, which breaks the happy coincidence above => the UB turns into ASAN failures.

## Solution

Today, `from_promise(*this)` is done in two places in `Task.h`:
 - `get_return_object()` -- covered by this diff explicitly, and quite annoying to make work without punning in general:
    * Another approach is promise type erasure for the handle within `Task`, and undoing it via `from_address` as appropriate. This would add complexity, but have a similar risk profile.
    * Wrapping the promise by inheritance is one possible approach, but it has a couple of serious issues (slicing the harder one to eliminate)
 - virtual final `getErrorHandle()` -- (1) we shouldn't get here without instantiating `get_return_object`, (2) I hope to land D82905093 to devirtualize it, which will incidentally plumb through the correct promise to safely form a handle without even potential UB.
