## Back-story, or ... the trouble with `folly::coro` cancellation

The C++ proposal [P1677](https://wg21.link/p1677), part of the design rationale of C++26 [std::execution P2300](https://wg21.link/p12300), argues that cancellation is serendipitous success, and should have a separate channel from "error handling". The crux of the arguments is that normal error handling should never interrupt the prompt release of resources by cancellation. Whereas, in `folly::coro` code, this class of bug is commonplace.

It is very easy to accidentally interrupt unwinding due to cancellation. Namely: `co_await co_awaitTry()` / `co_await_result()`, `catch (const std::exception&) {}`, or `catch (...) {}` all have this property.

### Why was throwing cancellation chosen in the first place?

Cancellation-as-exception does have some good historical justification. Without async RAII, it is impossible to correctly use `AsyncScope` -- or any other utility requiring async cleanup -- together with tools like `co_nothrow` that directly unwind a coroutine stack.

To be more specific, imagine a coro awaiting a child coro that might unwind immediately (due to `co_nothrow` + error, or "future `P1667` non-throwing cancellation"). Then, in order to use an async scope, or other background-execution idioms, the coro author **must** know to use `async_closure` RAII (a native async scope for this is WIP), or use the older, more dangerous `co_scope_exit`, to guarantee the cleanup of the async scope. Failure to do this with today's `AsyncScope` will cause a CHECK failure in `~AsyncScope` as the current coro unwinds.

### So, where are you going with this?

There will be several follow-up work-streams:

(1) Next: `co_await value_or_error(...)`, which implements `P1667`-like "semantics of unwinding in a prompt, uninterruptible way when the child is cancelled. For now, this will incur an RTTI test for `OperationCancelled`, 20-30ns. But, hot code already has plenty of solutions to avoid this.

(2) `safe_async_scope` will supersede `AsyncScope`, and make it reasonable to default to `co_await value_or_error()` in all new structured-concurrency code.

(3) `rich_exception_ptr` will enable `result` to check for cancellation in an RTTI-free way (at least on the happy path).

(4) `Try` can then be reimplemented in terms of `result`, making these RTTI-free cancellation checks available in coro code. This will immediately bring `value_or_error` close to perf parity with `value_or_error_or_stopped` aka `co_awaitTry`.

(5) With RTTI-free cancellation, we can introduce a new signal `co_yield co_cancelled_nothrow`, with `P1667` semantics. It is TBD whether `co_awaitTry` should catch it (like `value_or_error_or_stopped`), but it will definitely **not** be thrown by default, massively improving cancellation performance, and making try-catch-all safe to use again. Of course, upon exiting coro code (e.g. `blocking_wait` or future conversions), the cancellation signal can no longer unwind stacks automatically, so throwing might have to remain the backwards-compatibility story here. A more bold refactor might migrate all `blocking_wait` users to something returning `optional` with `nullopt` on cancellation -- or any other alternative for specifying the return-value-when-cancelled.

(6) Eventually, in the very long haul, we can rename `P1667`-cancellation in `folly` to "stopped" uniformly, to minimize confusion. However, first, many of the prior issues need to be untangled in existing code.
