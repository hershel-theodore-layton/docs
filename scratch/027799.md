## This Diff
* Establish new util class `RequestFanoutLimit` using `folly::ConcurrentHashMap` (see RFC) to track number of xbox each request recursively spawn.
* In xbox-server code:
    * Initialize the RequestFanoutLimit limiter during server start up
    * `->increment()` count for root request id *before* a job is queued
    * `->decrement()` count for root request id *after* job *finishes* running
    * `->clear()` the limiter upon server shutdown.

## [RFC] `folly::ConcurrentHashMap` vs. `folly::AtomicHashMap`:
I actually initially started with `folly::AtomicHashMap`, but during integration test found out that it does not reclaim the memory space even after the key is erased. https://fburl.com/code/g1ns3217

In our use case, this means we need spaces proportional to the number of ***TOTAL requests the served in the entire server lifecycle*** (despite only Cfg::Server::ThreadCount requests can run in parallel) - because memory cannot be freed or reclaimed by erase.

Following https://www.internalfb.com/wiki/Concurrency/#data-structures, I then used `folly::ConcurrentHashMap` instead which reclaims memory space upon erase. It is slightly less performant as compared to `AtomicHashMap` (lock per shard instead of lock per key), but this should be tweakable by configuring the number of shards. Please please comment any concerns.
