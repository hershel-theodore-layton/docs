Commit title: Add `has_unicode_error` flag to enable fast-path for unicode string map fields
Commit body:
Summary:
This diff enables a performance optimization for Python Thrift maps by detecting UTF-8 decoding errors during deserialization and setting a `has_unicode_error` flag when fallback to bytes occurs.

## Motivation

When deserializing Thrift maps with `string` keys/values in Python, the current implementation uses `FallibleString` which falls back to `bytes` when UTF-8 decoding fails. However, downstream validation code couldn't distinguish between maps with all-Unicode strings (which can skip validation) vs maps with some bytes (which need validation). This forced validation to run on all maps, even when unnecessary.

## Changes

1. **C++ Deserialization (TableBasedSerializerImpl.h)**:
   - Refactored map deserialization `Context` struct to use `MapFieldTypeInfo` as the first member (standard layout requirement)
   - This enables type information to be accessible in `ImmutableMapHandler` via the first-member casting trick

2. **Python Map Handlers (types.cpp)**:
   - Modified `ImmutableMapHandler::read()` and `consumeElem()` to detect when string keys/values fail UTF-8 decoding (falling back to bytes)
   - Set `has_unicode_error` attribute on the `ImmutableInternalMap` when any key or value is bytes instead of Unicode String

3. **Constructor Template (constructor.h)**:
   - Added similar Unicode error detection in `Constructor<map<KeyT, ValT>>` for C++ to Python conversion

## Impact

- Python code can now check `ImmutableInternalMap.has_unicode_error` to determine if lazy validation can be skipped.

## Performance Wins ##
The current diff shows **massive improvements in first-time iteration** for Maps containing strings:

`buck2 run fbcode//mode/opt fbcode//thrift/lib/python/benchmark:containers`

*   🔥 **Map<i32, string>**: First iteration is now **2.3 times faster** (was 0.038ms, now 0.016ms)
*   🔥 **Map<string, string>**: First iteration is now **2.5 times faster** (was 0.041ms, now 0.017ms)

Besides, based on the best result from five runs, we can see that there is no regression in deserialization for the JSON protocol.
