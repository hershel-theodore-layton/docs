Summary:
Got this crash trying to run our application in TSAN canary in tupperware: P2067453943

The root cause was that workerCount() and idleWorkerCount() were reading resourcePools_ without holding the mutex, while addResourcePool() was modifying the vector under mutex protection. The fix ensures both readers and writers acquire the same mutex.

Changes Made
Header file (ResourcePoolSet.h):

Added #include <atomic>
Changed bool locked_{false} to std::atomic<bool> locked_{false}
Implementation file (ResourcePoolSet.cpp) - Updated all usages of locked_:

Writers (inside lock guard, use relaxed ordering since mutex synchronizes):

setResourcePool(): locked_.load(std::memory_order_relaxed)
addResourcePool(): locked_.load(std::memory_order_relaxed)
The lock() method (use release semantics to publish writes):

locked_.store(true, std::memory_order_release) - ensures all prior writes to resourcePools_ are visible to readers
Readers (use acquire semantics to see published writes):

numQueued(), numInExecution(), numPendingDeque(): locked_.load(std::memory_order_acquire)
workerCount(), idleWorkerCount(): locked_.load(std::memory_order_acquire) - removed mutex acquisition since acquire semantics from locked_ are sufficient once lock() has been called
findResourcePool(), hasResourcePool(), resourcePool(), resourcePoolByPriority_deprecated(), empty(), stopAndJoin(), describe(): locked_.load(std::memory_order_acquire) for the conditional lock check
Fixed critical deadlock in calculatePriorityMapping():

Changed from calling hasResourcePool() to directly accessing resourcePools_ to avoid recursive mutex acquisition when called from lock()
