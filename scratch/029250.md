Commit title: Check HRR ECH acceptance before computing PSK binders
Commit body:
Summary:
When HelloRetryRequest happens, PSK binders must be computed over a transcript that includes ClientHello1, HelloRetryRequest (HRR), and a truncated ClientHello2. ([RFC8446 Section 4.2.11.2](https://datatracker.ietf.org/doc/html/rfc8446#section-4.2.11.2)).

Meanwhile, the server indicates acceptance of ECH by sending a HRR which includes an `encrypted_client_hello` extension. It sets the 8-byte `confirmation` field in said ECH extension to 0, computes a transcript using that, and uses that interim transcript to compute an 8-byte value to be placed in the `confirmation` field. ([ECH draft Section 7.2.1](https://www.ietf.org/archive/id/draft-ietf-tls-esni-11.html#name-sending-helloretryrequest-2))

As a result, the client must on one hand compute the PSK binders with a transcript that includes the actual received HRR, and on the other hand check the server's acceptance of ECH using a transcript where the HRR's ECH extension `confirmation` field is zeroed out. The appending of the actual HRR to the transcript was being deferred to allow for the latter, but this broke the former.

To fix this ergonomically in code, the ECH acceptance check is moved up earlier, so that the actual HRR can be added to the transcript for the addition of PSK binders.
