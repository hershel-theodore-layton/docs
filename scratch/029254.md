Commit body:
Summary:
`rich_error_base` and `rich_exception_ptr` have the notion of an "underlying error", which is the actual error as far as all the control-flow-affecting APIs are concerned, i.e. all of these use the underlying error:
 - `get_exception()` -- and therefore things like `get_rich_error_code()` also look at the underlying error
 - `to_exception_ptr_slow()`
 - `throw_exception()`
 - `operator==`
 -  (non-public for now) `exception_type()`

But, for the purposes of tracking exception provenance, we allow the underlying error to have a wrapper (a stack / linked list of wrappers actually), which are traversed and rendered when the exception or its `rich_ptr` is rendered.

 ---

The `get_outer_exception` API here gives access to that outermost wrapper that is the *actual* exception stored in this `rich_exception_ptr`. This is mostly useful for formatting & tests. Users would rarely need to use it, but it's not private per se because `result` / `non_value_result` don't make it very easy to get at the `rich_exception_ptr` in the first place.
