Summary:
## What

Undo a change where when I first joined the team I thought it was best to have one BUCK file and one dune file per directory.

## Why

It's annoying to update all the BUCK and dune files and they don't actually help us with modularity in this case. Also, code_actions_services as one "chunk" makes sense to me, everything here has roughly the same concerns.

## Considerations

> TLDR: doesn't matter, feel free to skip reading

My reason for making too many build files in my youth was that I thought we would have proper wrapped module support (see [`wrapped` stanza](https://dune.readthedocs.io/en/latest/reference/dune/library.html)) in BUCK and have implementation-hiding for better modularity. But that day is not nigh. I could figure it out, but it keeps slipping down my priority list and if we need the files back we can always have AI make them, they are mostly boilerplate.

Re the current change's effect on build speed: I couldn't detect one, because not much code is affected.

Re if we keep going like this and have fewer buck files as a whole, I think:
- effect on build speed would be very minor.  iuc most of our build time is spent linking against a mountain of Meta dependencies including giant CPP and Rust deps anyway. To
- Any effect (positive or negative) would likely be down to the particulars of the files and Buck targets involved.  To the best of my understanding, fewer BUCK files for the same number of OCaml files means:
    - more work for OCaml to figure out in which order to link modules together
    - but less work for the non-OCaml-specific linker, since one big library is probably easier to rearrange than many little ones
    - more work in some cases for the OCaml compiler when changing some things inside the larger build unit: a larger compilation unit will have to be re-built rather than linking against a library that doesn't need to change
