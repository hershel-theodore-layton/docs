Commit title: Simplified support for splitting by shape predicates
Commit body:
Summary:
## What

This diff (a) simplifies how shape types are split by shape predicates and (b) adds on support for optional fields and open shapes now that it's straightforward to do so.

The previous splitting approach is more precise (it's the same as what we do for tuples) but is very expensive due to combinatorial explosion of types stemming from how we split types. Shape type splitting was not turned on for this reason.

The new splitting approach is less powerful but simpler. It aims to identify cases where the type fully passes the predicate (left) or fully fails the predicate (right) and produces a span in all other cases instead of trying to breakdown the type into atomic parts that fall into different partitions.

`split_ty_by_shape` is the key function here.

## Why

We speculate that actually breaking down the shape is low-priority for our users. And it's better to move forward with this limited support so that users can use `is shape(...)` (or more precise types) to decompose case types.

## Notes

* supportdyn continues to be a pain
  * open shape hints are wrapped in supportdyn when being converted to a decl ty and the supportdyn is pumped into the type for unspecified fields; this requires special handling

* There's a notable comment in `negate_ak_null_type` for the workaround I placed to avoid a soundness issue

* This diff can be reverted/revisited if we want to consider improving splitting. For reference D60318530 and stacked were changes I worked on for trying to do this performantly.
