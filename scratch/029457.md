Commit title: make graph construction deterministic
Commit body:
Summary:
This diff makes the construction of our test selection graph deterministic. The high-level goal is that when passing `--find-my-tests-max-test-files`, we have always processed the same set of files upon reaching the limit.

Done by addressing sources of non-determinism:

- `FindRefsService.find_references` uses `MultiWorker` under the hood when processing more than 10 files.
- iteration of `Hash_set` and `Hashtbl`, which do not guarantee any ordering

As a further step, I'm also ensuring that the overall output of `hh --find-my-tests` is sorted by relevance (tests with smaller distance first). That's just a nice-to-have.

Implementation note:
- Now that we are doing more things in a sorted fashion, I'm trying to sort by file name/class name first whenever possible. The hope is that consecutively processing all nodes for the same class/file is better for caching.
- I'm deliberately defining my own `compare` functions in two places where a `[@deriving ord]` would do. But I don't like doing that in cases where I care about in which order fields are used for sorting, because then the order in which fields are defined in the record becomes load-bearing.
