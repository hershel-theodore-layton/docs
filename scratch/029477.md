Summary:
The job of `immortal_rich_error<MyErr, ctorArgs...>` is like so:

## Make `immortal_`, a constant-initialized `MyErr`

Well, actually, an `immortal_rich_error_storage<MyErr>` -- user rich error types are incomplete, only final `immortal_rich_error_storage` and `rich_error` can be instantiated.

To get unique static storage for the instance, the storage has to be keyed off `ctorArgs...`. For this reason, we pass `ctorArgs...` as template params, which forces them to be structural types. In C++23, which supports `static` variables in constexpr functions, some additional options exist, but we're not there yet.

## Make `storage_`, a constant-initialized `ptr_immortal_exception_storage`

This gives `rich_exception_ptr` type-erased access to `immortal_`.

## Make `ptr_` , make a constant-initialized `rich_exception_ptr`

This part is fairly cheap and very optimizable, so it'd be likely be fine to do it at runtime, but keeping it `constexpr` avails us of constant-evaluation UB-detection in tests, and makes `rich_exception_ptr` a viable error-handling tool for `constexpr` code.

Per my note on the preceding D89023196, we could introduce an alternate, runtime, construction method for immortals -- and that could then also support non-rich errors.
