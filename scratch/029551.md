Commit title: flow typing for if-package checks
Commit body:
Summary:
The `if (package foo)` typing checks were implemented by adding package `foo` to the `loaded_packages` set in the global typing `env` (typing_env_types.ml, line 51) for the duration of the "then" block of the if/then/else statement (see `with_packages` in typing_env.ml, line 727).  This approach is brittle and does not easily extend to eg. supporting `invariant(package ...)` statements as `invariant` is desugared into `if (! condition) { fatal }`.

This diff removes the global `loaded_packages` set and implements flow-typing for `if (package ...)` checks.

- the global `loaded_packages` is pushed inside the per-continuation environment (typing_per_cont_env.ml)
- in the per-continuation environment, every package can have four 3 states:
  - `Exists_in_deployment`: the package is guaranteed to exist in the deployment, as result of a successful `if (package)` or `RequirePackage` runtime check.  __Invariants__:
     - if A includes B and A has `Exists_in_deployment` status, then B has `Exists_in_deployment` status too;
     - if A includes B and B has `Unsatisfiable_package_constraints` status, then A has `Unsatisfiable_package_constraints` status.
  - `Not_exists_in_deployment`: the package is guaranteed to _not_ exist  in the deployment, as result of a failed `if (package)` runtime check;
  - `Unsatisfiable_package_constraints`:  the package has been both checked to exist and to not exist, continuation is dead-code.

__Remark__: the package the file belongs to, and all its included packages, can also be assumed to exist in the current deployment, but none of them is stored in the per-continuation environment.

The per-continuation environment algebra is implemented in typing_local_packages.ml.  The algebra is complicated by the fact that packages can include other packages; if A includes B and A is deployed, then B is deployed too.  This impacts the semantics of `add pkg status` to the  `loaded_packages` of a continuation:
- if the status of `pkg` is `Exists_in_deployment`, then the status of all the included packages of `pkg` is first checked:
  - if all of them are either assumed to already exists, or have no assumptions made, then `pkg` and all its included packages are added to the `loaded_packages` with status `Exists_in_deployment`;
  - if any of them as status `Not_exists_in_deployment` or `Unsatisfiable_package_constraints`, then the `pkg` is assumed to be `Unsatisfiable_in_deployment` and no other assumptions are made on its included packages.

- if the status of `pkg` is `Not_exists_in_deployment`, then the only mapping `pkg -> Not_exists_in_deployment` is added to `loaded_packages`, as no assumptions can be made about the packages included by `pkg`.

- whenever conflicting assumptions are made on a package, then the status of the package, and of _all_ the packages that include it, is set to `Unsatisfiable_package_constraints`
