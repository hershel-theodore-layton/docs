Commit title: Require or_unwind for non_value_result & stopped_result_t
Commit body:
Summary:
As of the preceding D89798848, these work:

```
co_await or_unwind(non_value_result{})
co_await or_unwind(stopped_result)
```

This is the heavily advertised idiom for short-circuiting, so it's expected that users will write that by default.

Thus, the old patterns become syntax sugar, rather than essentials:

```
co_await non_value_result{} // no longer works
co_await stopped_result // no longer works
```

There's nothing *terribly* wrong with these, but defining them does bring a few minor downsides:
 - If `fn()` returns `non_value_result`, then `co_await fn()` can locally look like async coro, which can be misleading.
 - The `co_await` is registered for these regardless of the ambient coroutine context, so they pollute the overload resolution set for `co_await` for all `folly` objects.
 - *(kind of bogus, since this is stated without benchmark proof)* The move ctor for `non_value_result` is not trivial (and can't really be), so it may be harder for the compiler to optimize these than the by-reference `or_unwind`.
 - They're not consistent either with `or_unwind` nor with `co_error` / `co_result`.

This decision is reversible -- tf we find that requiring `or_unwind` too frequently results in verbose code, it's simple to bring these back, and it's a simple search-and-replace (or cAST codemod) to abbreviate the existing usages.
