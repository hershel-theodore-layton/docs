__✅ `HH\autoload_path_to_*` Functions Are Purity-Safe__

The implementations are purity-safe with one technical caveat explained below.

__Call Chain Analysis__
```
HHVM_FUNCTION(autoload_path_to_types, const String& path)
  └── autoloadMap().getFileTypes(path)
        └── AutoloadHandler::s_instance->getAutoloadMap()  // Static singleton access
              └── [polymorphic dispatch to one of:]
                    ├── RepoAutoloadMap::getFileTypes()  // Repo-authoritative mode
                    │     └── RepoFile::findUnitSymbols()  // Static lookup
                    │
                    └── FactsStore::getFileTypes()  // Facts/native autoload mode
                          └── SymbolMap::getFileTypes()
                                └── getPathSymbols<SymKind::Type>()
                                      └── readOrUpdate(...)
```

__Implementation Details__
|Component|Behavior|Purity Status|
|autoloadMap()|Returns reference to static autoload map singleton|✅ Pure (read-only access to global state)|
|RepoAutoloadMap::getFileTypes()|Lookups in pre-built static symbol tables|✅ Pure (deterministic read-only)|
|SymbolMap::getFileTypes()|Reads from in-memory cache + SQLite DB|⚠️ See caveat below|
|readOrUpdate()|Reader-writer lock pattern with lazy population|⚠️ See caveat below|

__⚠️ Technical Caveat: Lazy Cache Population__
The `SymbolMap::getPathSymbols()` method uses a `readOrUpdate()` pattern:
```
// From symbol-map.cpp:1577-1602
template <typename Ret, typename ReadFn, typename GetFromDBFn, typename WriteFn>
Ret SymbolMap::readOrUpdate(ReadFn readFn, GetFromDBFn getFromDBFn, WriteFn writeFn) {
  {
    // Try reading with only a reader lock.
    auto rlock = m_syncedData.rlock();
    auto readOnlyData = readFn(*rlock);
    if (readOnlyData) {
      return *readOnlyData;          // ✅ Pure path: just read from cache
    }
  }
  // Cache miss: fetch from DB and update cache
  auto dataFromDB = getFromDBFn(getDB());  // Read from SQLite
  return m_syncedData.withULockPtr([&](auto ulock) {
    // ...
    auto wlock = ulock.moveFromUpgradeToWrite();
    return writeFn(*wlock, std::move(dataFromDB));  // ⚠️ Writes to cache
  });
}
```
This writes to an internal cache on cache miss. However, this is semantically pure because:

1. Deterministic Output: The function always returns the same result for the same input
2. Unobservable Side Effects: The cache population is an internal optimization detail that doesn't affect program behavior
3. Thread-Safe: Uses proper locking (no data races)
Idempotent: Repeated calls produce identical results

And the `HH\Facts\path_to_*` functions (already marked pure in hhi) use exactly the same implementation.

This diff is making pure the Hack definitions in build.
