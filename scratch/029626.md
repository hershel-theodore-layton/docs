# AsyncSocket io_uring

Currently, the only way to use io_uring for network I/O is to use `AsyncIoUringSocket`. Using a different socket type has several issues:

* Much of the implementation logic is duplicated.
* Code assumes `AsyncSocket` and...
  * Rely on its implementation details. Several Ucache issues with `AsyncIoUringSocket` were caused by subtle differences in implementation.
  * Using `AsyncIoUringSocket` means changing the callsites. Many places assume `AsyncSockets`.
  * Some callsites (e.g. peekers) can't use `AsyncIoUringSocket` and there's currently an awkward async API to use io_uring in `AsyncSocket`; see `ReadMode::ReadZC`.

Make `AsyncSocket` work with `IoUringBackend` natively. The main design goal is identical user facing behaviour.

# Connect

Add a new bool flag `useIoUring_`. Always disabled for now.

`AsyncSocket` issues a non-blocking `connect()` syscall immediately and optimistically transitions to an ESTABLISHED state when using TFO. **Intentionally call `connect()` even with io_uring** rather than issuing an io_uring connect request because there are tests and possibly services that assume this behaviour. When using io_uring connect requests, the EVB must loop at least once after issuing the request.

If `connect()` returns EINPROGRESS, arm a poll with POLLOUT on the sockfd in `IoUringConnectHandle`. When this request completes, check for success via `handleConnect()`, same as the epoll path.

This design can be revisited in the future if needed. It is trivial to make `IoUringConnectHandle` issue connect directly.

## Socket Callbacks

`IoUringConnectCallback` provides a defined API for the handle to callback into an `AsyncSocket` parent. All handles will use something similar.

## Lifetime

`AsyncSocket` owns `IoUringConnectHandle` under normal situations. When the request is cancelled, ownership is transferred from `AsyncSocket` to `IoUringBackend`, which will delete `IoUringConnectHandle` in the cancellation callback.
