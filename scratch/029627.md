# AsyncSocket io_uring

Currently, the only way to use io_uring for network I/O is to use `AsyncIoUringSocket`. Using a different socket type has several issues:

* Much of the implementation logic is duplicated.
* Code assumes `AsyncSocket` and...
  * Rely on its implementation details. Several Ucache issues with `AsyncIoUringSocket` were caused by subtle differences in implementation.
  * Using `AsyncIoUringSocket` means changing the callsites. Many places assume `AsyncSockets`.
  * Some callsites (e.g. peekers) can't use `AsyncIoUringSocket` and there's currently an awkward async API to use io_uring in `AsyncSocket`; see `ReadMode::ReadZC`.

Make `AsyncSocket` work with `IoUringBackend` natively. The main design goal is identical user facing behaviour.

# Design

## IoUringSendHandle

Maintains a queue of requests `SendRequest`, similar to how AsyncSocket maintains `WriteRequest`.

## SendRequest

Each `SendRequest` is self-contained with its own `WriteCallback`, independent of others. This is different to read/recv where there is a single shared `ReadCallback`.

`SendRequest` is logically an io_uring sendmsg request. Once submitted, one or more completions will be issued, until either all the data has been sent, or an error is received. In the completion callback, update the handle and the socket on the state of the send (partial, complete, or error).

The main entrypoint is `IoUringSendHandle::write()`, which will allocate a `SendRequest`, and either issue the request if there are no pending writes, or add it to the back of the queue. **There is only ever at most 1 send request inflight** at any one time.

The request object is allocated with a trailing flexible array for the variable length iovec array.

## Immediate Write

Like `connect()`, `AsyncSocket` will attempt a non-blocking write immediately upon calling `writeImpl()`. Tests (and likely services) assume this behaviour. Preserve it even when using io_uring.

The overall logic is the same with io_uring: attempt an immediate inline non-blocking sendmsg(). Whatever that can get written gets written. If it is fully written - great. Anything remaining gets turned into an io_uring sendmsg request.

## onReleaseIOBuf()

The source IOBufs for the send might be too special to be freed via the IOBuf freeFn, and need to be freed via `WriteCallback::releaseIOBufCallback`.

## Failures

`IoUringSendHandle::failWrite()` and `IoUringSendHandle::failAllWrites()` are similar to their `AsyncSocket` equivalents. They are called from `AsyncSocket` to ensure that cleanup order is identical.

There was a bug with `AsyncFizzClients` using `AsyncIoUringSocket` as the transport, caused by slightly different cleanup ordering.

## Event Updates

Unlike `ReadCallbacks` and `setReadCB()`, it is **not possible** for callers to disable writes. Writes are only disabled when all sends are complete or when the socket is erroring out during `shutdownWriteNow()`.

`IoUringSendHandle::update()` simply updates `sendEnabled_` which gates future send request submissions. If the socket is closing/erroring out, the head request that is inflight would have been cancelled already.

## sendPartial()/sendDone()

Extract `AsyncSocket` logic for partial/complete sends into separate functions. `IoUringSendHandle` will call into these functions to ensure identical handling.

## hasPendingWrites()

Can't only check `writeReqHead_ == nullptr` to determine no pending writes. Also check requests in `IoUringSendHandle`.

## Socket Callbacks

`IoUringSendCallbacks` provides a defined API for the handle to callback into an `AsyncSocket` parent. All handles will use something similar.
