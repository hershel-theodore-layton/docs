# AsyncSocket io_uring

Currently, the only way to use io_uring for network I/O is to use `AsyncIoUringSocket`. Using a different socket type has several issues:

* Much of the implementation logic is duplicated.
* Code assumes `AsyncSocket` and...
  * Rely on its implementation details. Several Ucache issues with `AsyncIoUringSocket` were caused by subtle differences in implementation.
  * Using `AsyncIoUringSocket` means changing the callsites. Many places assume `AsyncSockets`.
  * Some callsites (e.g. peekers) can't use `AsyncIoUringSocket` and there's currently an awkward async API to use io_uring in `AsyncSocket`; see `ReadMode::ReadZC`.

Make `AsyncSocket` work with `IoUringBackend` natively. The main design goal is identical user facing behaviour.

# Design

## IoUringRecvHandle

Maintains a single `RecvRequest`, always trying to keep one issued.

## RecvRequest

There is a single `RecvRequest` in use, independent of which ReadCallback is installed at each moment in time.

This design is more opinionated than `AsyncIoUringSocket`'s `ReadSqe`. We **require** the use of buffer pools, either provided buffers or zero copy receive.

In the happy case, a long-lived ReadCallback is installed, and a multishot recv/recvzc continues to issue completions without needing any resubmits. This is true for the Thrift Parser ReadCallback case, for Thrift clients/servers.

In the unlikely event of buffers running out, there is a fallback path that allocates a buffer and issues a recv request.

## ReadBufferAvailable()

`AsyncSocket` reads data out into ReadCallback in three:

1. `getReadBuffer()` - Have the callback allocate a buffer to receive data into.
2. Issue recv syscall.
3. `readDataAvailable()` - Notify the callback that data is in the buffer allocated earlier.

With io_uring multishot requests, data is already in a pre-registered buffer and is delivered without copying via `readBufferAvailable()`. ReadCallbacks **must** implement this API.

## Small Reads

Some ReadCallbacks are intended to only **peek** a small number of bytes out of a socket, i.e. `SocketPeeker` and derived types. This is achieved by returning a tiny buffer via `getReadBuffer()`.

These callbacks **always** resets the ReadCallback recursively in its own callback. Require these ReadCallbacks to override `maxBufferSize()` to match the buffer size allocated in `getReadBuffer()`.

For these ReadCallbacks, issue a normal recv rather than multishot. When handling pre-receive data, go through the normal `handleRead()` path and do a copy.

## Event Updates

Unlike sends, callers **can** explicitly turn reads on/off, by setting ReadCallback.

With epoll and readiness execution model, if there is no ReadCallback installed, the socket can opt to *not* issue recv/recvmsg syscalls.

With io_uring and multishot recv requests, there are two options:

1. Cancel the inflight multishot recv request, and when a valid ReadCallback is installed, resubmit.
2. Keep the request inflight, read data into a queue.

Opt for option 2, knowing that ReadCallbacks are generally set to nullptr briefly in between valid callbacks. For Thrift especially, the Parser ReadCallback remains installed for the duration of a normal, healthy channel.

Some services i.e. Proxygen do NOT do this, and toggle ReadCallbacks rapidly. We can revisit this in the future.

## recvEOF()/recvErr()

Extract `AsyncSocket` logic for read errors/EOF into separate functions. Then, both the epoll + io_uring paths will call the same code, ensuring identical behaviour.

## Socket Callbacks

`IoUringRecvCallback` provides a defined API for the handle to callback into an `AsyncSocket` parent. All handles will use something similar.
