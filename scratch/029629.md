# AsyncSocket io_uring

Currently, the only way to use io_uring for network I/O is to use `AsyncIoUringSocket`. Using a different socket type has several issues:

* Much of the implementation logic is duplicated.
* Code assumes `AsyncSocket` and...
  * Rely on its implementation details. Several Ucache issues with `AsyncIoUringSocket` were caused by subtle differences in implementation.
  * Using `AsyncIoUringSocket` means changing the callsites. Many places assume `AsyncSockets`.
  * Some callsites (e.g. peekers) can't use `AsyncIoUringSocket` and there's currently an awkward async API to use io_uring in `AsyncSocket`; see `ReadMode::ReadZC`.

Make `AsyncSocket` work with `IoUringBackend` natively. The main design goal is identical user facing behaviour.

# Motivation

Since io_uring uses a completion based model, when a socket is detached from an EVB, there could be inflight requests that **must** complete on the old EVB.

# Design

There are three cases when detaching:
1. There are no requests. Trivial.
2. There are requests, and the head request is not inflight. Also trivial.
3. There are requests, and the head request **is in flight**.

This inflight request must complete on the old EVB, and we do not want to issue any new requests until it is done. From a high level, use a promise/future pair to:
* Signal completion of the inflight request on the *old* EVB
* Gate request submission on the *new* EVB

Upon detach, create a promise/future pair. Store the promise in a lambda function that will be fulfilled when the request completes on the old EVB with the result `cqe->res`. The old handle is kept around, and its lifetime is tied to the inflight request.

When attached, create a new handle *from* the old handle. Reconstruct the request queue, and clone the head request. This cloned request maintains the inflight state, and if true, prevents submissions.

The key point when attaching is chaining a continuation onto the future that runs in the **new EVB**. This continuation extracts the result from the old request, and feeds it into the callback of the new, cloned request.

## Detach Chains

If the socket is detached multiple times, before the 1st request completes, the future chain ensures that the result is delivered to the final attached EVB.
