# AsyncSocket io_uring

Currently, the only way to use io_uring for network I/O is to use `AsyncIoUringSocket`. Using a different socket type has several issues:

* Much of the implementation logic is duplicated.
* Code assumes `AsyncSocket` and...
  * Rely on its implementation details. Several Ucache issues with `AsyncIoUringSocket` were caused by subtle differences in implementation.
  * Using `AsyncIoUringSocket` means changing the callsites. Many places assume `AsyncSockets`.
  * Some callsites (e.g. peekers) can't use `AsyncIoUringSocket` and there's currently an awkward async API to use io_uring in `AsyncSocket`; see `ReadMode::ReadZC`.

Make `AsyncSocket` work with `IoUringBackend` natively. The main design goal is identical user facing behaviour.

# Motivation

Since io_uring uses a completion based model, when a socket is detached from an EVB, there could be inflight requests that **must** complete on the old EVB.

# Design

There are two cases when detaching:
1. The read request is not inflight. Trivial.
2. The read request is inflight.

This inflight request must be cancelled and the pending read must be handled on the old EVB. When reattached onto a new EVB, the new read request must not be submitted until it is safe to do so, when the old pending read is done.

Similar to sends, recvs also use a promise/future pair. But it is more complex since data must be chained and moved, not just a result code.

## Detach

Upon detach, if there is an inflight request (likely), **create** a `DetachedReadCallback` (DRC) that replaces the caller provided `ReadCallback` and **cancel** the request.

This means there will be one (or more, if multishot) completions calling `DetachedReadCallback::recvSuccess()`, followed by a final `recvEOF()` or `recvErr()`.

Any data received via `recvSuccess()` will be appended to an IOBuf chain, and the final `recvEOF()`/`recvErr()` will fulfill the promise with the data chain. All of this happens on the previous EVB that the socket detached from.

## Attach

When attached to a new EVB, `clone()` is called to create a new handle from the previous handle that contains the **future** that will be fulfilled with the pending read data. When the future is fulfilled, `processPendingRead()` queues the pending data and resumes the read on the *current* handle, which is on the *new EVB*.

The invariant is that while there is a pending read there cannot be any submissions on the new handle/EVB.

## Detach Chains

The pending read futures are chained together in case of multiple detach/attach cycles. This is very much an edge case that I do not expect to ever realistically happen.

`IoUringRecvHandle::detachEventBase()` will chain existing pending reads (from previous EVBs) to the *current* pending read.

The invariant is that only the final continuation (from the last `IoUringRecvHandle::setPendingRead()`) will call `processPendingRead()`. Guarantee this by:

* Check for `backend` pointer, it is nullptr if detached. Only the last handle will have a valid pointer.
* Hold a guard on the old handles to ensure checking `backend` is safe.
* `processPendingRead()` also checks for `backend` pointer, since it is scheduled later. The socket may be detached again.

## Queued Data

Always deliver the queued data first in both `processPendingRead()` and `AsyncSocket::checkForImmediateRead()`.
