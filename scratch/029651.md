Commit title: CommutativeWrapperAwaitable::co_withCancellation should not rewrap as rref
Commit body:
Summary:
AFAIK, the addition of `remove_reference_t` here doesn't affect any existing wrapper awaitables.

It showed in a wrapper I was adding up-stack.

Deducing `Result` as an rvalue reference caused a problem because:
- The default `co_withCancellation` for non-must-use-immediately types returns `Awaitable&&` in order to support the immovable awaitable `Baton`. This is unfortunate, but a fix for another time.
- The wrapper then selects the `co_withCancellation` overload for a non-must-use-immediately type, and creates `Derived<Awaitable&&>`.
- In the case of my wrapper, it cannot deal with its template param being a ref, so this broke. In any case, the idea of returning `Derived<Awaitable&&>` doesn't really make much sense.

Aside: If `Baton` were wrappable, this change could cause problems, but it's not, and if we were to make it wrappable, the right thing to do would be to give it a member returning a must-use-immediately awaitable, rather than await the baton itself. This would simplify a lot of the folly::coro code, so I'm reiterating this in the comments.
