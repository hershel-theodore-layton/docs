Commit title: Make FutureAwaiter's await_ready and await_suspend noexcept
Commit body:
Summary:
Folly's coroutine library provides "value-only" await wrappers that capture exceptions from `await_resume()` instead of throwing them:

```cpp
int val = co_await task();  // may throw

// Value-only await - captures errors in result type
result<int> res = co_await value_or_error(task());  // should never throw
if (res.has_value()) { ... } else { handle(res.error()); }
```

To guarantee no-throw, value-only wrappers need `await_ready` and `await_suspend` to be noexcept.  The upcoming `ValueOnlyAwaiterBase` mixin will enforces this via `static_assert`.  However, `FutureAwaiter`'s methods are currently not marked noexcept, even though the throwing scenarios are either:

1. Already caught by a prior noexcept function (`co_viaIfAsync`)
2. Can be safely caught and stored in `result_`.

This change eliminates the risk of `FutureAwaiter` throwing when used with value-only wrappers.

## Analysis of throwing scenarios

### `await_ready`

```cpp
bool await_ready() {
  if (future_.isReady()) {           // calls getCore().hasResult()
    result_ = std::move(future_.result());  // calls getCore()
    return true;
  }
  return false;
}
```

`getCore()` throws `FutureInvalid` if `core_` is null.

**However, `await_ready` is only reachable after `co_viaIfAsync` succeeds.**

Looking at line 1873 of Future.h:

```cpp
friend Future<T> co_viaIfAsync(
    folly::Executor::KeepAlive<> executor, Future<T>&& future) noexcept {
  return std::move(future).via(std::move(executor));
}
```

The rvalue `via()` method (line 911 of Future-inl.h) calls:
- `this->getExecutor()` - which calls `getCore()` - throws if invalid
- `this->setExecutor(...)` - which calls `getCore()` - throws if invalid

Since `co_viaIfAsync` is `noexcept`, an invalid future causes **termination**, not an exception that propagates to `await_ready`.

**Conclusion:** `await_ready` can safely be marked `noexcept`.

### `await_suspend`

```cpp
void await_suspend(coro::coroutine_handle<> h) {
  auto future = std::move(future_);
  future.setCallback_(...);  // can throw FutureAlreadyContinued
}
```

`setCallback_` calls `throwIfContinued()`:
```cpp
void FutureBase<T>::throwIfContinued() const {
  if (!core_ || core_->hasCallback()) {
    throw_exception<FutureAlreadyContinued>();
  }
}
```

This can throw if:
1. `core_` is null - **Cannot happen** (same reasoning as await_ready)
2. `core_->hasCallback()` is true - **Can happen** when a Future already had a callback attached via lvalue `via()` before being awaited

The lvalue `via()` attaches a callback via `thenImplementation` -> `setCallback_`. If you then try to await the original future, the callback check fails.

**dbg vs opt behavior:**

In `Core::setExecutor()`:
```cpp
void setExecutor(KeepAliveOrDeferred&& x) {
  DCHECK(
      state_ != State::OnlyCallback &&
      state_ != State::OnlyCallbackAllowInline);
  executor_ = std::move(x);
}
```

- **Debug builds**: The DCHECK fires inside `co_viaIfAsync` -> `via()` -> `setExecutor()`. Since `co_viaIfAsync` is noexcept, the program terminates.

- **Opt builds**: The DCHECK is a no-op. `co_viaIfAsync` succeeds. Then `await_suspend` calls `setCallback_` -> `throwIfContinued()` -> throws `FutureAlreadyContinued`.

**Conclusion:** `await_suspend` can be made noexcept by catching the exception and storing it in `result_`. Return type changes to `bool` with `false` indicating the coroutine should resume immediately (since we have an error).
