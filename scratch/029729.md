Commit title: Fix handling of contexts with FuncFamilies in non-distributed HHBBC
Commit body:
Summary:
There's two ways to look up a return type in HHBBC. The first does not
provide a context. In that case, we simply call unctx() to drop any
contextual information from the type. The second case we do provide a
context. In that case, we pass the type through
context_sensitive_return_type() to possibly further refine the type.

If we source the return type from a func-family, the same is done for
each func-family member. However, there's a bug here. Func-families
cache their results, and use the same cache in both cases. Therefore,
if you call the second version first, it will cache the type
containing the contextual information. Then if you call the first
version, it will simply return the contextual type. It assumes that
unctx() has already been called on each func-family member, so it is
simply returned. Therefore, the contextual type "leaks" out to where
the context doesn't apply. This can result in nonsense, in particular,
it can cause Bottoms where the current context isn't compatible with
the context in the return type.

We still want to use the same cache for both. Therefore, calculate the
func-family type in the same way in both cases. The difference is now
the first version applies unctx() on the type after the cache lookup,
while the second version uses
context_sensitive_return_type(). Essentially, the cached type is
always the contextual one.

While doing this, I realized some of the context handling in
distributed HHBBC was sub-optimal. It was correct, but applied unctx()
too much and thus dropped context in places where it could be
useful. The second case delegated to the first. Improve the types by
having the second case use it's own logic, preventing unctx() being
called too early.
