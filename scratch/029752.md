## What

- Fix bug in our language server's implementation of formatting, where we delete lines at the top of the file (bug T252565225)
- Prevent future regressions:
    - ci_hint for better test selection
    - better test coverage in ide_format tests and clearly distinguish the three cases that matter for newline formatting

## How we fix the regression

Update the condition
`if List.is_empty new_src_novel_lines && range_end_line < List.length old_src_lines then` delete_lines else replace_lines

The comparison should be against old_src_lines because range_end_line is computed from the old source's line indices. The comparison happened to work for certain cases but not others

## How we prevent future regressions

- Add more code coverage to the easy-to-maintain hh_single_ide_format tests
- Update test selection in our BUCK files (ci_hint) to make sure both IDE integration tests and hh_single_ide_format tests run on changes.

## Long Context: Feel free to skip

Our IDE support for Hack shells out to hackfmt and converts hackfmt patches into Language Server Protocol Edits.

For some reason, I find it very hard to reason about this sparse and supposedly easy logic, because edits with empty ranges can delete lines.

Pesky newlines can be buggy in three places:
- Top of file
- Bottom of file
- Neither top nor bottom

Some twisted history of me misundersting this code:
- (top of file +middle) We had an issue where extra newlines would be deleted: repro in D60978552 . The fix covered intentional extra newlines in the middle and top of the file but, unfortunately, did not correctly handle newlines at the end of the file.
    - Fixed in D60978552. Key logic is:
        - `if List.is_empty new_src_novel_lines` then delete_lines else replace_lines
- (end of file)
    - Our colleagues found a new bug introduced by the previous fix
    - They kindly fixed the bug in D88329959:
        - `if List.is_empty new_src_novel_lines && range_end_line < List.length new_src_lines then` delete_lines else replace_lines
    - The fix above introduced a new bug where we delete too many lines at the *end* of the file
- (top lines again)
    - The Slack fix for end of file (D88329959) broke top-of-file
    - We didn't see the breakage right away because:
        - The LSP-integration-tested and our test selection was bad (fixed in this diff)
        - The previous newlines fixes were not tested by hh_single_ide_format tests, which are easier to read and edit than the LSP integration tests
