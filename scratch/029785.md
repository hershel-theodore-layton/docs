Summary:
## What

### Internal API changes:
- Replace the ambiguous errors.mli API with functions that are clearer about whether they deal with errors, or errors+warnings:
   - `has_errors`: true when there are actual errors (ignores warnings)
   - `has_no_errors`: true when there are no actual errors (ignores warnings)
   - `has_no_errors_or_warnings`
- Rename the `has_no_errors` function (takes a callback) to `try_no_errors` to avoid a naming conflict with `has_no_errors`
    - avoids a name conflict with `has_no_errors`
    - the naming is consistent with other `try_*` functions in errors.mli
     - used for backtracking in sound dynamic code

### Potentially Observable Changes

We intentionally change behavior, under the following principle:  **we never want presence of warnings to affect type errors**. Apparently-accidental violation the principle before caused D90856070 and D90247637.

Changes to logic that could theoretically be user-facing today but may be hard to observe:
- Backtracking for sound dynamic previously was affected by presence of warnings due to its use of `run_and_check_for_errors`. Now that `run_and_check_for_errors` no longer is affected by warnings, it is theoretically possible that we produce type errors for sound dynamic in *more* places, though I didn't observe this in WWW.

Changes to logic that are not *currently* user-facing:
- Warnings no longer can affect hh_single_type_check exit code: hh_single_type_check.ml:2134
- The theoretical case of "parser warnings":
   - afaict these change nothing in practice *today* since we currently do not have any parser warnings. I suspect that if we add parser warnings in future, presence/absence of warnings should not affect whether we consider an AST to be valid, so looking at warnings only will continue to be the right thing to do
    - in ast_provider.ml, we cache ASTs even if they have warnings
    - In IDE, we show type errors even if there are parser warnings (clientIdeDaemon.ml)

And calling out some behavior that *doesn't* change:
- cases concerned with display of errors/warnings: saveStateService.ml, server_progress.ml, hh_single_type_check.ml
- No change to [typing_utils](https://www.internalfb.com/diff/D90780879?permalink=2264952574005081): we keep the fix in D90780880 but the fix is now less ad-hoc.

## Why

Not distinguishing errors from warnings in errors.ml was the cause of multiple bugs. See recent fixes in
-  `run_on_intersection` bug (repro: D90856070, fix in D90780880).
-  try_* functions issue (repro: D90247637, fix  in D90201956, later removed in D90780880 and D90383335)

The conceptual issue is that we should never go down a different code path in type-checking based on the presence or absence of an error.

With this change, I suspect the worst such footguns are resolved.

## Follow on work

- Team members most familiar with sound dynamic may want to revisit the backtracking logic and see if we can remove it–like Andrew previously did for other footgunny Errors.try_* functions in D90780880 and D90383335.
- Remove unused functionality from errors.mli and dead code: D91132746 (in progress)
- Stop using the same word for two different things. We currently have errors and warnings each being a kind of error and it's part of how we got into this mess.
