Commit title: fix SNI mismatch with certificate returned from Fizz certManager
Commit body:
Summary:
The unified cert manager implementation was not entirely consistent with Fizz behavior.

When there is a "default certificate" installed on the FIzz cert manager (very common), then Fizz will return the default certificate as long as compatible with the client supported signature algorithms __regardless of SNI matches__.

Consider a scenario where there are two certificates:
`foo.com, RSA` (not default) and `bar.com, EC` (default)

`maybeRSA` and `maybeEC` would be foo.com and bar.com respectively. Both of these would be installed on the corresponding `SSL` connection.

Now consider a client that supports both RSA and ECDSA authentication connecting to `foo.com`
- When this client connects to Fizz, the client receives `foo.com` since Fizz considers SNI.
- When this client connects to OpenSSL, the client receives `bar.com` since OpenSSL simply looks for the cert that matches the highest preference signing algorithm (ECDSA).

This diff changes the unified cert manager behavior to be consistent with Fizz certmanager semantics. It does this by categorizing certificates as "direct matched" (sni matches) and "default matched" -- only installing direct matched certificates if there are any.

This ensures that a client that supports both RSA and ECDSA asking for `foo.com` will receive the `foo.com` RSA certificate. Since `foo.com` has an RSA direct match, only the RSA certificate is available on the installed `SSL*` object.
 ---
The case that we currently are still inconsistent with Fizz is the case where a TLS 1.2 client that only supports EC and asks for `foo.com`.

On OpenSSL, the connection will be aborted with a handshake_error, since there is no ECDSA certificate installed.

On Fizz, the connection will proceed with (`bar.com, EC`), even though it is the incorrect SNI, rather than aborting.
