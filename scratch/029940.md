Commit body:
Summary:
### Better error-path & value-path performance

`ValueOrFatalAwaiter` now implements `await_resume_result()`, returning `value_only_result<T>`. Compared to the old impl, this:
  - Avoids throwing overhead for most inner awaitables -- we look for `await_resume_result`, then `await_resume_try`, then try/catch.
  - Avoids `result` union-type overhead for this value-only data path.

 ---

### `value_or_fatal` composes with `value_or_error...`

The motivation here is that upcoming pipeline code uses `value_or_error...` for its plumbing, and it's much simpler not to have to treat value-only awaitables separately.

Changes to `Noexcept.h` were required because otherwise, `value_or_error` would activate the "bypass exception handling" code path in the parent promise, and `OperationCancelled` propagation would **bypass** our `ValueOrFatalAwaiter::await_resume` handling.
  - `valueOrErrorAroundValueOnlyAwaitable` and some other tests exercise this.
  - This didn't used to be a problem because without `await_resume_result`, you couldn't compose `value_or_fatal` tasks inside of value-only wrappers.

NB: `value_or_fatal` still won't compose with `co_nothrow` or `co_awaitTry`, this is covered by existing tests. These could be relaxed later, but I don't see why.

 ---

### Fix policy implementation

While the API allowed default-on-error as of the previous diff, as of this diff, the **implementation** of `on_stopped_and_error<V>` now actually handles all errors, not just `OperationCancelled`.
  - The new `PolicySubstitutesValue` covers this.
