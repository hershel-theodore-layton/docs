Summary:
## Changes

No change to anything visible outside our team.

hh_single_type_check:
- Add validation for --config options in hh_single_type_check
- On incorrect key:
    - exit with nonzero return code
    - if the option is close to a correct option, provide a "did you mean" suggestion

Internals:
- move our `most_similar` function (finds the most similar name) from tast_env to string_utils because it doesn't have anything to do with `tast`s and  I wanted to use it from `Config_keys`
- remove levenshtein from the public API of string_utils, since it's no longer needed outside the module.

## Why

Today, it's too easy to mis-type an option and have the code do something different than what we expect.

Thanks sowens for pointing out after we used `--config` in more places (D91319457) there was more potential for missing typos.

## Alternative Considered

I considered a "parse, don't validate"-style approach, but it imo would be too invasive or require too much machinery. For example, the Config_file.Getters module is used for more than just hhconfg/--config parsing (also used for Hackfmt, for example) so the benefits would be limited.

## Follow-on

- Consider reusing the config option validation library here for hh_client as well. In that case, we don't want to fail hard (for release+rollback safety), but can still leverage a warning and/or the "did you mean" feedback.
