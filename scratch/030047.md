Commit title: `rich_exception_ptr` supports multiple sigils
Commit body:
Summary:
This is a small step towards the end-goal of removing `folly::Expected` from the innards of `result`. Profiling showed that extra abstraction to have noticeable costs.

To do this, we need some kind of variant-selector bit to choose between "value" and "error-or-stopped" state. Conveniently, `rich_exception_ptr` already has this functionality, at the cost of as single `uintptr_t` comparison.

`rich_exception_ptr` stores a union of states, with 3 low "alignment" bits used as a type selector. One of these bit patterns (`SIGIL_eq = 2`) is reserved for "sigil" states — folly-internal-only markers that don't represent exceptions.

Previously, only one sigil existed: "empty try" (`kSigilEmptyTry = 0`), used by `Try` to represent uninitialized state.

This diff adds a second sigil, generalizing the API. It also adds a "private" getter API, which will be needed up-stack.

### Why Not Reuse "Empty Try"?

We could pun "empty try" to mean "result has value", since:
- By design, `result` ↔ `Try` conversion should reject "empty try" values
- So the states would never collide in practice

However, using distinct sigils provides defense-in-depth:
- A state-management bug with punned sigils could access uninitialized `res_`
- With distinct sigils, such bugs are slightly less likely and more debuggable
- The performance cost of supporting distinct sigils is negligible -- they're mostly "you pay for what you use".  The only thing I can see in this diff is an extra comparison on the "cold path" of `operator==` ... and some defensive error handling in "throw" and "get eptr". None of this should affect baseline result performance.
