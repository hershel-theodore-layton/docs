Commit title: reorder named arguments and parameters in hackc to precede positional args
Commit body:
Summary:
Context: When working on the interpreter implementation of named parameter calls, we realized that maintaining a left-to-right execution order incurs significant stack shuffling overhead and makes calls with variadics very expensive due to the nature of how you want the stack to be arranged for calls like (1, 2, y=3, z=4) (the top |named args| elements need to be popped off in the variadic packing helper).

This diff changes the ordering of argument evaluation in calls (at the HackC side) to be:

1. All named args, sorted by key
2. All positional args, preserving relative ordering

It also reorders parameters so that all named parameters are lex sorted and precede any non-named parameters. The variadic capture parameter remains at the end.

This means that named args will be at the bottom of the stack, positional args will be at the top, with the named arg with the latest name being before the first positional arg (if any).

The upside of this is performance - the stack will be arranged in a natural manner, and for known func entry calls performance will be identical to passing everything positionally.

Downside is that side effect evaluation order will no longer be left-to-right, which is the intuitive order I suspect most people would expect evaluation in.

My thesis is that this will not affect people as much as we may initially fear in practice, here's why:

1. The main classes of side effects we expect are logging, mutating class/global state, and exceptions. Exceptions and logging shouldn't bite people in practice, and we're used to lots of logging happening in PSP anyway. Global/class state is the only place I really expect there to be problems, and both of those are quite rare. Since we're not changing any existing behavior (you need to opt into named arg/param usage for now), any evaluation-order issues will be on net-new code and should be easy to debug. This does mean we will be locked into this convention moving forward and only get one shot at it.

2. This isn't without precedent - expressions with awaits completely change evaluation order, as we hoist any `await e` subexpression to a temp if it happens to be within a larger expression.

After looking at what reordering looks like in practice, I think this is the right design decision, but want to keep this discussion open for comments as it comes with real downsides.

If we feel strongly that we need to keep evaluation order consistent, we can likely accomplish this with an elaboration pass in HackC, and keep HHVM blissfully ignorant of the user-specified order of operations.
