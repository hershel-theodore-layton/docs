Commit body:
Summary:
D92565783 suggests the crash in T230122079 is likely a linking issue for FB4A E2E build.

- It only reproduces in the FB4A E2E build flavor: `automation_fbandroid_landblocking_for_perftest`.
- The crash happens on every HTTP request.
- It only reproduces when LTO is disabled (`mode/nolto`).

`HttpClientException` [inherits](https://fburl.com/code/s23ulll2) from `HttpException`, which [inherits](https://fburl.com/code/7drj1ash) from `proxygen::Exception`. Neither `HttpClientException` nor `HttpException` declares a virtual destructor. In `mode/nolto`, this can lead to vtable emission in multiple translation units; if an exception object/reference crosses translation-unit boundaries, virtual dispatch can end up using an incompatible vtable and crash (SIGSEGV).

This diff works around the issue by introducing a key function (via out-of-line destructor definitions) so the vtables are anchored to a single translation unit.

Claude’s [explanation](https://docs.google.com/document/d/1ttTknVleCoz2d-LgnGTo2ZcIexQpQ-3hHLs7QyMQR8Y/edit) of why the workaround is effective:
```
Without a key function (the first non-inline virtual method defined in a .cpp), the compiler may emit vtables in every translation unit that uses the class. With LTO disabled (`mode/nolto`):
- Each translation unit ends up with its own vtable at a different address.
- When an exception reference crosses translation-unit boundaries, the vtable pointer can become invalid.
- Virtual dispatch then uses the wrong vtable, leading to a SIGSEGV.

Defining the (virtual) destructors in the .cpp files creates a key function and anchors the vtables to a single translation unit.
```
