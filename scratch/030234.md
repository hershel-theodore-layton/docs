Commit title: Fix transparent newtype leaking inner opaque type's constraint
Commit body:
Summary:
When a transparent newtype wraps an opaque newtype (e.g., `newtype N = M`
where `M` is opaque with constraint), the enforcement calculation was
incorrectly exposing the inner opaque type's constraint through the
transparent wrapper.

This caused incorrect behavior under implicit pessimisation: for a method
returning `N<T>`, the stored type became `(int & ~N<T>)` instead of just
`~N<T>`. The intersection with `int` (from the inner opaque type's
constraint) allowed code to incorrectly pass type checking when it
shouldn't.

The fix checks if the inner type resolves to an opaque type (PRopaque)
when processing a transparent wrapper, and if so, doesn't expose the
inner type's enforcement. This respects the opacity boundary and is
consistent with the existing comment about newtype opaqueness.
