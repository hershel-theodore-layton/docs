Commit body:
Summary:
This diff is part of a workaround for the problem described in T255951179. The bug is currently triggered when tmpwatch deletes parts of a saved state, but not the entire folder. The general workaround is that instead of relying on tmpwatch to delete saved states, we use our own cleanup mechanism in State_cleaner more aggressively.

This diff does just that: It changes the default value of `saved_state_cache_limit` from 20 to 5. This option was introduced in the previous diff in this stack to control how many saved states we allow to exist in the cache at the same time before pruning the least recently used one. This means that afterwards we can stop using `tmpwatch`.

The old value of 20 lead to ~154 GB of saved states residing on disk, while the new value of 5 results in ~40 GB.
