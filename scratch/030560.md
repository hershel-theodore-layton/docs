Commit title: Fix exception_tracer for libc++ builds
Commit body:
Summary:
This fixes a regression where exception_tracer produced no stack traces under libc++ builds. The dlsym(RTLD_NEXT) interposition approach for __cxa_throw and friends is unreliable in fbcode because ASAN stubs and PLT resolution can bypass folly's redefinitions, causing exception_tracer to silently fail with dynamically linked libc++.

This change unifies exception_tracer to always use the --wrap linker mechanism in fbcode, regardless of C++ stdlib (libc++ or libstdc++) or linkage mode (static or dynamic). The --wrap flag works at static link time by rewriting all references to e.g. __cxa_throw within the binary's object files to call __wrap___cxa_throw (folly's interposition) instead, while making the original available as __real___cxa_throw. This works even with dynamically linked libc++abi because the rewriting targets call sites in our code, not within libc++abi.so itself — the dynamic linker resolves __real___cxa_throw to the libc++abi.so symbol at runtime. By contrast, the dlsym(RTLD_NEXT) approach relies on dynamic symbol resolution order, which ASAN stubs and PLT quirks can disrupt. The dlsym fallback is kept in the C++ code for non-fbcode platforms (e.g., open-source CMake builds).

However, --wrap only rewrites calls within the objects being linked — calls to __cxa_begin_catch made inside libc++abi.so itself (e.g., failed_throw calling __cxa_begin_catch internally on uncaught exceptions) are not intercepted. To handle this, getCurrentExceptions() now falls back to checking the uncaught trace stack when the caught trace stack is empty.
