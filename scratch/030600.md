Summary:
## Motivation

TLDR today we export `O({# interceptors * # twjobs})` timeseries, and I want to reduce this to `O({# twjobs})`

Our goal is to address T225886769 by reducing the number of emitted interceptor metrics. I propose only emitting the aggregated metrics by default rather than per interceptor. For the purposes of investigation, the aggregated metrics will be enough to determine if it is an interceptor that is causing an issue by being slow. Service owners can then deep dive by enabling the individual metrics in their own monitoring configs.

## This diff

Add fb303 metrics that report the total combined latency of invoking all interceptors for each lifecycle method, complementing the existing per-interceptor latency metrics. This enables monitoring the aggregate overhead of the interceptor framework without needing to sum individual interceptor metrics.

For each of the 8 lifecycle events (onRequest, onResponse, onConnectionAttempted, onConnectionEstablished, onConnectionClosed, onStreamBegin, onStreamPayload, onStreamEnd), a new virtual method is added to InterceptorMetricCallback that takes only `std::chrono::microseconds` (no qualified name). At each callsite, a `folly::stop_watch` is started before the interceptor loop and the elapsed time is reported after the loop completes.

Example metric names:
- Per-interceptor (existing): `thrift.interceptor.module.MyInterceptor.on_request_processing_duration_us.avg`
- Total (new): `thrift.interceptor.on_request_processing_duration_us.avg`
