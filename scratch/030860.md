Commit title: Fix severe lock contention in ThriftClientStats and ServerStats
Commit body:
Summary:
Lock profiling on a production push server under overload test (Java 25, 10ms
threshold, 60s) revealed that ConcurrentHashMap.computeIfAbsent() in
ThriftClientStats.incrementCounterValues() was the dominant source of
lock contention in the entire JVM — by orders of magnitude:

{F1986052727}

  ThriftClientStats.incrementCounterValues computeIfAbsent: ~3,416s + ~2,326s + ~957s
  ServerStats.incrementCounter computeIfAbsent:             ~198ms
  All other lock contention combined:                       ~100ms

ConcurrentHashMap.computeIfAbsent() synchronizes on the hash bucket
node even when the key already exists. Since these stats methods are
called on every RPC with a small, fixed set of method-name keys that
stabilize after startup, every thread serializes through the same
bucket locks just to read values that are already present.

The fix uses the same optimistic get-first pattern that Caffeine cache
uses (which they explicitly document as "an optimistic fast path to
avoid unnecessary locking"): do a lock-free ConcurrentHashMap.get()
first, and only fall through to computeIfAbsent() on a cache miss.
After startup, get() always returns non-null and the locked path is
never entered.

Applied to all 8 computeIfAbsent call sites across both classes:
- ThriftClientStats: incrementCounterValues (2 maps), addHistogramValue (1 map)
- ServerStats: incrementAverages (1 map), incrementCounter (2 maps),
  updateDistribution (1 map)
