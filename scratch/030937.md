Commit title: Add supportsStreamInterception() opt-in to ServiceInterceptorBase
Commit body:
Summary:
D90922910 introduced a regression: for every streaming RPC, when
any service interceptor is registered (even purely unary ones),
HandlerCallbackBase::sendReply creates a StreamInterceptorContext.
This incurs heap allocation (make_shared), shared_ptr refcount
bumps for every interceptor, storage vector allocation, and
moveRequestStorage — all per-RPC overhead. Most interceptors
never override onStreamBegin/onStreamPayload/onStreamEnd, so this
work is wasted.

This diff adds an opt-in mechanism:
- ServiceInterceptorBase gains a virtual
  supportsStreamInterception() method (default false).
- Interceptors that override streaming methods must also override
  supportsStreamInterception() to return true.
- At server startup, processModulesSpecification() caches a bool
  hasStreamInterceptors via std::any_of — O(1) per-RPC cost.
- sendReply(ResponseAndServerStreamFactory&&) checks the cached
  flag instead of !getServiceInterceptors().empty().

When no interceptor opts in, the entire StreamInterceptorContext
creation block is skipped. The downstream consumer
(ServerGeneratorStreamBridge::fromAsyncGeneratorImpl) already
null-guards every use of the interceptorContext shared_ptr, so a
nullptr propagates safely — no onStreamBegin, onStreamPayload,
or onStreamEnd callbacks fire, and no per-payload co_await is
reached.
