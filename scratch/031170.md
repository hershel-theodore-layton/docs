Commit title: F14 faster hash & tag from CRC
Commit body:
Summary:
The current hash & tag functions for integer keys looks like this (`hash` is the key itself):
```
std::size_t c = _mm_crc32_u64(0, hash);
tag = (c >> 24) | 0x80;
hash += c;
```
Mathematically we have two hash functions H1(k) (the bucket index `hash`) and H2(k) (the 7 bit `tag`):
```
H1(k) = CRC(k) + k
H2(k) = (CRC(k) >> 24) | 0x80
```
H1 mixes in the key itself while H2 uses only the bits from the CRC. This is a good way to keep the two hashes uncorrelated, but it doesn't matter which hash we add the key to; the following would be just as good of a hash function with the added benefit of a faster H1:
```
H1(k) = CRC(k)
H2(k) = ((CRC(k) >> 24) + k) | 0x80
```
It turns out that H2 becomes critical as well when we increase its latency by a cycle by doing this, negating the benefit of making H1 faster. To also make H2 faster, let's say we didn't shift H2 to have independent bits of the CRC from H1:
```
H1(k) = CRC(k)
H2(k) = (CRC(k) + k) | 0x80
```
This is (empirically) no worse of a hash scheme https://godbolt.org/z/sTszavKGb. It also performs considerably better in the benchmark: geomean **+2.41%** Find speedup vs. the previous change (geomean **+4.07%** Find speedup vs. the base commit in this diff stack) as measured on Bergamo:
```
taskset -c 37 buck2 run @//mode/opt fbcode//folly/container/test:hash_maps_bench -- --bm_regex="f14" --bm_mode=best-of
```
