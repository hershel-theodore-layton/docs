# thrift-python enums, `int`, `IntEnum` & `__str__` inconsistency
thrift-python enums are both `Enum` objects and `int` (this concept is supported in the standard library as `IntEnum`)
```
class E(_fbthrift_python_types.Enum, int):
    A = 0
    B = 1
    C = 2
```

The following code type-checks and, as expected, integer operations have `int` results (no longer enum):
```
x: int = E.A
y: int = E.A + 1
>>> print((type(x), type(y)))
(<class '...thrift_enums.E'>, <class 'int'>)
```
❗️ You can no longer assume `str(x)` where `x: int` returns a proper `int` value
```
>>> print(x, y)
E.A 6
```
This different behavior has also been discussed upstream for `IntEnum`
A more wide-sweeping PEP 663 [https://peps.python.org/pep-0663/](https://peps.python.org/pep-0663/) was rejected, but an important aspect from the PEP was accepted https://mail.python.org/archives/list/python-dev@python.org/message/RN3WCRZSTQR55DOHJTZ2KIO6CZPJPCU7/
> One aspect of the PEP we do agree with is the alignment of IntEnum's str() and format(). It is confusing that they give different results, and that is worth the small compatibility breakage to fix.

This was accepted and changed upstream:
* [https://docs.python.org/3/library/enum.html#enum.IntEnum](https://docs.python.org/3/library/enum.html#enum.IntEnum)
```
Changed in version 3.11:
  __str__() is now int.__str__() to better support the replacement of existing constants use-case.
  __format__() was already int.__format__() for that same reason.
```

This formatting inconsistency has caused SEVs
- S586280 unicorn.native-indexer package not released for 1.5d

Old IntEnum behavior pre 3.11 (not using `int.__str__`) caused other SEVs in 2018
- S161583 Celebrity-impersonation reporting broken for 4 hours

* There's a known gotcha in our codebase: Python MySQL bindings format instances variables of `int` using `str(x)` and converting to thrift-python now leads to incorrect SQL generation (int constants replaced with strings).

Instead of making a blanket breaking change to all enums, this diff adds an opt-in `python.EnumFormatAsInt` annotation. Enums annotated with this will have `__str__` and `__format__` return the integer value (matching Python 3.11+ `IntEnum` behavior). Unannotated enums keep the existing `"EnumName.member"` format.

## Implementation
Following the existing `Flag(Enum)` pattern:
- Added `python.EnumFormatAsInt` structured annotation in `python.thrift`
- Added `EnumFormatAsInt(Enum)` runtime subclass in `types.pyx` that overrides `__str__` and `__format__` to return the int value
- Wired the annotation through the compiler: URI constant, `format_as_int?` template property, and mustache template to select the base class
- Generated enum classes use `EnumFormatAsInt, int` as base when annotated, otherwise `Enum, int` (default)

## Usage
```thrift
include "thrift/annotation/python.thrift"

python.EnumFormatAsInt{}
enum Priority {
  low = 0,
  normal = 1,
  high = 2,
}
```
```python
>>> str(Priority.normal)
'1'
>>> f"{Priority.high}"
'2'
```
