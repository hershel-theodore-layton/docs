Commit title: Make egress rate limit check event-driven instead of O(N) polling (~17% of slb_regional CPU savings)
Commit body:
Summary:
Strobelight profiling of proxygen/slb_regional shows `checkIfEgressRateLimitedByUpstream` consuming ~27% exclusive CPU, with `findTransaction` at ~10.6% — combined ~37% of total service CPU (https://fburl.com/scuba/strobelight_services/csmo3xq0).

Root cause: `HTTPSession::runLoopCallback`'s scope guard and `onWriteSuccess` both call `invokeOnAllTransactions` to poll every transaction's egress buffer state on every event loop tick. This is O(N) per tick where N is concurrent transactions. The check is purely telemetry — it sets a boolean (`egressRateLimitedByIngressRate_`) used only by RevProxy for diagnostics, with no control-flow impact.

The fix makes this event-driven:
1. Add a point check in `HTTPTransaction::sendDeferredBody()` — when the egress buffer actually drains, call `checkIfEgressRateLimitedByUpstream()` there.
2. Remove both O(N) polling call sites from `HTTPSession::runLoopCallback` scope guard and `onWriteSuccess`.

This changes the check from "poll every transaction every tick" to "check only when a transaction's buffer drains" — eliminating ~37% CPU overhead.

Benchmark results (mode/opt, 3 runs, stable within 6%):

Data structure microbenchmark (1000 concurrent transactions):
```
benchInvokeOnAllTransactions(1000_txns)    5.49us    (old O(N) pattern)
benchEventDrivenCheck(1000_txns)           2.47ns    222,030% faster (new O(1) pattern)
```

Full session benchmark with real HTTPSession/HTTPTransaction objects (1000 txns):
```
benchSessionCheckEgressRateLimited(1000_txns)   39.37us    (old O(N) pattern)
benchSessionEventDrivenCheck(1000_txns)          6.99ns    563,380% faster (new O(1) pattern)
```

The new event-driven pattern is ~2,200x faster in isolated data structures and ~5,600x faster with real session objects at 1000 concurrent transactions.
