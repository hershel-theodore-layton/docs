Commit title: Remove annotation lowering for java.swift.type and java.swift.binary_string
Commit body:
Summary:
The thrift compiler's sema.cc previously lowered `java.swift.type` and `java.swift.binary_string` unstructured annotations from a typedef down to its inner type. This was a workaround for mustache template limitations — the generator couldn't easily look up annotations on the typedef chain, so the annotations were propagated to the underlying type.

This diff removes that lowering and instead has the generator look for these annotations on the typedef chain directly using `t_typedef::get_first_unstructured_annotation_or_null` and `t_typedef::get_first_structured_annotation_or_null`.

Changes:
- **sema.cc**: Removed the lowering block that copied java.swift.type/java.swift.binary_string from typedefs to inner types
- **t_mstch_java_generator.cc**: Changed `javaType` and `isBinaryString?` properties to walk the typedef chain. Added `typedefWithoutJavaType?` property for template use.
- **uri.h**: Added `kJavaBinaryStringUri` constant
- **Templates** (ReadType, WriteType, ReadTypeContainer, ReadTypeContainerNested{Key,Value}, ThriftBoxedType, Type, common/types): Updated to check `isBinaryString?` and `javaType` on typedefs before resolving through them, so annotations aren't lost during typedef resolution.

Bugfix: The structured `java.BinaryString` annotation on typedefs (e.g. `binary_string`) is now correctly handled when used as a map value type, generating `byte[]` instead of `String`. The old lowering only handled the unstructured `java.swift.binary_string` annotation.
