Commit title: Add ApproxSet vs BddSet workload tests with separate targets
Commit body:
Summary:
Adds QuickCheck-based fuzz test suites that simulate three concrete type checker workloads against both `ApproxSet.Make(TagDomain)` and `BddSet.Make(OrderedTagDomain)`. Follows the fuzz testing approach from [Hack Native's BDD type analysis](https://docs.google.com/presentation/d/16Z1tB1nGGU9ei8roV5KCsqbGgWkHRC6eWJJDrGVhs1E/edit?usp=sharing): randomly generate small class/interface hierarchies, randomly generate type operations, and check properties against ground truth. Separate `custom_unittest` targets use OUnit's `-only-test` flag to isolate each implementation, so CI reports per-implementation pass/fail and timing independently.

### Tag domain (`approxset_tag_domain.ml`)

**Mock tag type** mirrors `typing_tag_defs.ml` structurally (Prim, Dict, Shape, Vec, Tuple, Object, Instance, BuiltIn, Mixed) without pulling in `Typing_defs` dependencies. `Instance` embeds `ancestor_count` at creation time from the hierarchy, which serves double duty: BDD variable ordering (more ancestors = more specific = higher in order) and a self-contained `compare` without global state.

**Hierarchy generator** produces random class/interface hierarchies with 4-16 classes following Java/Hack inheritance rules:
- ~30% interfaces, ~70% concrete classes
- DAG in topological order: single class inheritance + 0-2 interface parents; interfaces extend 0-2 other interfaces
- Transitive closure for ancestors/descendants
- ~50% leaf classes marked Final
- ~20% non-final classes/interfaces are sealed (whitelist = random subset of descendants)
- ~30% non-sealed interfaces get `require extends` targeting an ancestor concrete class
- 2-3 interfaces marked "special" with non-Instance tags in their data type (mirroring `Stringish` includes `StringData`, `Traversable` includes `Dict/Vec/Keyset`, etc.)

A pool of 200 hierarchies is pre-generated at module load time with deterministic seeds. Tests sample from the pool rather than generating per trial, avoiding the extreme slowness of `Quickcheck.Generator.filter` for features like sealed classes that are rare in random generation. Hand-crafted `featured_hierarchies` serve as fallback.

**Relation function** mirrors `typing_data_type.ml:126-204`.

**Ground truth via witness denotation**: `make_denotation` assigns unique integer witnesses — one per `Prim` variant, one per leaf class, plus shared witnesses for overlapping pairs (Shape/Dict, Tuple/Vec, BuiltIn/Object). Atom-level denotations represent only raw hierarchy relationships; sealed_whitelist narrowing, require_extends narrowing, and special interface expansion all happen at the `to_datatypes` level via `A.inter` and `A.union`, mirroring the real architecture where `Tag.relation` handles raw hierarchy and `Class.to_datatypes` handles expansion.

**`to_datatypes`** mirrors `typing_data_type.ml`'s `Class.to_datatypes`: Final → singleton, NonFinal → singleton, sealed → union(whitelisted) ∩ singleton(bound), interface with require extends → singleton ∩ to_datatypes(required_class), special interface → normal ∪ singleton(extra_tag₁) ∪ ...

**Wrapped ASet** tracks `{ set: Impl.t; expected: Int.Set.t }` through every operation so that soundness of `are_disjoint`/`is_subset` can be verified against ground truth.

### Test 1: Refinement (`approxset_test_refinement.ml`)

Simulates `typing_refinement.ml`'s `split_ty_by_tag` — classifying union components as LEFT (⊆ predicate), RIGHT (disjoint from predicate), or SPAN.
- `test_single_refinement` (10k trials): single component vs predicate, verify LEFT/RIGHT soundness
- `test_if_else_chain` (5k): sequential `if ($x is T1) ... else if ($x is T2) ...` narrowing, verify remaining shrinks monotonically
- `test_negation_refinement` (5k): `!($x is T1 || $x is T2)` patterns via diff(mixed, union)
- `test_refinement_sealed_interface` (5k): sealed interface via `to_datatypes` producing union ∩ bound
- `test_refinement_require_extends` (5k): interface with `require extends` via `to_datatypes` intersection

### Test 2: Variant filter (`approxset_test_variant_filter.ml`)

Simulates `typing_case_type_variant.ml`'s `filter_variants_using_datatype` — filtering case type variants provably disjoint from an intersecting type.
- `test_variant_filter_basic` (10k): N variants (each union of 1-3 tags) vs intersecting type, verify no unsound filtering
- `test_variant_filter_with_intersection` (5k): intersecting type is intersection of 2 tag sets
- `test_variant_filter_with_negation` (5k): intersecting type is diff(mixed, tag_set) — simulates `Tneg`
- `test_variant_filter_sealed` (5k): variants are sealed whitelist classes via `to_datatypes`
- `test_variant_filter_require_extends` (5k): intersecting type from interface with `require extends`

### Test 3: Subtype disjointness (`approxset_test_subtype_disj.ml`)

Simulates `typing_subtype.is_type_disjoint_help` using complex type generator (`gen_type_set`: atomic singletons, nullable types, unions, intersections, negations, depth 1-3).
- `test_disjointness_soundness` (10k): `are_disjoint` true ⟹ ground truth intersection empty
- `test_subset_soundness` (10k): `is_subset` true ⟹ ground truth subset holds
- `test_disjointness_symmetry` (10k): `are_disjoint(a,b) = are_disjoint(b,a)`
- `test_nullable_disjointness` (5k): `?Final(i)` vs `?Final(j)` where i≠j — non-disjoint because null overlaps
- `test_negation_self_disjoint` (5k): `are_disjoint(T, mixed \ T)` for precise tags
- `test_complex_relate` (10k): is_subset both directions + are_disjoint, all verified against ground truth
