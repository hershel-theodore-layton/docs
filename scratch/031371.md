Commit title: fix files being stuck in disk_needs_parsing
Commit body:
Summary:
This diff fixes a bug caused by the interaction between `ServerMain` and `ServerTypeCheck` wrt updating `ServerEnv.env`, and using the latter to determine whether a new type-check should be started. This can cause `hh` to get stuck or report incorrect results until the next time a file changes on disk.

The following sequence of events leads to the bug:
1. Some file `f1` changes on disk and a type-check starts.
2. While this type-check runs, another file `f2` is changed, triggering the interrupt mechanism: `ServerMain.file_changes_interrupt_handler` adds `f2` to `env.disk_needs_parsing` and the type-check job gets cancelled
3. In `ServerTypeCheck.type_check_core`, `needs_recheck` is empty, and `env.full_check_status` is set to `Full_check_done`.
4. As long as no more files change on disk, `ServerMain.recheck_until_no_changes_left` gets empty `updates` and does not trigger new type-checks, despite `f2` still lingering in `env.disk_needs_parsing` and not having been checked.

At this point, the user-facing behavior is that invoking `hh` on the command line would get stuck and time out (if streaming errors are enabled) or incorrectly report type-checking results despite `f2` not having been checked yet (if streaming errors are disabled). Luckily, the problem is resolved the next time a file changes on disk, at which point `f2` will be re-checked, together with any new changes.

This bug does not affect Sandcastle, where the interrupt mechanism is not enabled.

The fix is that in `ServerMain.recheck_until_no_changes_left`, we now make sure to kick off a type-check if `updates` or `env.disk_needs_parsing` is non-empty. Previously, we were only looking at `updates`.

I'm certain that this change is safe and solves the problem, but I've left two comments in `ServerTypeCheck` in places where we determine whether a type-check is complete. It is unclear to me if we should actually be looking at `env.disk_needs_parsing` earlier on, not just in the next iteration of  `ServerMain.recheck_until_no_changes_left`.
