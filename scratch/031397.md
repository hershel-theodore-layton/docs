Commit title: Add ApproxSet vs BddSet performance benchmark
Commit body:
Summary:
To evaluate whether `BddSet` is a viable replacement for `ApproxSet` in
production, we need empirical data on their relative construction and query
performance under realistic workloads.

This diff adds a standalone benchmark binary (`approxset_bench`) that compares
the two implementations across five scenarios modeled after real hot paths in
the type checker:

- **Refinement** (10K trials) — models `typing_refinement.ml`'s
  `split_ty_by_tag`: builds `to_datatypes` sets and queries `are_disjoint`
  against predicates and their complements
- **Variant filter** (5K trials) — models `typing_case_type_variant.ml`'s
  `filter_variants_using_datatype`: builds N variant tag sets and checks
  disjointness against an intersecting set
- **Overlap validation** (2K trials) — models `typing_typedef.ml` pairwise
  overlap checking: builds N variant sets via `to_datatypes` and performs
  N*(N-1)/2 pairwise `are_disjoint` calls
- **Complex subtype** (10K trials) — models `typing_subtype.ml` with deeply
  nested expression trees (union/inter/diff) and queries both `are_disjoint`
  and `is_subset`
- **Construction only** (10K trials) — pure construction throughput with no
  queries

Key design decisions:
- Input types are defined at module level so identical pre-generated inputs are
  shared across implementations, ensuring a fair comparison
- Deterministic seeds via `Splittable_random.State.of_int` for reproducibility
- Construction and query phases are timed separately to distinguish where each
  implementation wins or loses
- Uses raw `Impl.t` operations (no `ASet` ground-truth wrapper) to avoid
  benchmark overhead
- Adding a new implementation requires only one new module + one
  `BenchScenario` instantiation
