Summary:
## What

When strict_consistent_construct=true, ban abstract classes from extending nonabstract __ConsistentConstruct classes.

## Why

There's [user confusion and pain](https://fb.workplace.com/groups/entschema/posts/31007400178881868/?comment_id=31007786435509909&reply_comment_id=31014690754819477) because devs expect `new static()` to be safe+allowed in __ConsistentConstruct hierarchies, yet our current rules around abstractness break this.

The relevant cases are ones like the following. `C2::m()` below would fail at runtime, since it would try to instantiate an abstract class:

```
<?hh

<<__ConsistentConstruct>>
abstract class C1 {
  abstract const int X;
  <<__NeedsConcrete>>
  public static function nc(): void {
    new static();
  }

  public static abstract function abs(): void;

}

// C2 is *not* concrete even though it is `abstract final`.
// C2 has an unimplemented member (the constructor)
abstract final class C2 extends C1 {
  const int X = 3;
  public static function m(): void {
    static::nc(); // hh error - because it calls `new` and the constructor for C2 doesn't exist
  }

  public static function abs(): void {}
}
```

The warnings are not wrong, they catch a real issue, but the best way to fix the issue is to avoid having the "weird hierarchies" in the first place and make it so a class is either for instantiating with `new` or not: `abstract final __ConsistentConstruct` is weird.

see fb-only section for data

## Next steps

- run `hh` with `--config strict_consistent_construct=true` to find and fix places in WWW with bad `abstract`
- Hack Improvement Proposal in progress to make strict_consistent_construct=true the default, but landing this change is still valuable even if we don't go that far.
