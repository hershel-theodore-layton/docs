Commit title: Fix get_receiver_ids discarding class names when encountering dynamic in union types
Commit body:
Summary:
## Motivation

When the Hack type checker processes successive `is` type refinements with
reassignment (a common pattern for interface feature detection), cross-references
for method calls are lost starting from the 3rd refinement. This causes:

- `hh --find-refs` to report 0 results for methods that ARE referenced
- Glean's TargetUses xrefs to be missing, making the dead code bot incorrectly
  identify used methods as unused and deprecate/remove them

## Root Cause

`Tast_env.get_receiver_ids` traverses types recursively using `List.fold` to
accumulate class names from union/intersection types. However, the `Tdynamic`
and `Tany` handlers create fresh lists (`[RIdynamic]` / `[RIany]`) instead of
appending to the accumulator, discarding all previously collected class names.

After 3+ successive `is` refinements, the type system introduces like-type
wrappers (`~T`), which are internally represented as `Tunion [T; Tdynamic]`.
When `List.fold` processes this union, it first accumulates the target interface
class from `T`, then encounters `Tdynamic` which replaces the entire accumulator
with `[RIdynamic]`, losing the target class name.

## Fix

Change `Tdynamic` and `Tany` handlers to append to `acc` instead of replacing
it: `RIdynamic :: acc` and `RIany :: acc`. This preserves class names
accumulated from sibling branches in union/intersection types.

Callers are unaffected:
- `get_class_ids` filters for `RIclass` only (extra `RIdynamic` filtered out)
- `typed_member_id` maps `RIdynamic` → `UnknownClass`, then
  `possibly_remove_unknown_classes` drops it when `ClassName` entries exist

## Test Plan

- Added `successive_is_refinements` test to `find_refs` test suite
- All existing `find_refs` tests pass
- Verified with `hh_single_type_check --find-refs`: all 4 methods now found
  (previously only methods 1-2 were found, 3-4 returned 0 results)
