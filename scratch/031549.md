Commit title: Enable parallel disassembly
Commit body:
Summary:
tc-print processes translations sequentially. The output phase is almost parallel — each translation's processing (reading machine code, disassembling, formatting) is independent — but three shared-state issues needed to be addressed:

1. **FILE* handles**: `TCRegionRec` used shared `FILE*` with `fseek()/fread()`, which is not thread-safe. Replaced with `mmap()`: TC dump files are memory-mapped at construction time, and `readFromRegion()` uses `memcpy()` from the mapped region.

2. **AnnotationCache**: The lazy load-and-cache pattern in `getIOBuf()` was not thread-safe. Added `std::mutex` with `lock_guard`. Contention is low since there are only a few distinct annotation files.

3. **alloca()**: Worker threads have smaller stacks, so large translations could overflow. Replaced `alloca(codeLen)` with `std::vector` in both x86 and AArch64 code paths.

With these addressed, the parallelization works as follows:
- Added `-P <N>` CLI option (default: `hardware_concurrency()`, `-P 1` for sequential).
- Added `generateTransOutput(TransID)` that captures output for a translation into a `std::string` via `std::ostringstream`.
- Added `parallelForEach()` that generates results in worker threads and streams them to the consumer (main thread) in order as each slot becomes ready via per-slot atomics. This bounds peak memory to roughly `nThreads * avg_result_size` instead of `count * avg_result_size`.
- Parallelized JSON mode (`getTC()`), default mode, creation order (`-s`), and top translations (`-t`). Output ordering is preserved.

Also fixed a pre-existing UBSan issue in `offline-arm-code.cpp` where a shift exponent of 32 on a 32-bit `Instr` type caused undefined behavior in AArch64 call address tracking.

Also fixed an out-of-bounds access in `printDisasm()` and `getDisasm()` when `findTCRegionContaining()` returns `TCRCount` (folded from D95586424).
