Commit title: Fix thread-safety bug in LmdbObjectMap
Commit body:
Summary:
LmdbObjectMap uses a process-global std::map to track LMDB handles
(MDB_env*, MDB_txn*, MDB_cursor*). When multiple HHVM worker threads
call mdb_env_close (or cursor_close) concurrently, they race on
std::map::erase, corrupting the red-black tree and causing SIGSEGV
in std::_Rb_tree_rebalance_for_erase. The counter field also has
non-atomic read-modify-write races on addObject.

The existing TODO in the file suggested making everything thread-local.
This commit does exactly that: changes LmdbObjectMap::get() to return
a thread_local instance instead of a process-global singleton. Since
LMDB handles are created and used within a single request thread in
HHVM, thread-local storage is the correct scope.

Stack traces of the crashes:
- P2242265347 (SIGSEGV in releaseObject during GC)
- P2242265392 (SIGSEGV in releaseObject during GC)
- P2242265302 (SIGBUS downstream from stale lock file after crash)
