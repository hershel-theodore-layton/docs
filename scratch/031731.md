# Explanation

D95846368 mistakenly changed CompareThreeWay<struct_t<T>> to use FieldIdAscending.

This made CompareThreeWay inconsistent with `operator<` (which goes through StructLessThan and always uses declaration order).

The bug is observable on nested structs with out-of-order field ids.

(On nested structs, `operator<` is implemented by using CompareThreeWay to improve performance, since you only scan the struct one time and it's more cache friendly).

Consider OutOfOrderStruct where field_2 (id=2) is declared before field_1 (id=1):

  lhs = {field_2=10, field_1=2}
  rhs = {field_2=20, field_1=1}

  // Direct: operator< uses StructLessThan (declaration order)
  lhs < rhs → compare field_2 first → 10 < 20 → true  ✓

  // Nested in OutOfOrderNested: `operator<` uses StructLessThan for outer
  // fields, then CompareThreeWay for inner struct values
  l.s()=lhs, r.s()=rhs
  l < r → CompareThreeWay<OutOfOrderStruct>(lhs, rhs)
        → (bug) field_1 first → 2 > 1 → false  ✗
        → (fix) field_2 first → 10 < 20 → true  ✓

# Production Impact

After D95846368, some structs might start using object model order in C++. It might affect users who rely on the ordering across procss, e.g., deterministic hash value will change if there structs that field id order doesn't match declaration order.

# Why unit-test didn't catch it

The unit test in D95846368 did not catch this because it only asserted `thrift_object_model_less` (which intentionally uses FieldIdAscending) on the nested OutOfOrderNested values, without also asserting `operator<`.

The direct non-nested case passed because `OutOfOrderStruct::operator<` goes through StructLessThan, bypassing CompareThreeWay entirely. Added EXPECT_LT assertions for the nested cases to close this gap.

In addition, this bug is hard to trigger, it's not caught by any other unit-tests.
