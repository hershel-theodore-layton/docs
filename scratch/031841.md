Commit title: Use noop pattern for BiDi error delivery, matching stream/sink
Commit body:
Summary:
D96343398 replaced the generic "BiDi stream terminated" error with proper
error propagation for BiDi channels. However, it used
`onFirstResponseError(EncodedFirstResponseError)` which, in the SRProxy
context, fell through `handleResponseError`'s exception type cascade to
the catch-all, producing `PROXY_CLIENT_APP` with an unhelpful message.
Stream and sink use a different approach — a noop server callback with
`onFirstResponse` — which preserves the serialized SR error headers and
delivers the correct error reason (e.g., `THROTTLING_PENDING`).

This diff switches BiDi to the same noop pattern used by stream and sink:

1. **`BiDiServerCallbackNoop`** (new, in `CallbackUtils.h`): A no-op
   `BiDiServerCallback` analogous to `StreamServerCallbackNoop` and
   `SinkServerCallbackNoop`. During `sendBiDiThriftResponse`, the
   framework calls `resetClientCallback` to update the noop's client
   pointer from the proxy callback to the transport-level callback
   (e.g., `RocketBiDiClientCallback`). After `onFirstResponse` returns,
   `getClientCallback()` returns the transport-level callback for safe
   teardown via `onStreamComplete` + `onSinkCancel`.

2. **`passSerializedExceptionToClient`** (updated BiDi path): Delivers
   the serialized error payload via `onFirstResponse` (preserving SR
   error headers), then tears down both channels. This matches the
   stream (`onFirstResponse` + `onStreamComplete`) and sink
   (`onFirstResponse` + `onFinalResponseError`) patterns.

3. **`RocketBiDiClientCallback::onFirstResponse`** (bug fix): The early
   cancel path was using `serverCallback_` (member, still `nullptr`)
   instead of `serverCallback` (parameter), causing a null pointer
   dereference when a client cancels before the first response.

BiDi error handling is now consistent with stream and sink — all three
deliver `THROTTLING_PENDING` for throttling errors instead of BiDi
returning `PROXY_CLIENT_APP`.
