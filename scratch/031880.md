Commit title: Fix unsigned integer underflow in AtomicHashMap threadEraseInsertRace test
Commit body:
Summary:
The `Ahm.threadEraseInsertRace` test was failing/flaky across multiple build configurations (dev-nosan, dev, opt, opt-asan, aarch64) because of an unsigned integer underflow bug in the erase thread synchronization logic.

In `testEraseEraseThread`, the condition `currentLevel - lag < i` uses `size_t` (unsigned) arithmetic. When `currentLevel` (loaded from `insertedLevel`) is less than `lag` (10), the subtraction wraps around to a very large positive number (~SIZE_MAX), which is never less than `i`. This causes the synchronization loop to exit immediately instead of waiting for the insert thread to get ahead by `lag` positions.

As a result, erase threads would attempt to erase keys before they were inserted, find `count(key) == 0`, skip them, and never come back. The insert thread would later insert those keys, but no erase thread would erase them, leaving the map non-empty and failing the final `EXPECT_TRUE(globalAHM->empty())` assertion.

The fix changes `currentLevel - lag < i` to `currentLevel < i + lag`, which is mathematically equivalent but avoids unsigned underflow. Additionally, `insertedLevel` is now explicitly reset to 0 before the test starts, ensuring proper test isolation if the test is repeated (e.g., via `--gtest_repeat`).
