Commit title: Optimize HPACK encode path with FOLLY_ALWAYS_INLINE
Commit body:
Summary:
Add FOLLY_ALWAYS_INLINE to the internal encode helper functions
(encodeHeaderImpl, encodeAsLiteral, encodeAsLiteralImpl, encodeLiteral,
encodeAsIndex) so the compiler is forced to inline the full encode chain
into the three private encodeHeader overloads.

The compiler's inliner was backing off due to cost estimation artifacts
from CHECK() and VLOG() macros that expand to large cold-path code,
inflating the estimated function size despite being dead on the hot path.

We can see these function are not getting inlined: https://fburl.com/strobelight/dqd8nzlj

Strobelight data for ::encodeHeader: https://fburl.com/strobelight/2pgq1dqu

ARM64 shows no meaningful change — the compiler already inlines these
functions on ARM64 without the annotation. The benefit is x86_64-specific
where the compiler's cost model was incorrectly penalizing these functions
due to CHECK()/VLOG() macro expansion.

perf stat (via --bm_perf_args="stat -d"), two runs:
```
                          Before          After
L1-dcache-load-misses   44.6M-74.8M    28.8M-37.5M    (~16-61% reduction)
branch-misses             1.79M-1.82M    1.77M-1.79M   (~1% reduction)

insn_per_cycle            2.8            2.8-2.9
```

L1 dcache misses consistently decrease. Inlining eliminates stack frame
overhead, keeping more data in L1 cache. Instruction count increases
slightly due to code duplication, but improved cache behavior more than
compensates.
