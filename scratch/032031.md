Commit title: NOINLINE Encode<i64_t> to prevent varint code bloat in OpEncode write paths
Commit body:
Summary:
With the force-inlining fix from D98193653, OpEncode struct write
methods now inline all per-field encoding. For CompactProtocol, writeI64
expands to zigzag + BMI2 pdep varint encoding (~80 bytes per call site for
the 10-byte worst case). Without NOINLINE, every i64 field gets its own
copy of this code, bloating the function and causing icache pressure.

This was identified through disassembly analysis: OpMixed::write was 965
bytes with varint inlined vs codegen Mixed::write at 742 bytes.

To avoid overindexing on one benchmark, added comprehensive benchmark
coverage across all four integer sizes (byte, i16, i32, i64) in both
struct-with-12-fields and list-of-10K-structs contexts, then benchmarked
each to determine the correct NOINLINE scope.

Results (CompactProtocol, OpEncode vs codegen, negative = OpEncode faster):

Struct write (12 homogeneous fields):
  byte:  42.4ns vs 42.2ns →   0%
  i16:  120.1ns vs 92.5ns → -23% (OpEncode wins)
  i32:  122.2ns vs 103.2ns → -16% (OpEncode wins)
  i64:   89.2ns vs 89.0ns →   0% (neutralized by NOINLINE)

BigList write (10K structs of 12 fields each):
  byte: 243.2us vs 242.7us →   0%
  i16:  970.6us vs 786.0us → -19% (OpEncode wins)
  i32:  984.6us vs 816.6us → -17% (OpEncode wins)
  i64:  726.4us vs 727.4us →   0% (NOINLINE has no per-element cost)

Reads: neutral across all types.

ComplexStruct (the original regression target, mixed field types):
  write: 68.6ms vs 61.9ms → -10% (OpEncode now faster)
  read: 116.2ms vs 95.9ms → -17% (OpEncode now faster)

i64 is the only type where NOINLINE is needed: its varint encoding is
large enough that inlining causes code bloat, but the per-call overhead
from NOINLINE is negligible relative to the encoding work. For i16/i32,
the varint is smaller so inlining is net positive, and OpEncode actually
generates better code than codegen (16-23% faster). Applying NOINLINE to
i16/i32 was tried and caused +79% regression on BigListInt.
