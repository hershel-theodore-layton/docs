## 🐛 Vulnerability

**heap_buffer_overflow** in `THttpParser.cpp:getReadBuffer()` (line 65) and `THttpTransport.cpp:refill()` (line 191)

The Thrift HTTP parser's buffer management uses a `uint32_t` variable (`httpBufSize_`) that doubles each time the buffer needs to grow. Starting from 1024, after 22 doublings it reaches `0x80000000`. The next doubling overflows the `uint32_t` to `0`, causing `realloc(ptr, 0+1)` to allocate only 1 byte while `httpBufLen_` retains the old value (~1.5GB). This creates a wild pointer: `httpBuf_ + httpBufLen_` points ~1.5GB past a 1-byte allocation, and subsequent `memcpy` writes attacker-controlled data to this wild pointer. A malicious server can exploit this by sending ~1.5GB of HTTP response data without completing headers, achieving remote code execution or denial of service against Thrift clients using HTTP transport. The existing `checkMessageSize` mitigation has a gap — it checks at `0x7FFFFFFF` but the overflow triggers at `0x60000000`.

**Source task**: [T259157625](https://www.internalfb.com/T259157625)

 ---

## 🔧 How This Fix Works

**Priority 0**: Site of logic error | **Approach**: Add overflow guard before buffer size doubling

The fix adds a simple check `httpBufSize_ > UINT32_MAX / 2` before each `httpBufSize_ *= 2` operation. When the buffer size would overflow on doubling, a `TTransportException` with `CORRUPTED_DATA` is thrown instead. This matches the existing error pattern used by `checkMessageSize()` in the same codebase. Both vulnerable sites are fixed: `THttpParser::getReadBuffer()` and `THttpTransport::refill()` (which had NO overflow protection at all). The approach was chosen over type widening (`size_t`) because it's minimal and doesn't change the class API, and over lowering `maxSize_` because that doesn't fix the root cause due to a timing gap between the size check and the overflow.
