Commit title: Eliminate Object[] allocation in generated Java hashCode methods
Commit body:
Summary:
The Thrift Swift Java codegen template for struct hashCode() generated:

    return Arrays.deepHashCode(new java.lang.Object[] { field1, field2, ... });

This allocates a new Object[] on every hashCode() call. For structs used as
HashMap/ConcurrentHashMap keys on hot paths (e.g. TopicKey in Iris, called
millions of times per second), this creates significant GC pressure.

The fix replaces this with inline hash computation using the standard
result = 31 * result + fieldHash pattern, with type-specific dispatch:

- Required primitives (bool/byte/i16/i32/i64/double/float): use static
  Type.hashCode(primitive) methods (e.g. Long.hashCode(field)) — zero
  allocation, zero boxing
- Optional primitives: use Objects.hashCode(field) — null-safe, already
  boxed so no additional allocation
- Raw binary (byte[]): use Arrays.hashCode(field) — content-based hash,
  matching the previous Arrays.deepHashCode behavior
- Adapted binary (ByteBuf/ByteBuffer via java.Adapter): use
  Objects.hashCode(field) — adapter transforms the type away from byte[]
- All other types (string, struct, enum, list, set, map): use
  Objects.hashCode(field) — null-safe, delegates to the type's hashCode()

This produces identical hash values to the old implementation (the
31 * result + element.hashCode() formula is exactly what
Arrays.deepHashCode uses internally) while eliminating the Object[]
allocation entirely.
