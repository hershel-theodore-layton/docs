`flushAllHandlers()` acquires `loggersByName_.wlock()` even though it only iterates the map and calls `getHandlers()` on each category — pure read operations. Using a write lock unnecessarily blocks all concurrent logging threads that need `loggersByName_` (e.g., `getCategory()`, `getCategoryOrNull()`). This is especially impactful on the FATAL log path, where `admitMessage()` calls `flushAllHandlers()` before aborting.

Five other call sites in the same file already use `rlock()` for identical read-only iteration patterns (`getConfigImpl()` at line 150, `updateConfig()` at line 374, `resetConfig()` at line 428, etc.). The `wlock()` in `flushAllHandlers()` was inconsistent with this established pattern.

This diff changes `wlock()` to `rlock()`, allowing concurrent read operations to proceed during flush.

Codex adversarial review notes:
- With rlock, flushAllHandlers() can now interleave with concurrent updateConfig()/resetConfig() handler mutations. In theory, this could cause flushAllHandlers() to miss an old handler being replaced. In practice, this requires a config update at the exact moment of a FATAL log, the FATAL message is already dispatched before flush, and AsyncLogWriter's destructor flushes remaining messages. Reviewer should assess whether the original wlock was intentionally chosen for this exclusion property.
