Commit title: Move client request compression and response decompression to caller thread via generated code
Commit body:
Summary:
Moves request compression and response decompression from the IO thread to the caller thread for thrift clients using ServiceRouter, gated by `thrift_client_compress_request_on_cpu` (default false).

## Motivation:
Request compression currently happens on the IO thread inside `packWithFds()`, and response decompression happens inside `unpack()`. This adds CPU work to the IO thread. By moving both to the caller thread — where serialization/deserialization already runs — we reduce IO thread load and eliminate unnecessary thread switching.

## How it works:

Two new virtual methods on `RequestChannel` (no-op by default):
- `compressRequest(request, rpcOptions, header)` — called by generated code after serialization, before sending.
- `decompressResponse(state)` — called by generated code before deserialization, after receiving.

Request path (caller thread → IO thread):
1. Generated `fbthrift_serialize_and_send_*()` calls `channel_->compressRequest()` after serializing the request.
2. `ServiceRouterClientChannel::compressRequest()` reads SR tier compression config, compresses the buffer using `folly::compression::getCodec()->compress()`, and stores the algorithm on `THeader` via `setPreCompressedAlgorithm()`.
3. `sendThriftRequest()` detects the pre-compressed state, sets `metadata.compression()`, and passes `skipCompression=true` to `packWithFds()` to avoid re-compression.
4. On compression failure, the original buffer is preserved (`compress()` takes non-owning `const IOBuf*`) and the IO thread compresses normally as a fallback.

Response path (IO thread → caller thread):

- When `skipCompression` was set on the request, `SingleRequestSingleResponseCallback` uses `unpackAsCompressed()` instead of `unpack()`, skipping IO-thread decompression. The compression algorithm is stored on `THeader` via `setResponseCompressionAlgorithm()`.
- Generated code calls `channel_->decompressResponse(returnState)` before `recv_wrapped_*()` in all client paths: coroutine, sync, future, and header-future.
- `ServiceRouterClientChannel::decompressResponse()` reads the algorithm from `THeader` and decompresses the response buffer.
- On decompression failure, throws `TTransportException(CORRUPTED_DATA)` — there is no fallback since the compressed data cannot be deserialized.

Benchmark results show that caller-thread compression delivers significant throughput and latency improvements that scale with payload size. For small payloads (8KB–32KB), performance is roughly neutral with QPS gains under 3%. The benefits become pronounced starting at 128KB (+17% QPS) and grow dramatically for larger payloads: 512KB sees an 89% QPS increase with P50 latency cut nearly in half, while 1MB payloads achieve a 98% QPS improvement with P50 dropping from 3,988μs to 1,957μs. At the largest tested size (4MB), QPS improves by 72% and P99 latency is reduced by 49%.
