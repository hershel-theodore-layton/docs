Commit title: Use weak_ptr for responseDecompressor to fix 115 test failures from D97352193
Commit body:
Summary:
D97352193 introduced caller-thread compression/decompression for ServiceRouter clients. The responseDecompressor lambda in `prepareRequestClientCallback` captured a `shared_ptr<RequestChannel>`, which extends the channel's lifetime until the callback is destroyed. This exposed pre-existing ServiceRouter singleton destruction ordering bugs in ~115 downstream tests — during test teardown, the extended channel lifetime causes `deallocateEphemeralShard()` to access freed `ComputedServiceHandleState`, resulting in heap-use-after-free.

Fix: change the shared_ptr capture to weak_ptr. This eliminates the lifetime extension that triggers the test failures while fully preserving the caller-thread compression/decompression feature:

- Sync and coroutine paths (the primary paths) call channel->decompressResponse() directly via a local shared_ptr in generated code — the lambda is not involved, so the feature works identically.
- Future/semifuture/callback path uses the lambda, but during normal operation the client holds the channel alive, so weak_ptr::lock() always succeeds and decompression runs correctly.
- decompressResponse() is a no-op for the base RequestChannel class and only does work for ServiceRouterClientChannel when thrift_client_compress_request_on_cpu is enabled (default false).
- The compressRequest() call in generated code is completely unaffected by this change.
