In `ContextCallbackList::addCallback()`, when a new `CallbacksObj` is allocated and stored to the `callbacks_` atomic pointer, both the store (line 662) and the load in `getContextString()` (line 668) used `memory_order_relaxed`. On weakly-ordered architectures (ARM), a reader thread could load the non-null pointer but not yet see the memory backing the `CallbacksObj` (constructor effects not visible), leading to undefined behavior.

The `push()` → `forEach()` path was already correctly synchronized via `end_`'s release/acquire protocol. This fix addresses specifically the first-time pointer publication path (null → non-null transition of `callbacks_`).

Fix: use `memory_order_release` on the store in `addCallback()` and `memory_order_acquire` on the load in `getContextString()`. The destructor's relaxed load (single-threaded teardown) and the `addCallback` load under `writeMutex_` (mutex provides acquire semantics) are correctly left as relaxed.
