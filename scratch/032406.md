Summary:
The original 'release HandshakeLogging after handshake' approach in D98389346
+ D99158082 was unsafe in two ways:

1. `fizz->releaseHandshakeLogging()` resets the entire HandshakeLogging
   pointer to nullptr, but `ConnectionEventLogEntry::addTLSInfo`
   (`fbcode/common/thrift/cpp/server/logging/EventLogEntry.cpp:526`) reads
   `state.handshakeLogging()->clientAlpns`. addTLSInfo is invoked lazily
   on the first request via `logSetupConnectionEventsOnce`, well after
   any release point in the AcceptObserver or Cpp2Worker — this caused
   the SIGSEGV pattern fixed defensively in D101461979 (852/926 fatals
   in 24h on zippydb.zorro.feed.atn).

2. Even with D101461979's nullptr guard, the same connection-event log
   path fires later in the connection lifetime on:
     - drop_connection.rocket (RocketServerConnection.cpp:694)
     - exceeded_{egress,ingress}_mem_limit (:816, :998)
     - transport.metadata family on every client MetadataPush frame
       (LoggingEventTransportMetadata.cpp:36/:41/:45)
     - sampled monitoring_over_header per-request (Cpp2Connection.cpp:682)
   So enabling the release would silently strip `client_alpns` from
   every late-fired connection event.

Changes
-------

**Cpp2Worker.cpp (fbcode + xplat) — revert D99158082:**
Remove `THRIFT_FLAG_DEFINE_bool(thrift_release_handshake_logging, false)`
and the `if (THRIFT_FLAG(...)) fizz->releaseHandshakeLogging();` block.
The flag was never enabled, so this has zero behavioral impact. Removing
it eliminates a foot-gun: turning it on would lose ALPN observability
(silently after D101461979) on all connection events fired post-handshake.

**zippydb HandshakeLoggingReleaseObserver — selective clearing:**
Instead of calling `fizz->releaseHandshakeLogging()` (which resets the
entire struct), `HandshakeLoggingReleaseObserver::ready()` now mutates
the struct in place via `fizz->getState().handshakeLogging()` (which
already returns a non-const `HandshakeLogging*` from a const State&).
A private helper `releaseLargeHandshakeLoggingFields()` swap-with-empty's
the seven large vector fields populated from ClientHello:
  - clientSupportedVersions
  - clientCiphers
  - clientExtensions
  - clientSupportedGroups
  - clientKeyShares (Optional<vector<NamedGroup>>: .reset())
  - clientKeyExchangeModes
  - clientSignatureAlgorithms
The smaller fields commonly read post-handshake are preserved:
  - clientSni     (read by FizzPeeker, QuicServerTransport::getSni,
                   HTTPForwardProxyHandler, etc.)
  - clientAlpns   (read by addTLSInfo on every THRIFT_CONNECTION_EVENT)
  - clientRandom, clientLegacyVersion, clientRecordVersion,
    clientSessionIdSent, testExtensionByte, originalChloSize,
    outerChloInfo

This keeps observability intact while still reclaiming most of the
~1-2KB per-connection HandshakeLogging memory footprint.
