Commit title: Fix hazptr leak in PayloadSerializer
Commit body:
Summary:
`PayloadSerializer::getInstance()` protects the returned object with a hazptr, which is then stored in `ServerRequest` (through `SerializedCompressedRequest`) and passed from the IO thread to the worker thread.

Passing hazptr holders across threads is explicitly disallowed:
https://www.internalfb.com/code/fbsource/[ec5e863b75402f918454d1a817b02931658c912a]/fbcode/folly/docs/Hazptr.md?lines=574%2C580-581

This creates a situation where the hazptr thread caches run a deficit in the IO threads, and a surplus in the worker threads; returning back the hazptrs requires synchronization, which defeats the purpose of hazard pointers.

Since this is a hot codepath, using something like a refcount is out of the question; however, we can rely on the fact that `initialize()` is supposed to be only called at startup, once by each code path that wants to replace the strategy, and that cannot be more than a handful. So, instead of protecting the object, we can just make it immortal, removing the need for any synchronization on the reader.
