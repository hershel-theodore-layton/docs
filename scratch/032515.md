Commit title: Fix go_setter_name regression for consts referencing structs from included programs
Commit body:
Summary:
D102067835 refactored the Go thrift generator to populate codegen metadata via AST visitor callbacks. The new `go_setter_name` property handler in `t_mstch_go_generator.cc` throws a `whisker::eval_error` when a field is not present in `field_setter_names`. However, `add_struct_go_field_setter_names` is only invoked for structs in the current program:

```cpp
visitor.add_structured_definition_visitor(
    [this](const const_visitor_context& ctx, const t_structured& node) {
      if (&ctx.program() == current_program_) {
        add_struct_go_field_setter_names(node);
      }
    });
```

When a const is declared with a struct type from an **included program** and initialized via field assignments (e.g. `const acl.Identity SSH_RA_VERIFIER_IDENTITY = { "id_type": "...", "id_data": "..." };`), the `templates/go/common/constants.whisker` template emits `elem.field.go_setter_name` for fields that belong to the included program's struct — which were never registered, causing:

```
[ERROR:go/common/constants:84] Object 'elem.field' has no property named 'go_setter_name'.
Cause: field_setter_names not initialized with setter name for field id_type
```

This breaks builds like `buck build fbcode//security/ra/ssh/if:sshra-go-sshra.thrift`.

The pre-D102067835 code handled this case implicitly: it computed `"Set" + go_field_name` and only attempted to disambiguate when the parent struct was found locally. For external program structs no disambiguation occurred and the simple form was returned — which is correct because the include has already done its own disambiguation when emitting the struct's setter methods.

This change restores that fallback in the new property handler: when the field is absent from `field_setter_names`, return `"Set" + go::get_go_field_name(&self)` instead of throwing.
