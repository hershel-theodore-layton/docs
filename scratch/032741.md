Commit title: Add enforceable type alias check at enforceable positions
Commit body:
Summary:
Motivation:

Before this diff, the existing `Cross_pkg_access` check on a typedef reference only fired at the typedef *declaration site*. Once the typechecker resolved the alias to its underlying structural type, uses of the alias at runtime-enforced positions (params, returns, properties, enum bases, tparam upper bounds) silently passed package-boundary analysis. If the referenced typedef isn't loadable across the package boundary at runtime, HHVM's enforcement can fatal or throw — so the static check wasn't catching the actual runtime hazard.

Why only enforceable positions: the check is scoped to positions HHVM actually enforces at runtime. An earlier experiment (abandoned diffs D102344972 / D102347059 / D102354958) ran a stricter universal variant — firing at every typedef reference regardless of position or underlying type — and it flagged a large population of cases with no runtime consequence (tuple elements, interface method sigs, shape fields, refinement bodies, `(function(T): T)` closure internals, `where T as X` clauses, non-container generic targs, etc.). Tying the check to the HHVM enforcement boundary keeps signal:noise high and scopes the rollout to the real hazards.

Enum vs enum class: regular `enum E: T` *is* runtime-enforced on its base — HHVM's `Class::setEnumType` runs `resolvedWithAutoload` + `validForEnumBase` at class init and fatals if `T` is an unresolvable cross-package alias — so it counts as an enforceable position. `enum class E: T` is *not* — its `setEnumType` path is gated on `AttrEnum` which is skipped for enum classes, and its synthesized members (`getValues(): darray<string, T>` uses erased generics, `MemberOf<E, T>` erases to `mixed` via newtype) never observe `T` by name on an enforcement path.

Enforceable positions (errors when flag is off):
- Function / method / constructor params (including `inout`, `readonly`, promoted)
- Function / method / constructor return types
- Instance and static property types
- Abstract method signatures (the concrete override is invoked at runtime)
- Nullable `?T` at any of the above
- Upper-bound constraints on tparams (`T as X` on function, method, class)
- Regular `enum E: T` base type — see motivation above

Explicitly NOT checked:
- Variadic params (`T ...$args`) — not runtime-enforced
- Interface method signatures — interface methods are never invoked directly; only the concrete implementor is, and enforcement happens there
- Tuple element types — HHVM enforces a tuple as a vec of the right arity but does not check element types
- Enum class `enum class E: T` base — see motivation above
- Class constants (`const T X = ...`) — hackc strips the hint at emit time (see `emit_constant.rs`, no TypeConstraint on `PreClass::Const`), HHVM has no verifyClsCns path; the typechecker's Typing[4338] coercion is the only backstop
- Nested inside generics (`vec<T>`, `dict<_, T>`, `Box<T>`), shape field types, closure types, refinement bodies
- Where clauses, type alias RHS, explicit type constants (separate `Type_const` check), `as`/`?as` expressions (separate `As_expression` check)

Implementation:
- `typing_type_wellformedness.ml`: adds `in_interface` field on the local env struct and an `enforceable_type_alias_check` helper. `fun_param` inspects `param_info` to skip `Param_variadic`. `class_` sets `in_interface` from `c_kind` and passes `~base_is_enforceable:(is_c_enum c_kind)` to `enum_opt`.
- `typing_type_integrity.ml`: `Ttuple` and `Trefinement` branches stop propagating `Enforceable_type_alias` into element / refinement bodies.

Known limitations / follow-ups:
- `T as X` currently fires for every tparam `as` constraint. Ideally it should only fire when `T` actually appears at an enforced position in the signature (param / return / property / reified tparam). That requires per-tparam usage analysis; deferred.

Introduces a feature flag `package_allow_enforceable_type_alias_violations` (default `true`) to gate rollout. With the default, this diff is a no-op — the check fires only when the flag is set to false.

A follow-up diff adds a class-like carve-out so that aliases resolving to a class or interface (e.g. `type TEx = Exception`) do not fire — those go through HHVM's named-type lookup and are already covered by the existing `Cross_pkg_access` check at the class's use site. The strict-mode (`exp.v2.strict`) test artifacts that exercise the carve-out land alongside it.
