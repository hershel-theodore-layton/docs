Commit title: EB mode: offload stream subsequent item compression off the IO thread
Commit body:
Summary:
### Context
-------
D100902596 added EB-mode support for **initial response** compression offload via HandlerCallbackBase::getCompressionExecutorFallback(). However, **stream subsequent items** were still compressed on the IO thread in EB mode.

### Change
------
In HandlerCallback<T>::doResult(), when `executor_` is null AND `req_->isCpuCompressionEnabled()` is true, use the same getCompressionExecutorFallback() helper from D100902596 (which walks the context chain to the server's handler executor and falls back to folly::getGlobalCPUExecutor()). The fallback executor's lifetime is held by a local KeepAlive<> for the duration of Helper::call, which is sufficient since the cob captures it into its own KeepAlive<>.

Safety per callback type:
- Unary: the executor parameter is unused in HandlerCallbackHelper::call.
- Stream: the generator now runs on a CPU executor instead of the IO thread — matches TM-mode behavior.
- Sink / BiDi: the executor controls where the consumer runs; CPU executor is fine (and matches TM-mode behavior).
