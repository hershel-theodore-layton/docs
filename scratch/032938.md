Commit title: Schedule BiDi user coroutine at HI_PRI in CPU-pool mode; run inline in EB mode
Commit body:
Summary:
When a BiDi handler returns a `StreamTransformation`, `ServerBiDiStreamFactory::start()` builds the user's coroutine and schedules it onto the server executor via `co_withExecutor(serverExecutor, task).start()`. That uses the executor's default priority (`MID_PRI`), so under load the first iteration of every BiDi RPC waits behind whatever else is queued on the resource pool.

Switch to two execution paths based on whether `serverExecutor` is the IO thread's EventBase:

- **CPU-pool mode** (the common case): `addWithPriority(..., HI_PRI)` to bias the initial resume above other queued work on the resource pool.
- **EB mode** (handler annotated `cpp.ProcessInEbThreadUnsafe`, dispatched via `defaultSync` ResourcePool / `acceptSync`): `addWithPriority` would throw because `EventBase` inherits the throwing default `Executor::addWithPriority` from folly/Executor.cpp, and a priority bump is meaningless on a single-queue executor anyway. Use `startInlineUnsafe` to run the coroutine prologue synchronously on the IO thread (we are already on the EB, which is the task's bound executor — `startInlineUnsafe`'s precondition).

Subsequent resumptions (after the first `co_await`) are unaffected — the priority bump and the inline start only apply to the initial schedule.

Motivated by an investigation showing ~7ms p99 wall-clock between `callback->result(StreamTransformation{...})` returning and the user's lambda body executing on the dvaar/MySQL bidi path under load. The gap was attributed to scheduling latency, not framework setup work. See https://docs.google.com/document/d/1FGlFoh5zIT0dh6IHe5BbzFbywUhprrhekc88Ozo6b6A for the data.

The MySQL Thrift Server's `BidiSqlSession` interaction is annotated `cpp.ProcessInEbThreadUnsafe`, so without the EB-mode branch this change would crash the very service it was meant to optimize. Confirmed by the regression test added below: without the EB-mode branch, the test process terminates with `terminate called after throwing an instance of 'std::runtime_error': addWithPriority() is not implemented for this Executor`. With the branch, it passes end-to-end.

Caveats:
- Only the first resume is biased (CPU pool) or run inline (EB); subsequent iterations follow whatever the awaitable picks.
- CPU-pool case: this runs counter to `ParallelConcurrencyController`'s policy of scheduling new external requests at LO_PRI to favor in-flight continuations. Trade-off is intentional for BiDi startup, which is on the critical path of every RPC for clients that use first-query-via-RPC.
- Executors without priority queues will throw if reached on the CPU branch. The check `serverExecutor.get() == evb` covers the EB-mode case but does not cover hypothetical custom executors that lack `addWithPriority` and aren't an EventBase. None are known in production today; if encountered, extend the discriminator (e.g. `getNumPriorities() > 1`).
