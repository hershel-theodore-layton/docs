Commit title: distinguish notify wait termination
Commit body:
Summary:
We investigated a Watchman process that was holding one CPU for a long time.
`top -H` showed a single hot thread, TID 1290759, named `notify 14049573`.

A gdb backtrace showed that this thread was not processing filesystem events.
It was sitting in the notify wait path:

  Thread 44 (LWP 1290759 "notify 14049573"):
  #0  __GI___poll(...)
  #1  InotifyWatcher::waitNotify(int)
  #2  watchman::InMemoryView::notifyThread(...)

`perf report` matched that stack: nearly all samples were in the kernel `poll`
path, including `do_sys_poll`, `inotify_poll`, `fdget`, `fput`, and
time-reading helpers. This pointed to a tight poll loop rather than expensive
user-space event handling.

`strace` made the loop explicit. The hot thread repeatedly executed:

  poll([{fd=6, events=POLLIN}, {fd=4, events=POLLIN}], 2, 86400)
    = 2 ([{fd=6, revents=POLLIN}, {fd=4, revents=POLLIN}])

Each call returned in a few microseconds, and the trace showed the same poll
call repeating continuously.

`/proc/<pid>/fd` identified the two fds:

  fd 4 -> pipe:[82961748]
  fd 6 -> anon_inode:inotify

So the inotify fd had pending events, and the watcher terminate pipe was also
readable.

The old `InotifyWatcher::waitNotify()` implementation returned `false` whenever
the terminate pipe was readable. `notifyThread()` also used `false` for
timeouts, so it handled this result by continuing the outer loop. In the
observed state, `stopThreads_` was not set, so the outer loop did not exit.
That meant Watchman neither drained the terminate pipe nor consumed the pending
inotify events, leaving both fds readable and causing `poll()` to return
immediately forever.

This diff separates those states by making `waitNotify()` return `Ready`,
`Timeout`, or `Terminate`. `notifyThread()` now exits on `Terminate` and only
continues waiting on real timeouts.
