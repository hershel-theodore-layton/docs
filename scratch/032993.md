Commit title: NettyNiftyRequestContext: never let getRequestHeader() return null
Commit body:
Summary:
**Background**: Java thrift servers wrap each inbound request in a RequestContext. For the Rocket transport (and legacy Rocket, and legacy header) the implementation is `NettyNiftyRequestContext`, constructed per-request from the headers carried on the inbound frame. When a client sends a request with no header metadata, the headers map passed to that constructor is null.

**Bug**: the constructor stored that null verbatim. `getRequestHeader()` then returned null and `getClientTimeout()` did `.get(...)` on the same field. Any consumer that chains `.containsKey(...)` or `.get(...)` on `getRequestHeader()` NPEs on those requests. `LoadHeaderRpcServerHandler.singleRequestSingleResponse` is one such consumer (any service with `setLoadHeaderEnabled(true)` runs every request through it); a few external callers like `LoggingInterceptor`, `JobInstanceLogUtilities`, and `infrasec.Utils.shouldSetSrHeader` chain similarly.

**Fix**: default the null at the source. The constructor now coerces a null `requestHeaders` to `Collections.emptyMap()`. No call-site changes needed — every existing `.get(...)` / `.containsKey(...)` chain becomes safe by construction.

Scope: `NettyNiftyRequestContext` is constructed by all three production server transports — unified (the new ALPN-aware path in `ThriftConnectionAcceptor`), legacy Rocket (`ThriftServerRSocket`), and legacy header (`ThriftServerHandler`) — so the fix protects every server path that goes through it.
