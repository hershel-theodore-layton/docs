Commit title: getdeps: fix feature-hash ordering bug in create_builder
Commit body:
Summary:
D104437306 introduced a feature system where each project's hash now includes its resolved feature set. A child diff then added `[features]` and `[dependencies.feature_rpc=on]` sections to the fbthrift manifest, meaning fbthrift's dependency list (and therefore its hash) differs depending on whether features have been resolved.

`get_project_hash` (and by extension `get_project_install_dir`) was computing hashes before feature resolution had run. In a standalone `getdeps.py test` invocation (separate process from the build), `check_built` was called before `create_builder`, so in a fresh process the features were not yet resolved and `check_built` computed the wrong install-dir hash. That propagated into a different cachelib hash, so `check_built` looked for the install marker at the wrong path.

Fix: add an auto-resolve guard at the top of `get_project_hash`. If `_features_resolved` is False when hash computation is requested, it calls `manifests_in_dependency_order(manifest)`, which already contains the `resolve_features` logic. This makes the ordering of callers irrelevant — any code path that needs a hash will automatically trigger feature resolution for the relevant manifest, without requiring callers to pre-arrange a specific call order.
