Commit title: Add genOnError delegation to TClientMultiAsyncHandler
Commit body:
Summary:
`TClientMultiAsyncHandler` delegates all `TClientAsyncHandler` lifecycle hooks (`genBefore`, `genAfter`, `genWait`, `genBeforeStream`, `genAfterStream`, `genWaitStream`, `genWaitSink`) to registered sub-handlers — except `genOnError`, which was missing. This meant `TClientPoliciedAsyncHandler::genOnError()` was never invoked when a declared Thrift exception was received.

## Impact

Since `SRClient::setupAsyncHandler()` always wraps `TClientPoliciedAsyncHandler` inside a `TClientMultiAsyncHandler`, the missing delegation silently broke:

1. **Backward agentic context propagation on error paths** (D103056890) — `readAgenticContextFromResponseHeaders()` in `genOnError` was never called, so backward context bits like `hasBlockedDSS4Read` were dropped on every declared Thrift exception.
2. **PrivacyLib error observation for Tally** — `TallyUseCaseVirtualPolicyEnforcer::genProcessError()` never fired.
3. **PrivacyLib error observation for Scuba** — `ScubaDatasetVirtualPolicyEnforcer::genProcessError()` never fired.
4. **PrivacyLib error observation for Manifold** — `ManifoldBucketVirtualPolicyEnforcer::genProcessError()` never fired.
5. **ThriftServiceMethodName post-RPC error observation** — `ThriftServiceMethodNameVirtualPolicyEnforcer::genProcessError()` never fired.

The `THRIFT_ERROR_OBSERVATION` killswitch was guarding code that was already unreachable.

## Root cause investigation (P2312801818)

While investigating P2312801818 (backward_context not populated after a Zones block on `GDA_DSSINPUT_FILTERING`), we traced the full chain:

1. When Claude Code runs `meta google.docs get --id=<DSS4_doc>` (with `--local`), the command makes a Thrift call to `GoogleAPIProxyService`.
2. The server evaluates PZ2, blocks the DSS4 flow, calls `appendHasBlockedDSS4Read()` on the server's agentic context, writes it to the `privacylib-propagation` response header, and throws `GoogleAPIProxy\Exception` (a declared Thrift exception).
3. On the client, `ThriftClientBase::genRecvImplHelper()` deserializes the declared exception, calls `genInvokeOnErrorHook()` which calls `asyncHandler_->genOnError()`.
4. Since `asyncHandler_` is `TClientMultiAsyncHandler` (set by `SRClient`), and it had no `genOnError` override, the call hit the base class no-op. `TClientPoliciedAsyncHandler::genOnError()` was never invoked, so `readAgenticContextFromResponseHeaders()` never ran.
5. The backward context from the server (with `hasBlockedDSS4Read`) was silently dropped.

We confirmed this with `error_log` probes in `readAgenticContextFromResponseHeaders`: all other Thrift services (token.service, aclchecker.service, oncall_service, dvaar.tier_2, zgateway, laser.*) returned backward context via `genAfter` (success path), but `google_api_proxy` never appeared because it returns a declared exception that routes through `genOnError` exclusively. The `genOnError ENTER` probe also never fired, confirming the multi-handler was not delegating.

## Local verification

After adding the `genOnError` delegation, we verified locally using the P2312801818 repro (`meta --local google.docs get --id=<DSS4_doc>`):

- **Before fix:** `/tmp/privacylib_cc_<session>/state.json` showed 34 audit entries, ALL with `backward_context: {}` (empty). No `hasBlockedDSS4Read` bit. The top-level `backward_context` was also `{}`.
- **After fix:** `state.json` now shows `"backward_context": {"hasBlockedDSS4Read": {}}` at the top level, and one of the audit entries also contains `"backward_context": {"hasBlockedDSS4Read": {}}`, confirming that `genOnError` is now called, the server's backward context is read from the response header, and the `hasBlockedDSS4Read` bit flows back to the client session state.

## Fix

Add the missing `genOnError` override to `TClientMultiAsyncHandler`, following the exact same pattern as all other delegated methods.
