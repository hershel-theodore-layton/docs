## What

Parser changes for shape and tuple destructuring per spec: https://fburl.com/hack_shape_destructuring_hip .

Changes are gated the behind `shape_and_tuple_destructuring` unstable feature.

## Details

The changes here are a combination of new stuff and tweaks to the WIP implementation of an earlier version of destructuring that didn't ship:
- Rename the feature to `shape_and_tuple_destructuring` for clarity. Note that both versions of the feature supported both shapes and tuples.
- The previous WIP implementation did not distinguish between shape/tuple expressions and shape/tuple destructuring patterns. This was likely because we can't tell when we see `shape('x' => $x)` whether it's part of an expression statement `shape('x' => $x);` or a pattern `shape('x' => $x) = $sh;`.
     - **Before**: We had a "pattern of use" where different code to handle destructuring and expressions had to determine ad-hoc what something was.
     - **After**: We represent destructuring patterns as real syntax in the abstract syntax tree. In the lowerer, where we translate the concrete syntax tree to our abstract syntax tree, we detect whether we are in lvalue position and construct the correct abstract syntax tree nodes. Fwiw I find this way easier to understand and less mistake-prone.
- A few other differences to be closer to the new spec.

## Test Snapshot Changes

- **typecheck tests** currently show spurious errors because this diff stubs out typing for shape/tuple destructuring. In the next diff we re-implement typing for shape/tuple destructuring with a different approach that fulfills [the spec](https://fburl.com/hack_shape_destructuring_hip)
- **emit tests** have some tweaks because the [the spec](https://fburl.com/hack_shape_destructuring_hip) is more restrictive than what was done in the earlier prototype implementation. In particular `shape('x' => $v[0])` is no longer allowed, since such a construction would reveal evaluation order and the corresponding `list($v[0])` construction was rarely used in practice. We don't want to reveal evaluation order for **so many reasons**–see spec! (side effects in patterns would make it harder to extend to efficient pattern-matching, `list` evaluation order was right-to-left so we'd either be inconsistent with `list` or inconsistent the rest of Hack, hard for humans and agents to understand side effects in patterns, etc.).
