Commit title: Add Cpp2RequestContextHolder to guard against dangling Cpp2RequestContext access
Commit body:
Summary:
The Python `RequestContext` wraps a raw `Cpp2RequestContext*` pointer that becomes dangling after the C++ request lifecycle completes. Background tasks or leaked references that access properties like `read_headers` after the handler returns dereference this dangling pointer, causing a SIGSEGV.

This diff introduces `Cpp2RequestContextHolder`, a shared-ownership holder that sits between Python and the raw C++ pointer. The holder uses a single `std::atomic<Cpp2RequestContext*>` with `memory_order_relaxed` — `nullptr` is the invalid state, eliminating both the TOCTOU race and the need for a separate validity flag. The holder is installed via `Cpp2RequestContext::setRequestData()`, whose destructor fires during `Cpp2RequestContext` destruction on the IO thread, atomically nulling the pointer at exactly the right point in the C++ lifecycle.

**Opt-in enforcement**: By default the holder invalidator is not installed, preserving existing behavior for callers that access the context after the handler returns. Callers opt into safety via `enable_validity_enforcement()`, which installs the invalidator and causes `RuntimeError` on invalid access when properties that require the raw pointer (`priority`, `set_header`, `request_timeout`) are accessed, or when `read_headers`/`write_headers` entries are iterated. A public `is_valid()` method allows callers to check without raising.

`read_headers` and `write_headers` return lazy wrapper objects without eagerly checking validity — the actual `RuntimeError` is raised at the point of use (when the wrapper's underlying `_getMap` calls `_get_ctx()`), not at property access time. This avoids a TOCTOU race (checking validity then returning a wrapper that could become invalid before use) and preserves backward compatibility with callers that pass a default-initialized `RequestContext()` to mocked functions without accessing the headers.

**Shared ownership**: Python holds a `shared_ptr<Cpp2RequestContextHolder>`, and C++ holds a second copy inside `setRequestData`'s `erased_unique_ptr`. The destructor invalidates the holder and releases C++'s reference. The holder (and the knowledge that the pointer is null) outlives both sides safely.

**Eagerly-copied data**: `method_name` is copied into the holder at construction time, so it remains accessible after invalidation alongside `connection_context` and `request_id`.

## Why is it difficult to trigger asan?
The memory isn't actually freed until the `DebugStub` holding a reference is freed. By default, the last 10 responses are held in the `RequestRegistry`, so triggering asan in the Python test `test_request_context_invalidated_in_background_task` requires completing 10 subsequent requests to ensure the reference to the original request is decremented and the memory is actually freed.

```
ASAN detects use-after-free (accessing memory returned to the allocator), not use-after-destroy (accessing a destructed object whose memory is still allocated).

  The Cpp2RequestContext is an inline member of ThriftRequestCore, which is co-allocated with DebugStub in a single memory
  block via AllocationColocator (RequestsRegistry.h:307-343). When the request finishes, the custom Deleter
  (RequestsRegistry.h:235-262) does:

  1. moveToFinishedList() — moves the DebugStub to the finished list, calls incRef() (refcount: 1→2)
  2. p->~T() — destructs ThriftRequestCore (including ~Cpp2RequestContext()), but does NOT free memory
  3. stub_->decRef() — refcount: 2→1, memory stays alive because the finished list holds a ref

  The object is dead but the memory block is still allocated. ASAN can't see this.

  The memory is only truly freed when the DebugStub is evicted from the finished list (limit=10 per IO worker,
  ThriftServerConfig.h:826) or when RequestsRegistry is destroyed at server shutdown. The test sends 100 requests through 1
  IO worker, so eviction does happen — and the server is also stopped before the background task runs — so the memory IS
  eventually freed. But by then, the test only does _ = captured_ctx.read_headers, which doesn't dereference _ctx.
```
