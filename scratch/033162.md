Commit title: Fix Rust codegen for bidirectional streams with initial response
Commit body:
Summary:
The fbthrift Rust client codegen for bidirectional streaming methods that declare an initial response (e.g. `InitialResponse, sink<X>, stream<Y> echo()`) had three bugs that caused the client to fail with `MissingResult` ("Empty union ...Error") whenever the server actually serialized the initial response into field 0 of the result struct.

The server-side codegen already supported initial response (`server_ok_type` partial in rpc.whisker emits a 3-tuple `(Initial, Stream, Sink)`), but the client side was hardcoded to a 2-tuple and treated all bidi methods as if they had no initial response.

Fixes:

- `errors.whisker` — `{{Function}}Reader::Success` was forced to `()` for any bidi method by the `void_initial_response = (or function.bidirectional_stream? function.void_or_void_stream?)` predicate. Drop the bidi clause so the existing `function.sink_or_stream?` branch picks `function.return_type` for the initial response. Also remove the bidi special case in the shared `deserialize_initial_response_alt` partial; falling through to the `sink_or_stream?` branch produces `::fbthrift::Deserialize::rs_thrift_read(p)?`, which already works for bidi-without-initial-response (reads `()` from a `Void` field via the impl in `xplat/thrift/lib/rust/src/deserialize.rs`).

- `rpc.whisker` — client `return_type` for bidirectional streams now optionally prefixes with `(InitialResponse, ` when `function.sink_has_first_response?` is true, mirroring the existing `stream_has_first_response?` handling for server-streaming methods. Output is a flat 3-tuple `(InitialResponse, BoxStream, FnOnce)` matching the server-side `server_ok_type`.

- `client.whisker` — bidi body now binds the deserialized initial response to `initial_response` (instead of unconditionally discarding it as `_initial_result`) when there is one, and includes it in the result tuple. Also switches from `await??` to `await???` so the inner `Result<Success, Error>` is fully unwrapped (the third `?` propagates a typed handler error to the function's return type via `From`); the existing variant just left a `Result<(), Error>` sitting in `_initial_result` and silently dropped any handler error from the deserialization step.
