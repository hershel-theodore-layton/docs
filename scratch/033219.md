Commit title: Optimize crc32_sw for small buffers on x86 by avoiding unnecessary double bit-reversals
Commit body:
Summary:
**Inefficiency:** CRC-32 computation involves three logical steps: bit-reverse the input, polynomial division, bit-reverse the output. In `crc32_hw`, the PCLMULQDQ hardware path and the software fallback (`crc32_sw`) both keep the intermediate CRC state in bit-reversed form. So when `crc32_hw` calls `crc32_sw` for fringe bytes, the intermediate state (`startingChecksum`) is already bit-reversed. However, `crc32_sw` delegates the implementation to `boost::crc_optimal`, whose constructor expects un-reversed input. So, in `crc32_sw`, folly first un-reverses `startingChecksum`, just to have `boost::crc_optimal` constructor bit-reverses it back for internal storage via `reflect_unsigned`. The two reversals cancel out, but both are individually necessary due to the API contract of `boost::crc_optimal`.

Once `boost::crc_optimal` object is constructed, Boost's per-byte processing through `boost::crc_optimal::process_bytes` call is already efficient.

**Fix:** Replace the Boost dependency with a direct implementation to avoid the unnecessary double bit-reversals through the `boost::crc_optimal` construction. This allows the intermediate state (`startingChecksum`) to stay in bit-reversed form throughout. The per-byte loop is identical to what Boost's `reflected_byte_table_driven_crcs::crc_update` already does (`table[(crc ^ byte) & 0xFF] ^ (crc >> 8)`), just without the Boost object wrapping it.

**Why this matters:** `crc32_hw` on x86 calls `crc32_sw` for unaligned fringe bytes (0-15 bytes per call) that can't go through the PCLMULQDQ hardware path.

Benchmark on x86_64 (calling `crc32_sw` directly):

| Buffer Size | Old (Boost) | New (Table) | Speedup |
|-------------|-------------|-------------|---------|
| 8 bytes     | 22.12 ns    | 5.63 ns     | 3.93x   |
| 16 bytes    | 36.64 ns    | 16.01 ns    | 2.29x   |
| 32 bytes    | 69.18 ns    | 44.55 ns    | 1.55x   |
| 64 bytes    | 154.30 ns   | 128.41 ns   | 1.20x   |
| 1 KB        | 2.73 us     | 2.72 us     | 1.00x   |

Large buffers converge because both implementations spend most time in the identical per-byte table loop.
