Commit title: Fix flaky `ResponseWriteTimeout` test on mac-arm64
Commit body:
Summary:
The `HeaderOrRocket/HeaderOrRocket.ResponseWriteTimeout/1` test occasionally fails on mac-arm64 because macOS TCP buffer auto-tuning dynamically enlarges socket buffers after the test explicitly shrinks them. This allows the server to push the entire response into kernel buffers before the write timeout fires, causing `messageSent()` to cancel the timeout and the client to receive the response successfully.

Three changes fix this:

1. **Enforce a minimum response size of 2MB** regardless of `SO_SNDBUF` value, ensuring the response always overwhelms kernel auto-tuned buffers on macOS (which can grow up to `tcp_autosndbufmax`, typically ~1MB).

2. **Reduce the write timeout from 1000ms to 200ms**, widening the margin between the timeout and the time needed to drain a 2MB+ response through a slow reader (1000 bytes / 100ms = ~10KB/s).

3. **Use platform-aware `setRecvBufSize`** in `SlowReadCallback::install()`, matching the `folly::kIsLinux ? 0 : 1` pattern already used elsewhere in the same file (e.g., `EnforceEgressMemoryLimit` test at line 775).
