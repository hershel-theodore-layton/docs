Commit title: Offload stream/sink/bidi response decompression from IO thread to consumer thread
Commit body:
Summary:
Response decompression for stream, sink, and bidi RPCs currently happens on the IO thread inside DefaultPayloadSerializerStrategy::unpack, called from `RocketClient::handleStreamResponse` / `handleSinkResponse` / `handleBiDiResponse`. This adds CPU work to the IO thread. StrobeLight confirms uncompressBuffer on the IO thread's `AsyncSocket::ioReady` stack.

This diff offloads that decompression to the consumer thread (the coroutine/fiber that consumes stream elements), gated by the existing `thrift_client_compress_request_on_cpu` flag.

How it works — two coordinated changes with a clean flag-OFF/flag-ON contract:

1. Transport level (RocketClient): When the flag is enabled, use `unpackAsCompressed` instead of `unpack` for stream/sink/bidi payloads, skipping IO-thread decompression. Also activates `skipDecompression` for unary responses in `sendSingleRequestSingleResponse` (previously hardcoded to false).
2. Consumer level (decode path): `decode_stream_element` in `GeneratedCodeHelper.h` now checks `metadata.compression()` and decompresses before deserialization. This naturally runs on the consumer's thread, not the IO thread. The same function handles all three cases: stream payloads, sink final responses, and bidi stream elements.

To coordinate these two layers without coupling, `DefaultPayloadSerializerStrategy::unpack` now clears `metadata.compression()` after decompression. This means:
- Flag OFF: unpack decompresses AND clears compression metadata → consumer sees no compression → no-op
- Flag ON: `unpackAsCompressed` skips decompression, compression metadata stays set → consumer decompresses

Also adds `Flags::clientCompressRequestOnCpu()` helper to `servicerouter/common/Flags.h` following the existing pattern, replacing scattered `THRIFT_FLAG_DECLARE_bool` + `THRIFT_FLAG(...)` usages in production code.
