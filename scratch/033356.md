Commit title: KeyUpdate: call configureClientRecordLayer on new AppTraffic layers
Commit body:
Summary:
fizz's tls state machine creates new `AppTraffic` `EncryptedReadRecordLayer` / `EncryptedWriteRecordLayer` instances during the client KeyUpdate handlers (`KeyUpdateInitiation` for client-initiated, `KeyUpdate` for peer-initiated + reciprocal write), but does not call the corresponding `configureClientRecordLayer` hook that was introduced in D73874318.

downstream subclasses (e.g. `facebook::services::CompositeReadRecordLayer` / `CompositeWriteRecordLayer`) rely on that hook to flip per-connection state...

when it is skipped the new layer silently regresses to the standard fizz AAD framing while the peer (whose own configure was called via the symmetric server-side `KeyUpdateInitiation` handler that already wires it) keeps using the enhanced framing. The AAD mismatch fails AEAD authentication on the first post-KeyUpdate record with `fizz::FizzException: error decoding record in state Established: std::runtime_error: decryption failed`.

this was reproduced by ellenhuang in standalone SSC → HN benchmarks with StopTLSv2 enabled. the companion server-side fix is above.
