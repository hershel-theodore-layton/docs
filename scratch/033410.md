Summary:
Reland of D103913775 + D103914232 with fixes for linker relocation overflow (T271330365).

The original diffs changed `ClientInterceptor::onResponse` from `void` to `std::optional<folly::coro::Task<void>>` and wrapped `processClientInterceptorsOnResponse` return types in `InterceptorResult<T>` = `std::variant<Try<T>, Task<Try<T>>>`. This caused linker relocation overflow in ~100 opt-mode binaries because:

1. `InterceptorResult<T>` was instantiated per RPC return type (every generated sync client method), creating variant+Task machinery for each T
2. `blockingWaitInterceptorResult<T>` was a template instantiated per T with `std::get_if<Task<Try<T>>>` and exception handling entries
3. A per-T coroutine lambda was generated inline in `processClientInterceptorsOnResponse(THeader*, Try<T>&&)`
4. Generated co_ header methods inlined `std::get_if<Task>` + `co_await` dispatch per method

This reland avoids all four issues:

- `InterceptorResult<void>` is the only variant instantiation — the `Try<T>` overload returns `folly::Try<T>` directly by resolving `InterceptorResult<void>` eagerly via `resolveInterceptorResult`
- `blockingWaitInterceptorResult` is a non-template function accepting `InterceptorResult<void>&&` only
- No per-T coroutine lambda — the `Try<T>` template calls `resolveInterceptorResult` which is an inline sync-path check + out-of-line `blockingWait` for the rare async case
- Generated co_ methods use non-template helpers: `interceptorResultHasTask` (inline bool check) to skip coroutine frame allocation on the sync path, `coExtractInterceptorTask` (inline Task extraction) for true `co_await` on the async path

Validated: 7 opt-mode targets that fail with original D103913775 all pass with this reland. Section layouts are byte-identical to remote/master for tested binaries.
