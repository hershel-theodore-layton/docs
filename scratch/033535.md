Commit title: Preserve zero-copy state across StopTLS plaintext transition
Commit body:
Summary:
toFDSocket() creates a new AsyncSocket after StopTLS handshake completes,
but does not preserve the SO_ZEROCOPY state from the original socket.
This causes StopTLS connections using the standard (non-modified) path
to fall back to copy_from_user on every sendmsg, adding ~6% CPU overhead
for large data transfers.

Fix:
1. SSLUtil.cpp: Capture hadZeroCopy from the underlying AsyncSocket before
   detachNetworkSocket, then re-enable SO_ZEROCOPY on the new socket.
   Only covers the TCP (AsyncSocket) path; the io_uring path would need
   separate handling via AsyncIoUringSocket.

2. TCPAwaitableTransport.cpp: Move setZeroCopy() + setZeroCopyEnableThreshold()
   from connect() (before fd exists — setsockopt silently fails) to
   preConnect() (after fd exists, before connect completes).

3. TLSFizzAwaitableTransport.cpp: For the standard toFDSocket path,
   re-enable SO_ZEROCOPY + threshold on the plaintext socket using
   the threshold from TLSFizzTransportConfig. For the modified
   (useModifiedStopTLSDowngrade) path, zero-copy state is already
   preserved because tryExchangeWrappedTransport steals the entire
   AsyncSocket object. Added XLOG instrumentation on both paths to
   validate zero-copy state post-downgrade.

4. TransportConfigs.h + SSLSocketFactory.cpp: Plumb zeroCopyThreshold
   from ConnectionContext into TLSFizzTransportConfig so the StopTLS
   callback can restore the caller's configured threshold. Added
   TODO(T273011121) for removal when toFDSocket is rewritten to steal
   the whole AsyncSocket.
