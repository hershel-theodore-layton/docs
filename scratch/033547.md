Commit title: Migrate stats from SlidingTimeWindowMovingCounter to CompositeMovingCounter
Commit body:
Summary:
Replaces `SlidingTimeWindowMovingCounter` in the four Java-runtime call sites — `ThriftClientStats`, `ServerStats`, `GcStats`, and `VirtualThreadScheduler` (Java 21 multi-release) — with `CompositeMovingCounter` (the counter introduced in the parent diff). All sites use only the `Rate` interface methods (`add(long)`, `oneMinuteRate()`, `tenMinuteRate()`, `oneHourRate()`); the migration is mechanically an import + type + constructor swap.

Deletes `SlidingTimeWindowMovingCounter.java` and its test (`SlidingTimeWindowMovingAverageTest.java` — misnamed; it tested the counter directly, and its coverage is fully subsumed by `CompositeMovingCounterTest` from the parent diff).

The new counter is strictly an upgrade. The old implementation eagerly allocated an `ArrayList<LongAdder>` of 3600 buckets (1s × 60 minutes) per counter, ran a linear scan via `tickIfNecessary()` on every `add()`, and built a fresh `LongAdder` plus a `Stream.skip().limit().mapToLong()` traversal on every rate read. `CompositeMovingCounter` uses 180 `AtomicLong` slots across three packed rings plus one `LongAdder` reservoir, with a single CAS per rotation (regardless of which window is read) and an O(1) hot-path `add()`. Memory footprint per counter drops by roughly an order of magnitude, and read paths no longer allocate.

Verified no external consumers reference `SlidingTimeWindowMovingCounter` outside `thrift/lib/java` — the only matches across the repo are auto-generated buck autodeps index TSVs under `autodeps2/indexers/jvm/index/`, which regenerate after the deletion.
