Commit title: Always propagate unavailability of memory read to the root block during register rematerialization
Commit body:
Summary:
mem_read_available_recurse is called to check if a memory read is available at instIdx in a block b. This method does a walk of all the predecessors of the block to check if there is a conflicting write. The results of this walk are cached for faster future lookups in state.memReadAvailableCache. The cached result of a block B is set to:
1. TriBool::Maybe to indicate that B has been visited but its results are not yet finalized (its predecessors are currently being analyzed)
2. TriBool::Yes if each of B's predecessors are either a) currently processing (backedge) or b) have the memory read available.
3. TriBool::No if any one of B's predecessor has a conflicting write. Since we may have optimistically set the availability of a block in B's subtree to Yes in 2a), propagate the No to B's successor tree ("fixup").

There is however a bug in the current code which omits updates to the root block (rematerialize point). If a block has only one successor, its fixup is skipped because the successor should be the next block in the recursive call stack which should handle it correctly after the function exits from the current level. However, this doesn't hold true for the root call block as there is no caller that can fix its subtree. This results in stale TriBool::Yes entries of B's successors. If a subsequent walk comes across this cached result, it will incorrectly overlook the conflicting write and assume the memory is available for rematerialization.

 {F1989993958}
This minimal cfg demonstrates the problem.
```
B1 -> [B0] (yes)
      [B5] -> [B3, B2, B1, B5] backedge via B5 found, so set these blocks to Yes
              [B4] (conflicting write)  set B4 to No
      set B5 to No
set B1 to No
```
But since B1 has only one successor, fixup for B1 doesn't run leaving B2 and B3 in the cache as Yes incorrectly.
