## Motivation

Services migrating incrementally from fibers to coroutines need both fiber and coroutine callers to contend on the same mutex instance. `folly::coro::Mutex` only provides `co_lock()` — fiber code cannot use it. `folly::fibers::TimedMutex` only provides `lock()` — coroutines calling it block the OS thread because `baton_.wait()` takes the futex path outside fiber context.

Neither mutex can serve both callers alone. This diff adds `co_lock()` and `co_scoped_lock()` to `TimedMutex` so that fibers call `mutex.lock()` and coroutines call `co_await mutex.co_lock()` on the same instance, correctly serializing against each other. Once all callers are migrated to coroutines, the mutex can optionally be replaced with `coro::Mutex`.

This follows the same pattern as `fibers::Semaphore::co_wait()` and completes the intent of D8580775, which made `fibers::Baton` awaitable specifically to enable reuse of fiber primitives like `TimedMutex` from coroutines.

## Implementation

`co_lock()` enqueues a `MutexWaiter` into `fiberWaiters_` and does `co_await waiter.baton()` instead of `waiter.wait()`. The `fibers::Baton` already has coroutine support via `BatonAwaitableWaiter` (D8580775), so `unlock()` dispatches correctly to coroutine waiters with no changes.

`co_scoped_lock()` wraps `co_lock()` and returns a `std::unique_lock<TimedMutex>` via `std::adopt_lock`, following the `coro::Mutex::co_scoped_lock()` pattern.

Supports cancellation via `CancellationToken`, following the same pattern as `Semaphore::co_wait()`: a `CancellationCallback` removes the waiter from the list under `lock_` and posts the baton. The `is_linked()` check under the spinlock serializes with `unlock()` dequeue to resolve the race.

Also adds benchmarks comparing lock() vs co_lock() across thread, fiber, and coroutine configurations.

## Timeout usage

`co_lock()` supports timed acquisition via `folly::coro::timeoutNoDiscard()`:

```cpp
co_await folly::coro::timeoutNoDiscard(mutex.co_lock(), 100ms);
```

**Do NOT use `folly::coro::timeout()`** — the `discard=true` variant can throw `FutureTimeout` even when the lock was successfully acquired, permanently leaking the mutex. `timeoutNoDiscard()` preserves the result when `co_lock()` succeeds, regardless of whether the timer also fired.

## Known gaps
- No native timed variant (`co_try_lock_for`) — use `folly::coro::timeoutNoDiscard(mutex.co_lock(), duration)` as a stopgap
- No `TimedRWMutexImpl` equivalent — only `TimedMutex` is covered
- Coroutine waiters always use `fiberWaiters_` regardless of `Options::stealing_`
