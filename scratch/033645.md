Commit title: folly/AsyncUDPSocket: per-fd zero-copy bookkeeping with release callback
Commit body:
Summary:
Unifies MSG_ZEROCOPY completion tracking on `AsyncUDPSocket` around a single per-fd `ZeroCopyFdBookkeeping` object. Each `AsyncUDPSocket` is constructed with its own internal `ZeroCopyFdBookkeeping`; the bookkeeping is not exposed on the public API. Sharing across fd-aliasing instances (e.g. `SO_REUSEPORT` workers using `setFD(SHARED)`) is supported through a dedicated factory that wires the shared `shared_ptr` correctly, so callers cannot accidentally desynchronise per-fd state.

The new `writeChain(wcb, addr, buf, options)` overload takes a lean `AsyncUDPSocket::WriteCallback` whose only method is `getReleaseIOBufCallback()`. When the write goes out as MSG_ZEROCOPY successfully, the release callback (if non-null) is invoked once with the IOBuf after the kernel posts the completion, so callers can pool/recycle the underlying memory. The existing 3-arg `writeChain` delegates with `wcb=nullptr`, preserving behavior for current callers.

There is no longer a per-instance `idZeroCopyBufMap_` — the bookkeeping is the single source of truth, which removes the dual-path branch in both `writeChain` and `processZeroCopyMsg` and the duplicated empty-check in `handleErrMessages`.

Removed from the public surface: `getZeroCopyBufId()`, `addZeroCopyBuf()`, `releaseZeroCopyBuf()`, `getNextZeroCopyBufId()`, and the `zeroCopyBufId_` counter. All in-tree callers of these symbols are on `folly::AsyncSocket` (TCP), not `AsyncUDPSocket`, and are unaffected.

Behavior change worth noting: `ioBufFreeFunc_` no longer fires on MSG_ZEROCOPY completion. It still fires synchronously at the end of `writeChain` for the non-zerocopy and ENOBUFS-fallback paths (where the kernel copies the data and immediately releases the userspace IOBuf).
