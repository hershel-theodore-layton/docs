Commit title: Fix sporadic libtbbmalloc.a race in parallel make
Commit body:
Summary:
`libtbbmalloc.a` sporadically failed to build under parallel make, with errors like `ar: libtbbmalloc.a: file format not recognized`, `make[1]: *** [../../build/Makefile.tbbmalloc:111: -o] Error 1`, and `ar: unable to copy file 'libtbbmalloc.a'; reason: No such file or directory`.

Root cause: `MALLOC.STATIC` was defined as `$(LIB_OUTPUT_KEY)libtbbmalloc$(CPF_SUFFIX)$(DEBUG_SUFFIX).a`. `LIB_OUTPUT_KEY` is unset on this platform and falls back to `$(OUTPUT_KEY)` (`common_rules.inc`), which is `-o ` with a trailing space (`common.inc`). So `MALLOC.STATIC` expanded to the two whitespace-separated tokens `-o libtbbmalloc.a`, and GNU make parsed the static-lib rule as a multiple-target rule with the two targets `-o` and `libtbbmalloc.a` sharing a single recipe. Because the recipe referenced `$(MALLOC.STATIC)` rather than `$@`, both target instances ran the identical command `ar -rcs -o libtbbmalloc.a $(MALLOC.OBJ)`. Under `make -j` (rules.py builds with parallel=True) the two `ar` processes wrote `libtbbmalloc.a` concurrently and clobbered each other, which is the sporadic failure. The make target reported as `-o` is the fingerprint of the two-token expansion, and `Waiting for unfinished jobs....` confirms a parallel build.

This static-tbbmalloc rule is FB-local (added in D30234077); upstream TBB 2018_U5 does not build a static tbbmalloc at all, and its supported static-build path (`extra_inc=big_iron.inc`) sets `LIB_OUTPUT_KEY` empty, so upstream never hit this. The `-o ` prefix is a linker output flag that belongs only in the `.so` link recipes, not in an `ar` target name.

Fix: drop the stray `$(LIB_OUTPUT_KEY)` prefix so `MALLOC.STATIC` is the single token `libtbbmalloc.a`. The rule now has exactly one target and one `ar -rcs libtbbmalloc.a ...` recipe, so the duplicate concurrent `ar` invocation, and the race, can no longer occur.
