Commit title: Fire lint 5655 on any override the caller depends on, not just same-package overrides
Commit body:
Summary:
D107104593 gated lint 5655 on `current_name = target_name`, so it only fired when a `__PackageOverride` pulled the callee into the caller's *own* package. That is too narrow: the lint exists to flag edges that compile *only because of* an override, regardless of which package the override targets.

5655 now fires iff (1) the caller can reach the callee's overridden package — otherwise it is a hard package violation, not a lint — and (2) the caller cannot reach the callee's underlying, pre-override package, i.e. the override is load-bearing. `can_access_ignoring_package_override` already computes (2), so this drops the `current_name = target_name` guard and delegates to it for every `(PackageConfigAssignment, PackageOverride)` edge. Underlying-package reachability is the sole criterion; whether the target is reached structurally (via `includes`) or by a runtime `package` / `__RequirePackage` load no longer matters.

This restores firing on the `intern -> gen_execx@scripts` (overridden into `prod`) shape D107104593 suppressed: `intern` reaches `prod` but not `scripts`, so the override is the only reason that edge compiles.

```
// gen_execx.php -- assigned to package `scripts`, but pulled into `prod`
<<file: __PackageOverride('prod')>>
function gen_execx(): void {}

// caller.php -- in package `intern`; intern includes prod, but NOT scripts
function run(): void {
  gen_execx(); // Lint[5655]: drop the override and gen_execx is back in
               // scripts, which intern cannot reach, so this edge only
               // compiles because of the override.
}
```

The pre-D107104593 `when package_includes current_pkg target_pkg` guard is deliberately not restored. It would suppress the lint whenever the caller reaches the overridden package only because that package is runtime-loaded (an `if (package ...)` / `__RequirePackage` gate on the target) rather than via structural `includes` — but the underlying package is still unreachable in those cases, so the override is still load-bearing and the edge should fire.

```
// gen_execx.php -- package `scripts`, pulled into `prod`
<<file: __PackageOverride('prod')>>
function gen_execx(): void {}

// caller.php -- in package `tool`, which does NOT include prod
function run(): void {
  if (package prod) { // reaches prod via a runtime load, not via includes
    gen_execx();      // still Lint[5655]: scripts is still unreachable, so
                      // the override is still load-bearing. The dropped
                      // package_includes guard would have silenced this.
  }
}
```

The 5655 message also no longer claims the callee is "already in the caller package" (false when the target merely includes the caller). It now reads: "Although the callee is accessible to the caller's package {current} via __PackageOverride('{target}'), that package override is load-bearing here: without it the callee stays in package {underlying}, which {current} cannot reach, so this edge would be an error. This edge prevents removal of the __PackageOverride and SHOULD BE REMOVED." followed by the existing hg mv / __RequirePackage / package-check guidance.

`lint_into_override_03` is isomorphic to the suppressed case and expects a lint again; the other pre-existing `.exp` changes are message-wording only. Two new tests pin the dropped-guard behavior: `lint_into_override_loaded_target` — caller in `pkg1` reaches the override target `pkg2` only via a runtime `package pkg2` check, and the underlying `pkg3` is unreachable, so 5655 fires (the removed `package_includes` guard would have silenced it since `pkg1` does not include `pkg2`) — and `lint_into_override_loaded_target_guarded`, the same setup additionally gated on the underlying `package pkg3`, which must not lint.
