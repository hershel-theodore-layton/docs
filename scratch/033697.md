Commit title: Fast path for saturated IntervalRateLimiter
Commit body:
Summary:
Every `check()` performed a `fetch_add` on `count_`, contending a cache line across threads even when the limiter was already saturated and the call was guaranteed to be rate-limited. Under heavy logging this contention dominates the cost we are nominally trying to avoid.

The previous implementation was structured around the assumption that a clock read is more expensive than an atomic increment, so `count_` was the cheap fast-path check and the clock was consulted only in `checkSlow`. On modern hardware the opposite is true, especially under contention: `coarse_steady_clock` is a couple of loads from a vDSO page, while a contended `fetch_add` serializes through the cache coherence protocol and can cost orders of magnitude more as the number of threads grows.

Add a fast path that, when the current interval is still active and `count_` is already at the cap, returns `false` after two ordinary loads with no RMW.

To make the fast-path interval check cheaper, repurpose `timestamp_` to store the end of the current interval rather than the start, so the check is `now < timestamp_` instead of `now < timestamp_ + interval_`. The `kInitialTimestamp = min` sentinel still naturally falls through to `checkSlow` on the first call.

`checkSlow` keeps the original ordering of `count_.store(1, release)` *after* the CAS that publishes the new interval end. Resetting before the CAS would close the visibility window between the new `timestamp_` and the stale `count_` seen by a fast-path reader, but a losing CAS would then stomp the winner's count and could admit up to `maxPerInterval_` extra events. The retained ordering leaves only a few-instruction window in which a fast-path reader may falsely reject one event at the interval boundary -- acceptable for a rate limiter, since calls are unordered across threads and a falsely-rejected one is indistinguishable from one that arrived just before the boundary.
