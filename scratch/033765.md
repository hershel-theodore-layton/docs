Commit title: Fix the build after upstream rework
Commit body:
https://github.com/facebook/hhvm/commit/c5f58c11d1707016fbcfa59abd0bc930e22503f9
reworked the OSS build extensively and got rid of building Meta
first-party deps via `ExternalProject` in favor of discovering them via
`find_package`. This is arguably more idiomatic CMake since the general
consensus these days appears to be to decouple dependency management
from the project build system - `find_package` doesn't care whether
the dependency is supplied by a system package, by a PM like Conan,
by `CMAKE_PREFIX_PATH` populated by getdeps or whatever.
It also rids us of various patches to folly/fizz that are no longer
needed.
So take this opportunity to do a wholesale cleanup:

* Remove vendoring for everything that we can build via `getdeps`
  or trivially install as a system package. This includes all Meta
  first-party deps, zstd, jemalloc, boost, glog, gflags, fmt, lz4,
  magic_enum, brotli, double-conversion, libsodium, libzip, rust
  and re2.
* Move most `find_package` calls to `HPHPFindLibs.cmake` where most
  of them were living already, so that it's easier to see them at a
  glance. Also avoid creating `INTERFACE` libraries for dependencies
  that already expose CMake targets (notably all Meta first-party deps).
* Vendor the single-header `usdt` library under `third-party/usdt`.
  https://github.com/facebook/hhvm/commit/c5f58c11d1707016fbcfa59abd0bc930e22503f9
  was trying to load it from a Meta internal directory.
  The official [usdt
docs](https://github.com/libbpf/usdt/blob/b0144b02dd885941cf60b2359365c768ee602b27/README.md)
  explicitly encourage consuming the library in this manner.
* Make `HPHPCompiler.cmake` into a base toolchain file and introduce
  `HPHPClangToolchain.cmake` so that we can use the same compiler
  and hardening flags for both getdeps-built dependencies and HHVM
  proper via a simple `CMAKE_TOOLCHAIN_FILE` stanza.
  This is especially handy since we're using a full LLVM toolchain
  so we want to make sure every C++ dependency is built with libc++.
* Bring back the explicit Cargo.toml for `generate_configs`.
  https://github.com/facebook/hhvm/commit/c5f58c11d1707016fbcfa59abd0bc930e22503f9
  tried to replace it with a synthetic Cargo.toml generated in the
  configure phase, but this isn't very workable because the `options`
  crate in `hack` also has a dependency on this library.
  We'll have to ask someone to fix the autocargo exports.
* Partially revert the Hack Rust FFI changes from https://github.com/facebook/hhvm/commit/c5f58c11d1707016fbcfa59abd0bc930e22503f9
  which broke linking the FFI staticlib into the final HHVM executable.
  Return to the previous working arrangement instead where we create
  a Rust staticlib and a C++ staticlib and declare an explicit circular
  dependency between the two so that the linker can work out the
  details. Symlink cxxbridge headers from the synthetic Rust staticlib
  to their original package paths under the build directory as some
  `#include`s expect to find them there.
* Get rid of `hphpize` and supporting infrastructure, as it's been
  without use since HHVM dropped support for developing and loading
  shared library extensions.
